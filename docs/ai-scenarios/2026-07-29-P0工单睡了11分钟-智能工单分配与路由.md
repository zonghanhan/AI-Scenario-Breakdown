# 2. 业务场景故事

## 《周五 17:03，那条标着 P0 的工单在公共池里睡了 11 分钟》

### 第一章：17 点整，公共池里堆了 143 条未分配工单

周五下午，企业协作 SaaS「连犀」的客服中心进入每周最忙时段。销售在冲月底回款，客户在催「为什么昨天还能登录，今天全员掉线」。

客服主管赵敏盯着大屏：未分配工单 143 条，平均等待 6 分 40 秒，VIP 客户「华鼎制造」的工单已经红了 4 分钟——按 SLA（服务等级协议，就是和客户签的响应时限承诺），P0 工单必须在 5 分钟内被**正确的人**接单。

刚转岗做 AI 产品的林舟被拉进战情室：「算法组说意图分类模型准确率 91%，今晚能不能上线自动派单？」

一线组长老周冷笑：「91% 是实验室数字。上周你们把『发票打不开』分给财务接口组，财务组根本不会修客户端崩溃。」

赵敏敲桌子：「今晚别讨论模型分数。我要的是：VIP 不再睡公共池，新人不再接数据库宕机，值班表和技能表对得上。林舟，你给我路由方案，不是分类报告。」

**悬念**：林舟心想——派单不就是匹配一下关键词吗？能有多难？

---

### 第二章：关键词路由上线第一天，「退款」成了黑洞

林舟的第一版方案很「互联网」：规则引擎按关键词路由。

- 含「登录」「闪退」「崩溃」→ 客户端组
- 含「同步失败」「接口」「webhook」→ 开放平台组
- 含「账单」「发票」「退款」→ 商务运营组
- 其余 → 公共池，客服手动领

周一上线，自动化率冲到 78%，赵敏在晨会表扬。下午三点，华鼎制造发来工单：

> **标题**：P0｜生产环境全员无法登录，影响 2,300 人  
> **正文**：从 14:50 开始 OAuth 回调失败，请立即处理。另：上月发票金额有误，请一并核对。

系统做了两件事：

1. 命中「登录」「OAuth」→ 分给客户端二线工程师小韩；
2. 命中「发票」→ **拆出子工单**分给商务运营。

小韩 8 分钟接单——勉强踩进 P0 线。但真正的问题是 OAuth：**根因在身份服务证书过期**，属于基础设施组，不在小韩的技能表里。小韩花了 20 分钟才发现要转单，期间华鼎工单状态一直是「处理中」，SLA 计时却没停。

更糟的是那条被拆出去的「发票有误」子工单：在商务池里睡了 47 分钟，因为商务同事以为「P0 登录问题」还在主工单里跟着处理。

华鼎客户成功经理在群里 @ 了 CEO。

林舟的复盘写在白板上：**关键词只认识词，不认识优先级组合；拆单策略没跟 SLA 绑定；路由不看技能，只看字面。**

**悬念**：赵敏说：「别急着上模型。先把值班表、技能表和 VIP 名单接进来。」

---

### 第三章：技能标签加上了，负载均衡却把最熟的人饿死了

第二版，林舟引入 **技能标签（Skill Tag）** 和 **负载均衡（Load Balancing）**：

- 每个客服/工程师有技能：客户端、身份认证、数据库、计费、开放平台……
- 每张工单经意图分类后，映射到所需技能组合；
- 路由时选「在线 + 有技能 + 当前待办最少」的人。

周三压测，平均等待从 6 分 40 秒降到 3 分 10 秒。林舟以为稳了。

周五同类事故再来：身份证书过期，意图分类正确标为「身份认证 / P0」，系统找到了三个有「身份认证」技能且负载最低的工程师——**全是入职 3 个月内的新人**，而唯一处理过上次证书事故的资深工程师老何，因为手头有 2 张 P1 工单，被算法判为「不够空闲」。

新人尝试重启、清缓存、让客户重装客户端，浪费了 15 分钟。老何在隔壁工位听到关键词，手动抢单，3 分钟定位证书，但 SLA 已经超时 9 分钟。

老周指着监控：「你的均衡是 **工单数量均衡**，不是 **风险能力均衡**。证书过期一年遇一次，但遇上了就是 P0 中的 P0。」

林舟第二次意识到：智能派单不是「找最闲的人」，而是「找**此刻最合适**的人」——合适包括技能深度、历史相似案例、是否值班负责人、甚至是否刚处理完同类问题（上下文还在脑子里）。

**第二个产品二选一**：优先「最闲的人」还是「最能搞定的人」？赵敏的答案很干脆：**P0/P1 走能力优先，P3 长尾走负载均衡。**

---

### 第四章：SLA 优先级与 VIP 策略——不是贴个标签就完事

第三版，林舟把路由拆成两层决策：

**第一层：优先级与队列准入（该不该插队）**

- 客户等级：战略客户、VIP、标准
- 工单严重度：P0 生产不可用、P1 核心功能受损、P2 单用户、P3 咨询
- 情绪信号：模型从正文里打出「愤怒」「威胁续约」等标签，只做 **加权**，不单独决定路由

**第二层：在正确队列里选代理人（该给谁）**

- 硬约束：技能匹配、值班表、是否可接外呼
- 软排序：相似历史工单处理量、近 30 天同类 SLA 达标率、当前负载（P0 时权重降低）

同时加了 **VIP 兜底规则**：战略客户 P0，若 3 分钟内无人接单，自动升级到值班长，并同时拉客户成功经理进协同频道——不是再分一条新工单，而是 **升级事件（Escalation）**。

试点第一天，就出了一条尴尬记录：

> **标题**：P0｜系统登录不了！！！  
> **客户**：某 20 人小团队试用版  
> **正文**：明天要给老板演示，急！！！

情绪模型打出「高焦虑」，严重度模型打出「登录类高频故障」，优先级被抬到 P1，插进了 VIP 队列前面。而真正华鼎的 P0 证书事故，因为标题写得克制，在第一版模型里只被判成 P1，排在后面 2 分钟。

赵敏看着两条工单的时间线：「客户喊得响，不等于事故响。试用版 20 人和生产 2,300 人，能一样吗？」

林舟加了两条 **业务硬规则**（永远压过模型）：

1. **客户等级封顶**：试用版工单最高 P2，不得占用 P0 值班通道；
2. **影响面字段必填**：企业客户工单必须选「影响人数 / 是否生产环境」，缺失则不让自动路由，先由值班员 30 秒人工定性。

**悬念**：规则补上了，分类模型却在周四晚上开始「漂移」——新上线的「AI 助手」功能带来大量新话术，准确率从 91% 掉到 84%。

---

### 第五章：模型说不准时，系统要学会「少做决定」

意图分类模型把「AI 助手回答错误」大量分到「通用产品咨询」，而真正该接的是「AI 功能组」——一个刚成立、只有 2 个人的新队列。结果新队列爆满，通用组却在聊「怎么关掉 AI」。

算法同学提议：「再训一版就好。」林舟问：「要多久？」「标注 2000 条，三周。」

赵敏等不了三周。林舟提出 **置信度分流**（和发票 OCR 那套一样）：

- **高置信**：自动路由到对应技能组；
- **中置信**：进入「待确认池」，由值班员 15 秒内点选正确队列（比从头手动派单快）；
- **低置信**：只自动打标签，不自动派单，进公共池并置顶高 SLA 风险客户；
- **多意图冲突**（如「登录 + 发票 + 退款」）：默认 **不拆单**，由一个「主责队列」接单，系统只推荐「可能相关的协作者」，避免子工单睡死。

同时上线 **路由可解释卡片**：客服领单前能看到——为什么分给你、命中哪些规则、模型置信度多少、相似历史工单 3 条。老周第一次没骂系统：「至少我知道你是猜的，我可以改。」

华鼎证书事故若再走一遍：

1. 客户等级 = 战略 → VIP 通道；
2. 影响 2,300 人 + 生产环境 → 硬规则 P0；
3. 意图「OAuth / 身份认证」高置信 → 身份组，但 P0 下 **能力优先**，直接命中老何（证书类历史 12 次）；
4. 若 3 分钟未接单 → 值班长升级，而不是在池子里继续等；
5. 「发票有误」作为 **关联标签** 挂在主工单，处理完 P0 后由系统生成 P2 续办，不抢主单路由。

**第三个产品二选一**：模型不准时，是「暂停自动派单」还是「降级为辅助推荐」？林舟选后者——完全退回人工，高峰期公共池会爆；全自动又会错分。辅助推荐 + 极短人工确认，是折中。

### 第六章：自动化率 72% 的周五，和一张算不清的账

一个月后，周五 17:03 再演一次大促式并发。大屏数据：

- 自动路由成功率 72%（其余为待确认或人工派单）；
- P0 平均接单 2 分 50 秒，达标率 96%；
- 华鼎同类工单 1 分 40 秒被老何接单，未再触发 CEO 群 @；
- 错分率（被接收人 5 分钟内转单）从 19% 降到 6%。

林舟在复盘会上被财务问：「上线智能派单，省了多少人？」

他摊开成本表：

| 项目 | 上月 | 本月 |
|---|---|---|
| 一线客服人力 | 38 人 | 38 人（未减编） |
| 平均首次响应时长 | 8 分 10 秒 | 3 分 40 秒 |
| SLA 违约罚款（合同） | ¥ 86,000 | ¥ 12,000 |
| 客户续约率（当季到期样本） | — | +4.2 pp |
| 意图模型推理 + 向量检索 | — | ¥ 4,600 |
| 路由规则维护（0.3 产品 + 0.5 工程） | — | 内部折合 ¥ 28,000 |
| 人工标注与 Bad Case 复盘 | — | ¥ 15,000 |

赵敏总结：「我们买的不是『少雇 5 个人』，是 **同样 38 人，少挨骂、少赔钱、少流失**。智能派单的 ROI，在 SLA 罚款和续约里，不在人头编制表。」

老周补了一句：「对我来讲，省的是 **找该找的人** 的 10 分钟，和 **被错分后背锅** 的憋屈。」

林舟写下结论：**智能工单分配与路由，不是分类比赛，而是「优先级 × 技能 × 负载 × 置信度」的编排系统；模型负责建议，规则负责底线，人工负责不确定。**

# 3. 系统正解

智能工单分配与路由系统的核心数据流是：**工单接入与字段补全 → 意图/情绪/实体识别（带置信度）→ 客户等级与 SLA 硬规则 → 队列准入与优先级排序 → 技能匹配 + 代理人排序 → 派单或升级 → 处理过程转单/协作者推荐 → 闭环反馈（转单、超时、满意度）→ 模型与规则迭代**。

- **第一章**对应工单接入与 SLA 监控——没有客户等级、影响面、值班表，路由就是盲人摸象。
- **第二章**对应规则路由与其局限——关键词快，但不懂组合语义与拆单风险。
- **第三章**对应技能标签与负载策略——要在「最闲」和「最会」之间按优先级切换权重。
- **第四章**对应 VIP、严重度与业务硬规则——模型不能推翻合同与客户层级。
- **第五章**对应置信度分流、可解释性与升级机制——不确定时少做决定，P0 超时必须升级而非等待。
- **第六章**对应运营指标与 ROI——价值在 SLA、体验和续约，而非简单的自动化率。

**AI 产品岗典型应用：**

- **写需求文档**：不只写「支持智能分类」，要列出工单类型、必填字段、队列清单、技能表结构、SLA 计时点、转单/升级/协作者三种路径的差异。
- **方案评审**：问清 P0 时负载均衡是否降权、试用客户能否占用紧急通道、低置信是进公共池还是待确认池、拆单条件是什么。
- **指标设计**：同时看首次响应时长、SLA 达标率、错分转单率、待确认池停留时长、自动路由覆盖率——不能只看分类准确率。
- **跨团队沟通**：与算法对齐置信度分段与标注回流；与客服确认值班表谁维护；与工程确认派单幂等（同一条工单不能派给两个人）、超时升级与消息通知。

# 4. 类比锚定

**类比：三甲医院门诊分诊台 + 专科号源调度。**

患者进门先分急诊与普诊（优先级），再根据症状分内科/外科/骨科（意图分类），同时看各科室当前候诊人数和专家是否在岗（负载与技能），危急值直接进抢救通道（升级）；分诊护士可以推翻机器预检，但要把原因记下来供后续改进。

| 医院分诊（旧经验） | 智能工单路由（新系统） | 映射关系 |
|---|---|---|
| 急诊 vs 普通门诊 | P0/P1 vs P2/P3 队列 | 决定「能不能插队」 |
| 主诉症状描述 | 工单标题、正文、附件日志 | 路由的主要语义输入 |
| 预检分诊台 | 意图分类 + 情绪/严重度模型 | 快速给出「建议去哪科」 |
| 科室与医生专长 | 技能标签 + 历史案例 | 决定「谁能处理」 |
| 候诊人数与专家号源 | 代理人当前待办 + 在线状态 | 负载均衡的输入 |
| 危急值直接进抢救 | VIP / P0 升级与值班长兜底 | 超时不能干等 |
| 护士改分诊并写备注 | 待确认池 + 可解释卡片 + 人工改派 | 人在环内，且留痕 |
| 病历随访与复诊预约 | 主工单 + 关联续办，而非随意拆单 | 避免子任务睡死 |

# 5. 类比边界与系统要点

## A. 系统核心要点总结

- **数据输入要求与格式规范**：除文本外，需客户等级、产品版本、影响面、环境类型、渠道来源；关键字段缺失时应阻断自动路由，而非用默认值硬派。
- **AI 模型能力边界与置信度**：意图分类擅长常见话术，对新功能、方言式描述、多意图混合易失效；必须输出置信度，并区分「分类错」与「优先级错」两类错误。
- **人工介入触发条件**：低置信、多意图冲突、战略客户 P0、模型未覆盖的新队列、客户情绪极端但影响面不明——应进待确认池或值班员定性，而非全自动。
- **容错与降级机制**：模型服务故障时回退规则路由；规则冲突时业务硬规则优先；派单失败要有重试与幂等；P0 超时必须自动升级，不能无限排队。
- **成本结构**：推理费用通常不高；真正贵的是 SLA 违约、错分导致的客户流失、标注与规则维护、值班协同流程改造；ROI 要算「体验 + 合同罚款」而不只是人力编制。
- **持续迭代**：新功能上线、话术变化会导致模型漂移；应用转单率、超时率、人工改派原因做每周复盘，而不是季度训一次模型就结束。

## B. 类比在哪里会失效

1. **医院分诊面对的生命危急相对可标准化，工单优先级却高度依赖 B 端合同与商业关系。** 同样「登录不了」，战略客户与试用版的处理权完全不同，类比无法覆盖商务策略。
2. **挂号后患者通常不换医生，工单却频繁转单、协作者并行。** 路由系统要支持动态转派、主责不变、子任务关联，而不是一次分诊定终身。
3. **医院候诊队列以「先到先服务」为主，智能路由要在 SLA、能力、负载之间动态加权**——这不是简单排队，而是多目标优化；过度追求均衡会牺牲 P0。
4. **分诊护士的判断相对稳定，AI 分类是概率输出。** 同一工单换模型版本、换提示词，路由结果可能变化；产品必须版本化并支持回放评估。
5. **类比掩盖了「拆单」产品决策。** 医院不会把「骨折 + 感冒」拆成两个独立无关联的就诊流程，但客服系统常 tempted 拆单；错误拆单比分类错误更隐蔽、更致命。

# 6. 深度业务洞察

1. **业务侧：客户要的是「有人快速接住我」，不是「系统看起来很智能」。** 销售常把「AI 智能派单」写进标书，客户真正验收的是首次响应时长、一次解决率、升级后多久有人管。立项时把「自动路由率」改成「P0 五分钟内正确接单率」，否则容易做偏。

2. **技术侧：意图分类准确率和路由正确率不是一回事。** 分类对了但派给没空的人、派给有技能但没经验的人，业务上仍算「错分」。评估要跟踪 **接收后 5 分钟内转单率** 和 **同类工单 SLA 达标率**，按队列、客户等级分层看。

3. **运营侧：技能表是活的，不是 HR 入职时填一次。** 新产品上线、组织调整、老员工转岗，若技能表不更新，比模型不准更常见。要有「谁有权改技能」「多久审计一次」「临时授权（如大促夜）如何自动过期」的运营机制。

4. **合规侧：情绪识别与优先级加权可能触及公平与歧视争议。** 试用客户因话术焦虑被插队、某类客户被模型系统性低估严重度，都会引发内部公平问题和客户投诉。硬规则需可审计，模型信号宜做加权而非一票否决，并保留人工覆写记录。

5. **商业侧：智能路由很难单独卖钱，常打包在客服套件里。** 对客户讲价值用 SLA 改善、人效提升、满意度；对内部讲成本要计入规则维护、标注、值班流程改造。若只算 GPU 推理费，会严重低估 TCO（总拥有成本），也高估利润率。

# 7. 学习资料参考

## 官方文档 / API 参考

1. **[Zendesk：智能路由与 SLA 策略（中英帮助中心）](https://support.zendesk.com/hc/en-us/articles/4408843597850-About-Zendesk-SLA-policies)**  
   **适合**：负责客服 SaaS 选型或写标书需求的 PM。  
   **解决什么**：理解 SLA 不是展示用 KPI，而是可配置的业务对象——计时点、违约、目标、优先级如何落到系统里。

2. **[Salesforce Service Cloud：Omni-Channel 路由概述](https://help.salesforce.com/s/articleView?id=service.omnichannel_intro.htm)**  
   **适合**：要做企业级客服路由方案对比的 PM。  
   **解决什么**：看成熟产品如何把技能、负载、优先级、渠道统一在一个路由引擎里，避免自己从零发明名词。

3. **[阿里云：智能客服对话分析 API 文档](https://help.aliyun.com/document_detail/175838.html)**  
   **适合**：需要和国内云厂商对接意图识别能力的 PM。  
   **解决什么**：了解对话分类、情绪、关键词等结构化输出长什么样，便于写接口字段与置信度需求。
