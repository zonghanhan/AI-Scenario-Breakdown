# 2. 业务场景故事

## 《产线停了，派单系统却把电工派去了隔壁换空调》

### 第一章：周三 14:20，华鼎三条产线同时红灯

工业设备维保 SaaS「迅修」的客户「华鼎制造」发来三张紧急工单，系统里都标着 **P0｜产线停机**：

1. **A 车间**：空压机异响后停机，影响包装线，约 120 人在等；
2. **B 车间**：中央空调主机高压报警，洁净车间温湿度超标，影响两条 SMT 线；
3. **C 仓库**：叉车充电桩接触不良，物流周转停滞。

华鼎园区很大——三个点位步行要 25 分钟，开车绕园区也要 12 分钟。客户成功经理在电话里吼：「不是派一个人来就行，是 **谁先恢复生产**！」

迅修的区域调度主管孙磊盯着地图：在岗工程师 5 人，其中 2 人在外勤返程路上，1 人正在隔壁「华鼎行政楼」做 **空调滤网更换（P3 例行保养）**。

刚接手 AI 产品线的程诺被拉进会议：「算法组说路径规划模型能把平均路程缩短 18%，今晚能不能自动派单？」

一线班长老马摇头：「18% 是路程。华鼎付的钱是 **停机损失**。你先把 **谁会修空压机** 和 **谁有洁净车间通行证** 搞清楚，再谈路线。」

**悬念**：程诺心想——派单不就是「谁最近派谁」吗？地图上明明老周就在华鼎行政楼隔壁。

---

### 第二章：「距离最近」上线，隔壁空调先被修好了

程诺第一版方案很直觉：**GPS 距离优先**。

系统逻辑：在「华鼎园区」围栏内，把未接单工单按坐标与工程师实时位置排序，最近的先派。

14:22，算法选中老周——他就在行政楼 200 米外，状态「作业中」。系统行为很「聪明」：

- 判定老周「已在园区内」，预计 8 分钟可转场；
- 把 **C 仓库充电桩（P0）** 派给老周，因为仓库离行政楼最近；
- A 车间空压机与 B 车间空调主机进入「待分配」，等老周「顺路」。

老周接单后懵了：「充电桩是低压电工活，我能做。但 **空压机是特种设备**，我没压力容器操作证，系统怎么把我派来的？」

孙磊手动改派：空压机给持证的张工，但张工在高新区，预计 47 分钟到达。B 车间空调主机没人接——因为系统把「中央空调」理解成「普通空调」，分给了行政楼做滤网的老周同组新人，新人没有 **洁净车间入场资质**。

15:10，华鼎 A 线仍停机。客户截图发到 CEO 群：**「你们派单系统是不是先保小单？」**

程诺在白板上写：**地理近 ≠ 业务近；工种近 ≠ 资质够；在园区内 ≠ 能立刻转场。** 老周那单 P3 空调滤网，若强行插单，行政楼物业会投诉；若做完再去仓库，A 线已经多停 40 分钟。

**悬念**：孙磊说：「别再加距离权重了。把 **技能、证照、工单类型** 设成硬门槛，过不了就别出现在候选人里。」

---

### 第三章：技能匹配加上了，时间窗口却把产线多等了半小时

第二版，程诺引入 **技能标签 + 证照校验**（和工单路由那套类似，但字段不同）：

- 工单类型：空压机、中央空调、低压配电、充电桩……
- 必需证照：压力容器操作证、洁净车间通行证、高压电工证、登高证……
- 硬规则：无证人员 **永不进入** 候选人池，不管距离多近。

同时接入 **客户预约时间窗**（客户说「希望 15:00–17:00 到场」）和 **SLA 截止时刻**（P0 必须 2 小时内首次到场）。

周三晚压测，错派率从 23% 降到 4%。程诺松口气。

周四同类场景再来：华鼎 B 车间空调主机高压报警（P0，洁净车间）。系统正确找到有资质的李工——**高压电工 + 洁净通行证 + 中央空调厂商认证**。完美匹配。

但李工当前在城东另一客户做 **计划性保养**，合同约定 16:00 前不能离场。系统算出的「最优」是：

- 李工 16:05 离场 → 驱车 38 分钟 → **16:43 到达**；
- SLA 要求 P0 **16:30 前首次到场**。

算法建议：「违约 13 分钟，仍在可接受范围。」孙磊暴怒：「洁净车间温湿度超标 13 分钟，可能废一整批料！**可接受** 是谁定义的？」

更隐蔽的翻车在同一张 **组合工单** 上：华鼎行政楼空调滤网（P3）与 C 仓库充电桩（P0）地址相近，系统把两单 **捆绑给老周「顺路做」**，时间窗显示 14:30–18:00「弹性」。结果老周按系统顺序先做完 P3 滤网——耗时 55 分钟（含等物业开门），再去仓库时已 15:40，充电桩 15 分钟修好，但 **A 车间空压机** 因张工路上堵车，16:20 才到场。

老马指着时间轴：「你的匹配管 **会不会修**，不管 **什么时候能到**；你的顺路管 **地理**，不管 **优先级**。」

**第二个产品二选一**：同一工程师手上已有低优先级工单，新的 P0 来了——是 **打断当前作业**、**转派同事**，还是 **让客户继续等**？孙磊拍板：**P0 可触发强制重排程（Re-schedule），并自动通知被影响的低优先级客户改期。**

**悬念**：程诺刚写好重排程规则，周五早上气象预警来了——台风外围，全市交通红色预警。

---

### 第四章：路径规划很炫，台风天里「最优路线」全堵死

第三版，程诺加上 **路径规划与排程优化**（VRP，车辆路径问题——一句话：在「谁去做、按什么顺序做、几点到」之间找综合最优）：

- 输入：工程师实时位置、可用时间窗、各工单服务时长估计、路况、园区内部门禁规则；
- 输出：每人当天的 **工单序列** + 预计到达/离开时刻 + 总行驶里程；
- 目标函数（业务给的权重）：**P0 SLA 违约分钟数** > **总行驶成本** > **工程师加班时长**。

周五 8:00，台风预警下积压工单 47 张，其中 P0/P1 共 12 张。系统跑完优化，大屏展示漂亮的路线图——平均里程下降 21%，看起来能省 3 辆外勤车。

8:40，现实开始打脸：

1. **服务时长估计错了**：系统默认「空压机故障排查 45 分钟」，张工到现场发现要拆主机查轴承，实际 2.5 小时——后面 3 张「顺路单」全部连锁延误；
2. **路况模型滞后**：高速封路信息 20 分钟前更新，系统仍把李工排进已封闭路段，绕行后 SLA 违约 35 分钟；
3. **园区规则没建模**：货车禁行时段，带大件备件的车进不了 B 车间，师傅人在门口干等 18 分钟，系统却算「已到场」；
4. **备件未齐**：充电桩工单派对了人、对了时间，但 **所需继电器型号** 在区域仓没货，师傅空跑一趟——系统里的「可执行工单」与仓储 WMS 没打通。

上午 10 点，孙磊收到 6 个客户投诉「约好了没人来」。复盘会上，算法同学说：「模型假设服务时长服从历史均值。」老马冷笑：「产线停了的时候，没有均值，只有 **最坏情况**。」

程诺提出和发票 OCR 同构的改造：**置信度 + 分层执行**。

- **高确定工单**（证照齐、备件齐、历史服务时长方差小、标准故障码）：全自动排程派单；
- **中确定**：系统出推荐序列，调度员 30 秒内确认或微调；
- **低确定**（无相似历史、需厂家远程支持、备件待确认、首次服务的设备型号）：只推荐「建议派谁」，**不自动锁时间窗**，由调度员电话客户重新约定；
- **P0 且多资源冲突**（两人都能修但都不够快）：触发 **升级面板**，展示「换人 / 加人 / 请客户产线局部切换」三选一，而不是悄悄违约。

**悬念**：中午 12:15，张工在高速上追尾，工单状态变成「执行中」——人回不来了，手里还有 4 张未完成的单。

---

### 第五章：师傅倒下了，系统不能只会「把单标红」

张工事故无大碍，但车辆维修需 4 小时。他手机 App 上还有 4 张工单：1 张 P0 进行中（配件已拆一半），3 张 P1 待执行。

旧系统行为：把张工标「离线」，4 张单全部扔回 **未分配池**——和工单路由里「子工单睡死」是同一类灾难。

程诺连夜补 **执行态迁移（State Handover）** 规则：

1. **进行中 P0**：优先派 **同技能 backup 工程师** 接力，系统推送「已拆至哪一步、现场照片、禁动部位」；原工单 **不关闭、不新建**，避免重复计费与客户困惑；
2. **未出发的 P1**：按新位置重新跑排程，但保留 **原客户已确认的时间窗**，若新方案违约 >15 分钟，自动发短信让客户选「改期 / 坚持原窗 / 升级」；
3. **备件与工具**：随车物料挂靠在 **工单** 而非 **人** 上，转派时库存跟着走，避免「人换了、料还在坏车上」；
4. **SLA 计时**：张工离场前的等待时间可计入「不可抗力」申诉池，但 **产线停机分钟数** 仍对客户透明——商务条款靠这个谈判，不是让算法偷偷抹掉。

下午 3 点，李工接力 P0，40 分钟恢复 B 车间空调。华鼎客户成功在群里发：「这次转派比上次顺畅。」

孙磊却问程诺：「全自动排程率多少？」

程诺报：「台风天 34%，平时大概 62%。」

孙磊点头：「合理。今天要是 90% 自动，投诉会更多。**天气、事故、备件、客户临时改窗**——这四件事永远存在，系统要学会 **少做绝对承诺**。」

**悬念**：月底成本会上，财务把外勤账单拍在桌上：里程下降了，但 **加班费爆了**。

---

### 第六章：里程省了 18%，加班费多了 32%

月末复盘，程诺展示成绩单：

| 指标 | 旧系统（距离优先） | 新系统（技能+排程） |
|---|---|---|
| 平均首次到场时长（P0） | 68 分钟 | 42 分钟 |
| 错派率（需二次转单） | 23% | 4% |
| 总行驶里程 | 基准 | **-18%** |
| 外勤加班费 | 基准 | **+32%** |
| 客户 SLA 达标率 | 71% | 89% |
| 调度员日均人工改派 | 86 次 | 28 次 |

财务总监皱眉：「里程省了油钱，加班费谁付？」

孙磊解释：「旧系统『省』的是 **假成本**——师傅空跑、错派、二次上门，油钱少但 **停机赔偿** 更多。新系统把 P0 压进 SLA，李工、张工这周各加了 6 小时班，是因为 **华鼎三张 P0 没违约**，合同里 **免赔** 条款生效，省下的是 **六位数潜在罚款**。」

程诺补充隐藏账：

- **路径规划 API** 与地图服务：¥ 1.2 万/月；
- **排程优化算力**（每日凌晨滚动重排）：¥ 0.8 万/月；
- **证照与技能主数据维护**（三方机构证书到期提醒）：内部人力折合 ¥ 1.5 万/月；
- **服务时长标注**（新机型冷启动）：本月临时加 ¥ 3 万标注预算；
- **客户改期短信与补偿券**：¥ 0.4 万/月。

「算法账单不到 2 万，**数据与运营** 才是大头——和翻译项目的术语库、工单路由的技能表是同一逻辑。」

周五晚，程诺在文档里写下结论：**工程类 AI 派单不是「地图 + 派单」，而是「资质硬约束 + 时间窗承诺 + 动态排程 + 执行态接力 + 备件可执行校验」的人机协作系统。** 地图只解决「怎么去」，不解决「该不该去、能不能修完」。

孙磊合上笔记本：「下次评审，别报『路径优化提升 18%』。报 **P0 平均停机缩短多少分钟、错派一次的成本是多少**——老板听得懂，客户也认。」

# 3. 系统正解

工程类 AI 派单系统的核心数据流是：**工单接入（故障码/设备档案/优先级/客户等级）→ 可执行性校验（证照、技能、备件、工具、客户时间窗）→ 候选人池生成（硬约束过滤）→ 排程优化（顺序 + 路线 + SLA 权重）→ 派单与通知 → 执行态跟踪（到场、开工、完工、拍照）→ 异常重排（堵车、事故、加时、客户改窗）→ 结算与 SLA 审计**。

- **第一章**对应工单接入与客户上下文——园区、产线影响面、P0 定义来自 B 端合同，不是算法猜的。
- **第二章**对应 **硬约束过滤器**——距离是软排序，证照与技能是硬门槛；「人在附近」不等于「人能接单」。
- **第三章**对应 **时间窗与 SLA 排程引擎**——匹配「会修的人」之后，还要算「何时能到、是否打断在手工单」。
- **第四章**对应 **VRP 路径优化 + 服务时长估计 + 外部数据（路况、门禁、仓储）**——优化目标必须是业务加权，不是纯里程最短。
- **第五章**对应 **执行态迁移与降级**——人、车、料、工单状态四位一体转派，避免回池睡死。
- **第六章**对应 **成本与 ROI 模型**——里程、人力、停机赔偿、标注与主数据维护要放在同一张表里看。

**AI 产品岗典型应用场景：**

1. **需求文档**：写清「派单」输入字段清单——除地址外，必须列 **设备类型、故障码、必需证照、备件 SKU、客户预约窗、是否允许打断当前工单**；缺失时系统是「阻断自动派单」还是「默认值硬派」，要写死。
2. **方案评审**：当算法说「平均里程降 18%」，追问 **P0 SLA 违约分布、错派转单率、服务时长估计误差**；三者任一恶化，里程优化可能负 ROI。
3. **指标设计**：核心指标不是「自动派单率」，而是 **首次到场达标率、一次修复率、每单平均行驶分钟、重排程客户满意率**；自动派单率按天气、客户等级分层看，避免晴天虚高。
4. **跨团队沟通**：对仓储说「备件未齐的工单不要进自动池」；对 HR/培训说「证照到期前 30 天自动降级技能标签」；对客户成功说「SLA 计时点以『可执行到场』为准，不是 GPS 进围栏」——避免商务承诺与系统计时不一致。

# 4. 类比锚定

**类比：外卖平台的「骑手调度 + 餐厅出餐」——但骑手还要带对「菜谱、厨具、健康证」，且迟到赔的是「整桌客人」而不只是一份饭。**

普通外卖派单也看距离、顺路、骑手负载；工程派单在此基础上多了 **强资质、长服务时长、可中断性、备件依赖**——更像「冷链骑手 + 安装师傅 + 急诊医生」的混合体。

| 外卖调度（旧经验） | 工程 AI 派单系统（新系统） | 映射关系 |
|---|---|---|
| 用户下单地址 | 工单服务地址 / 设备点位 | 决定「去哪」 |
| 骑手实时 GPS | 工程师 App 定位 + 作业状态 | 决定「从哪出发、是否可打断」 |
| 骑手类型（专送/众包） | 技能标签 + 证照（电工证、登高证、厂商认证） | 决定「谁有资格接」 |
| 预计出餐时间 | 服务时长估计（故障类型 + 历史工单） | 决定「排程靠不靠谱」 |
| 骑手手上未送达订单 | 工程师当前进行中工单与已锁时间窗 | 决定「能不能插 P0」 |
| 顺路多单合并 | VRP 路径优化与工单序列 | 降里程，但可能牺牲 P0 |
| 商家备餐好了才派单 | 备件齐套 + WMS 可执行校验 | 避免「人到料不到」空跑 |
| 超时赔付 | SLA 违约 / 停机赔偿 / 合同免赔条款 | 优化目标的真正权重 |
| 骑手事故/封号 | 执行态迁移、backup 接力、不可抗力申诉 | 异常不是「标红回池」 |

# 5. 类比边界与系统要点

## A. 系统核心要点总结

- **数据输入要求与格式规范**：除地址坐标外，需设备档案、故障码、工单优先级、客户等级、预约时间窗、必需证照与备件清单；关键字段缺失应 **阻断自动派单**，由调度员电话补全——默认值硬派会导致「派对了人但干不了活」。
- **AI 模型能力边界与置信度**：服务时长估计、路况预测、故障复杂度判断都是 **概率输出**；新机型、罕见故障码、客户描述含糊时，置信度低，应进「调度员确认」而非全自动排程。
- **人工介入触发条件**：P0 多资源冲突、备件缺货、证照临期、客户临时改窗、进行中工单强制打断、极端天气——应弹出 **重排程面板**，展示违约分钟与备选方案，而不是静默改约。
- **容错与降级机制**：地图/排程服务故障时回退「技能匹配 + 人工派单」；执行人突发离线必须支持 **工单级接力** 而非回池；SLA 计时与商务条款对齐，系统保留审计日志。
- **成本结构**：地图与优化 API 是小头；证照维护、服务时长标注、备件齐套、加班费、停机赔偿才是大头；ROI 用 **少一次错派、少一分钟停机** 算，不是用「少一公里」算。
- **持续迭代**：新设备型号、新园区门禁规则、季节路况都会让历史时长失效；用 **转单原因、加时率、客户改期率** 每周复盘，驱动标注与规则更新。

## B. 类比在哪里会失效

1. **外卖订单服务时长大多 30–45 分钟且可预测，工业维修从 20 分钟到数天跨度极大**——同一套「历史均值」排程在空压机大修上会系统性翻车。
2. **外卖骑手资质相对统一，工程派单是 **多工种 + 多证照 + 厂商认证** 的组合爆炸**——类比掩盖了硬约束过滤器的维护成本。
3. **外卖迟到赔一份餐，B 端产线停机赔的是 **整批物料、交付违约金、客户信任**——优化函数里「迟到」的权重要比 C 端外卖高几个数量级，不能照搬「多送几单」逻辑。
4. **外卖地址是门牌，工厂工单是 **园区内多点位 + 门禁时段 + 货车限行**——地理距离在园区内外完全不是同一套图。
5. **类比掩盖「进行中工单不可随意撤回」**：骑手可以拒单，师傅现场已拆机、已挂牌停电时，**转派是接力不是取消**——产品必须设计执行态迁移，而不是订单回滚。

# 6. 深度业务洞察

1. **业务侧：客户口头说「尽快」，合同写的是「2 小时首次响应、4 小时恢复运行」。** 销售演示常强调「智能路线规划」，客户验收盯的是 SLA 报表与停机分钟数。PM 立项要把「地图优化」写成 **达成 SLA 的手段**，而不是 KPI 本身；否则算法团队 optimize 里程，商务团队 still 赔罚款。

2. **技术侧：「派对了人」和「排对了序」是两次决策。** 先硬过滤资质，再在候选人里做 VRP——混在一起用一个模型端到端，可解释性和调试性都很差。线上出现错派时，要能回答「是技能表错了、时长估错了，还是路况旧了」——需要分模块埋点。

3. **运营侧：服务时长冷启动比意图分类更痛。** 新机型没有历史工单，模型只能猜；前 50 单几乎都要人工修正时长并回写标注。若运营预算没留 **「新设备上线派单护航周」**，系统会在新品旺季集体失效——和翻译项目的「新品类术语空窗」同构。

4. **合规侧：工程师证照与特种作业监管是法律问题，不是标签游戏。** 压力容器、高压电工、登高作业都有监管要求；系统若自动派给证照过期的人，出事故是 **产品 + 调度 + 公司** 连带责任。证照数据源要对接权威或 HR 主数据，过期 **自动下架技能**，不能仅靠师傅 App 自填。

5. **商业侧：工程派单常打包在 FSM（现场服务管理）套件里，单独卖「AI 排程」很难。** 对客户讲价值用停机缩短、人效、SLA 达标；对内部讲成本要含主数据治理、标注、调度员培训。只算地图 API 费用会严重低估 TCO，也高估毛利率。
