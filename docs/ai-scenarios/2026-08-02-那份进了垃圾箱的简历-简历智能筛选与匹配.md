# 2. 业务场景故事

## 《那份进了垃圾箱的简历，其实是我们要的人》

### 第一章：一个岗位，四十八小时涌进三千二百份简历

星澜科技要在两周内招一名 **高级后端工程师（AI 基础设施方向）**。HRBP 唐姐把 JD 挂到各大平台，周五下午 3 点发布，周日下午系统告警：已收到 **3,247 份投递**。

用人经理老周周一早会开门见山：「我只要 15 个人进技术面，周三之前给我名单。别跟我说人工一份份看——去年校招，两个实习生看了一周，眼睛都看花了。」

刚接手招聘 AI 产品的许扬翻着后台数据，发现现状比想象中乱：

- 同一岗位在 Boss、猎聘、内推邮箱三个渠道进来，**格式五花八门**：PDF、图片扫描件、在线结构化表单、甚至 Word 里嵌表格
- 老周在 JD 里写了「熟悉 Kubernetes、有 LLM 推理服务经验优先」，但投递里 **67% 的简历只写了「熟悉云原生」**，关键词对不上
- 内推通道有 38 份，按公司政策应 **优先进入人工池**，却被统一送进了自动筛选队列

唐姐压着火：「许扬，你们不是上半年就上线了智能筛选吗？为什么现在还是我在 Excel 里手动筛？」

许扬打开上季度的产品说明，发现系统定义的成功指标是「**自动过滤率 85%**」——听起来很美，但没人定义过「过滤掉之后，剩下的人能不能用」。

**悬念**：许扬决定先跑一轮全自动筛选，看看系统能给老周什么名单。

---

### 第二章：关键词筛得很爽，漏掉的人也更狠

周一上午 10 点，许扬触发批量任务：**JD 解析 → 简历结构化 → 匹配打分 → 按分数排序**。

JD 解析模块把岗位拆成：
- **硬性条件**：本科及以上、5 年以上后端经验、熟悉 Go 或 Java
- **优先项**：Kubernetes、Docker、LLM 推理/部署经验、高并发系统
- **加分项**：开源贡献、大厂背景、英语读写

简历结构化模块用 OCR + 文档解析（把 PDF/图片里的文字抽出来）+ NER（命名实体识别，从文本里抓出人名、公司、技能等字段），把三千多份简历压成统一 JSON。

匹配引擎第一版很「老实」——**关键词 + 规则**：
- 没写 Go/Java → 直接淘汰
- 没写「Kubernetes」但写了「k8s」→ 系统没认出来，扣分
- 工作年限从毕业年份推算，**空窗期超过 6 个月** → 标黄

中午结果出来：3,247 份 → **自动淘汰 2,891 份（89%）**，剩余 356 份按匹配分排序，Top 50 推给唐姐。

唐姐扫了一眼就打电话：「你们把 **赵行舟** 的简历淘汰了？老周的内推，昨天还亲口说『这人必须见』。」

许扬调出淘汰原因：
> 未命中关键词「Kubernetes」；工作年限计算为 4.8 年（差 0.2 年）；最近一份工作描述过短，置信度低。

他找来赵行舟的原件——人家写的是：
- 「**负责公司大模型推理平台的容器编排，日均调度 10w+ Pod**」
- 技术栈一行小字：「**Golang / gRPC / K8s / Triton / vLLM**」

问题一目了然：
1. **技能别名没进同义词库**：K8s ≠ Kubernetes
2. **年限规则太死板**：4.8 年被四舍五入还是截断，产品文档没写清
3. **内推优先级规则没生效**：标签在渠道层，筛选引擎在通用层，**管道断了**

老周在群里发了一句话：「如果赵行舟进不了 Top 15，这系统我不认。」

**第一个产品二选一**来了：是立刻加同义词、放宽年限、修内推通道？还是暂停自动淘汰，先全量进人工池？

许扬选了 **止血三件套**：同义词库热更新、内推简历强制进「人工必审」、自动淘汰改为「低分预警」而非「直接丢弃」。

**悬念**：修完规则，赵行舟进了 Top 5——但 Top 20 里出现了好几个「简历包装大师」。

---

### 第三章：语义匹配上线，简历造假也开始「懂向量」

周二，算法同学提议上 **语义匹配**（不只看关键词是否出现，而是理解两段文字意思是否相近）。许扬在评审会上问：「能解决 K8s 问题，还能解决什么？」

算法演示：把 JD 里的「LLM 推理服务经验」和简历里的「大模型在线 serving 优化」做向量相似度（把文字变成数字向量，算它们有多像），得分 0.87，高于纯关键词匹配的 0。

许扬批准灰度 20% 流量。

周三早上，唐姐又炸毛了：「Top 30 里怎么有三个 **技能栏塞满 47 个技术名词** 的人？点开项目经历，全是『参与』『了解』，没有一条能问细节。」

大模型时代的简历造假升级了——候选人用 AI 把 JD **反向翻译**成自己的技能清单：
- JD 写「熟悉 RAG」→ 简历写「精通 RAG 全链路」
- 实际只做过一次 Demo

语义匹配吃这套，因为 **字面意思确实像**。系统把「精通」和「熟悉」当成同一语义场，分数暴涨。

更麻烦的是 **假阳性**（不该推的推了）和 **假阴性**（该推的没推）同时存在：
- 一个做过三年 Java CRUD 的候选人，因为简历里堆砌了「微服务、分布式、高并发」，语义分进了 Top 15
- 一个 **转行** 候选人，上一份工作是制造业 IT，但业余维护过开源推理框架，**项目描述老实**，语义分只有 0.42

许扬和算法做误差分析，发现 61% 的「高分低能」简历命中同一模式：**技能区膨胀 + 项目区空洞**。

**第二个产品二选一**：继续调模型，让 AI 识别「水分」？还是加一层 **可解释的规则护栏**？

会上吵了四十分钟，最后方案很「PM」：
- **语义分不直接决定生死**，只作为排序加权项之一
- 加 **「项目可验证性」规则**：项目描述里必须有可追问要素（规模、指标、个人角色、技术决策），缺一项降权
- 加 **「技能-项目一致性」校验**：简历写了 vLLM，项目经历里至少要出现推理/serving/模型部署相关词，否则标为「技能堆砌嫌疑」
- 所有 **分数 0.7–0.85 的灰色地带**，不进自动推荐，进「HR 快速浏览队列」

**悬念**：护栏加上了，造假简历退潮——但合规部发来一封邮件，标题只有四个字：**「歧视风险」**。

---

### 第四章：筛人很快，审计很慢

合规专员老何把一份报告放在许扬桌上：「你们模型里是不是用了 **毕业院校、年龄、性别推断、照片颜值打分**？」

许扬一愣：「没有性别和颜值啊。」

老何点开特征清单：「**毕业院校 tier** 在排序特征里权重 0.12；**工作空窗期** 对女性候选人命中率显著更高；还有，你们 OCR 从身份证截图里 **误读了年龄**，三个 35+ 的候选人被『超龄规则』静默淘汰——这条规则产品文档里甚至没有。」

许扬后背发凉。他回去翻代码和配置，发现是三期迭代叠出来的：
1. 一期只有技能匹配
2. 二期 HR 提需求：「985/211 优先」——被实现成特征权重，而非「同等分数下人工备注」
3. 三期运维怕队列太长，加了「**35 岁以上降权**」的隐藏配置，来自某个业务方口头需求，**没有 PRD**

老何要求：
- 所有淘汰必须 **可追溯、可解释、可申诉**
- 敏感特征（性别、年龄、婚育、籍贯、照片）**不得进入排序模型**
- 每次筛选保留 **快照**：当时用的 JD 版本、模型版本、规则版本、候选人得分明细

许扬被迫喊停周四的自动出名单，花两天做 **合规改造**：
- 院校背景从「自动加权」改成「HR 面板可选筛选，默认关闭，且不影响基础匹配分」
- 删除一切年龄相关隐式规则
- 候选人端增加 **「申请状态说明」**：未通过时给出大类原因（技能不匹配 / 经验不足 / 岗位已关闭），不泄露具体特征权重
- 内推、转岗、回流员工 **强制人工复核**，算法只提供辅助摘要

唐姐吐槽：「怎么越改越慢了？」许扬回：「慢一天，比公司上热搜快一年。」

**悬念**：周五终于出了 15 人名单，老周面了 8 个，说「能用的只有 2 个」——问题又回到了匹配定义本身。

---

### 第五章：匹配不是找「最像 JD 的人」，是找「最能干活的人」

老周把面试记录甩在桌上：「你们要的是 **『JD 复读机』**，我要的是 **『能扛推理服务上线的人』**。」

他指了两份简历：

**A 候选人**，匹配分 0.91，面试一问「Triton 动态 batching 怎么调」，答成「用过，挺稳定的」。

**B 候选人**，匹配分 0.74，赵行舟内推名单外的另一个「低分选手」——简历里没堆关键词，但项目写得很具体：「把单机 QPS 从 800 拉到 4200，瓶颈在 GPU 内存碎片，方案是……」

老周说：「B 才是我要的。但你们系统把他排在第 47。」

许扬意识到 **产品目标函数** 从一开始就偏了：
- HR 要的是 **降低初筛工作量**
- 老周要的是 **提高面试命中率**
- 公司要的是 **录用质量 + 合规 + 候选人体验**

这三个指标不是一回事。「自动过滤 85%」只服务第一个。

他和唐姐、老周开了目标对齐会，重定义筛选系统的输出：

| 层级 | 输出 | 谁用 | 成功标准 |
|------|------|------|----------|
| L1 合规过滤 | 硬性不达标（学历、工作地点、签证） | 系统自动 | 误判率 < 0.5%，可申诉 |
| L2 匹配排序 | 技能/项目相似度 + 可验证性评分 | HR 快速浏览 | Top 50 里面试命中率 > 40% |
| L3 人工精选 | 15–20 人进技术面 | 用人经理 + HR | 终面通过率 > 25% |
| L4 反馈闭环 | 面试评价回写 | 算法迭代 | 每月复盘「高分低能」「低分高能」样本 |

赵行舟最终走了特批通道进面，B 候选人是老周从 **第 47 名的人工池** 里捞出来的——两人最后都发了 offer。

复盘会上，许扬写了结论：**简历智能筛选不是「自动 HR」，而是「把三千份压缩成值得花时间的五十份，且每一张被刷掉的牌都能翻回来」**。

# 3. 系统正解

简历智能筛选与匹配系统的核心数据流是：**多渠道简历接入 → 格式解析与结构化（OCR/文档解析/字段抽取）→ JD 解析与岗位画像 → 多路匹配打分（规则 + 关键词 + 语义相似度）→ 风险与合规护栏 → 分层输出（自动过滤 / 灰区人工 / 内推必审）→ 面试反馈回写与模型迭代**。

- **第一章**对应多渠道接入与任务编排——没有统一简历结构，后面所有「智能」都是空中楼阁。
- **第二章**对应 JD 解析 + 规则/关键词匹配——快、可解释，但别名、内推、年限边界必须产品化。
- **第三章**对应语义匹配与反作弊护栏——向量相似度解决「说法不同意思近」，但必须防止 JD 反向刷简历。
- **第四章**对应合规审计与可解释性——招聘场景下，特征工程和静默淘汰的代价远高于多筛几份简历。
- **第五章**对应目标函数对齐与人工精选层——系统交付的是「值得面试的短名单」，不是「最会写简历的人」。

**AI 产品岗典型应用**：
- **需求文档**：写清「硬性过滤 vs 排序加权 vs 人工必审」三层，别混成一个「匹配分」；内推、转岗、回流必须有独立通道。
- **方案评审**：问算法「灰色地带样本占比多少、假阳性/假阴性各靠什么兜底」；问法务「哪些特征绝对不能进模型」。
- **指标设计**：主指标用 **面试命中率**（Top N 里多少人进终面/录用），辅指标才是自动化率；单独监控「低分高能」申诉率。
- **跨团队沟通**：跟 HR 说「系统省的是初筛时间，不是替你做录用决策」；跟用人经理说「请用面试反馈帮系统认人，别只骂不准」。

# 4. 类比锚定

**类比：电商搜索排序——用户搜「轻薄羽绒服」，系统要从百万 SKU 里排出值得点开的列表。**

JD 就是搜索词，简历就是商品，匹配系统就是搜索排序引擎。规则过滤像「仅看有货、仅看自营」；关键词像标题匹配；语义匹配像「羽绒服」也能召回「薄款保暖外套」；人工精选就像运营把爆款推到首屏；面试反馈就像点击/成交数据回灌排序模型。

| 电商搜索排序（旧经验） | 简历筛选匹配（新系统） | 映射关系 |
|---|---|---|
| 用户搜索 query | JD / 岗位画像 | 定义「要找什么」 |
| 商品标题与属性 | 简历结构化字段（技能、经历、教育） | 被检索和比较的对象 |
| 标题关键词匹配 | 硬性条件 + 技能关键词规则 | 快、可解释，怕别名和漏召回 |
| 语义搜索 / 向量召回 | 简历-JD 语义相似度 | 解决「说法不同、意思相近」 |
| 刷单 / 标题堆砌 | 技能堆砌、JD 反向刷简历 | 需要反作弊与一致性校验 |
| 运营置顶 / 人工坑位 | 内推必审、猎头 RPO 通道 | 高优先级样本不能走通用排序 |
| 点击 / 成交 / 差评反馈 | 面试评价、录用结果、申诉样本 | 闭环数据，否则排序永远不准 |
| 搜索合规（广告法、违禁品） | 招聘合规（反歧视、可解释、审计） | 有些优化做了就是事故 |

# 5. 类比边界与系统要点

## A. 系统核心要点

- **数据输入要求**：简历来源多、格式杂，必须先做结构化（解析成功率、字段置信度、低质量扫描件分流人工 OCR 校对）。
- **AI 能力边界**：语义匹配懂「相似」，不懂「真假」和「能不能干活」；项目可验证性、技能-项目一致性要靠规则或二次模型补。
- **人工介入触发**：内推/转岗/回流、灰色分数段、低置信解析、合规敏感特征命中、候选人申诉——都应进人工池，而非静默淘汰。
- **容错与降级**：解析失败不淘汰，转人工；模型服务超时回退关键词排序；保留每次筛选快照支持翻案审计。
- **成本结构**：算力（OCR + 向量化 + 大模型摘要）< 人工复核时间 < **错杀好候选人 / 歧视诉讼 / 品牌伤害** 的隐性成本。

## B. 类比失效点

1. **电商漏展示一件羽绒服，用户划两下就划走了；简历被静默淘汰，候选人可能永远不知道你存在**——招聘的「漏召回」伤害的是公司口碑和人才池，不只是单次转化。
2. **商品标题堆砌可以平台处罚下架；简历包装是博弈**，候选人会持续针对你的匹配逻辑优化，模型迭代速度必须跟得上对抗。
3. **搜索排序可以 A/B 测点击率，招聘录用周期长、样本稀疏**，一个岗位可能只有个位数正样本，**数据飞轮转得比电商慢一个数量级**。
4. **电商排序很少涉及「年龄、性别、生育」等受法律保护的特征**；招聘系统里，特征选择本身就是产品决策，不是纯算法优化问题。
5. **类比掩盖「双向选择」**——候选人也在筛你；过度自动化、冷冰冰的拒绝体验，会让高意向人才直接拉黑雇主品牌。

# 6. 深度业务洞察

1. **业务侧：HR 说的「帮我筛掉不相关的」和用人经理说的「给我能面试的」，往往不是同一个需求。** 不先对齐目标函数，系统上线越快，内部信任塌得越快。

2. **技术侧：简历解析的瓶颈常常不是模型，是格式。** 扫描件、双栏排版、表格简历、一页纸塞三份工作经历——解析置信度低时，**宁可进人工，不要用低质量结构化结果去打分**。

3. **运营侧：没有面试反馈回写，筛选系统永远是开环。** 录用、拒录、面试评价、试用期表现，至少要回灌「低分高能」「高分低能」样本，否则语义模型只会越来越会识别「简历写法」而不是「真实能力」。

4. **合规侧：「985 优先」写在 HR 口头需求里，和写进排序特征里，法律风险完全不同。** 产品要把「可选筛选」和「隐式加权」彻底分开，且默认关闭敏感筛选。

5. **商业侧：ROI 别只算「省了多少 HR 小时」。** 一次错杀关键岗位候选人（竞品录用、内推关系受损、雇主品牌差评）的成本，可能覆盖三年的 SaaS 订阅费。高级岗位应默认 **低自动化率 + 高可解释性**。

# 7. 学习资料参考

### 官方文档 / API 参考

1. **[人社部等 — 招聘信息管理合规与就业促进相关指引（中文政策摘要）](http://www.mohrss.gov.cn/)**  
   **适合**：负责招聘类产品、需了解合规红线的 PM。  
   **解决什么**：建立「哪些信息不能作为筛选依据」的政策底线，避免产品特性踩雷。

2. **[LinkedIn Talent Solutions — 技能图谱与招聘匹配产品说明（英）](https://business.linkedin.com/talent-solutions)**  
   **适合**：做 B 端招聘 AI、需理解行业标准字段的 PM。  
   **解决什么**：了解技能标准化（Skill Graph）、岗位画像、候选人标签在工业界如何组织。

### 行业最佳实践

3. **[Greenhouse — Structured Hiring 结构化面试指南（英，含中文社区转载）](https://www.greenhouse.com/structured-hiring)**  
   **适合**：要和 HR、用人经理一起定义「什么叫匹配」的 PM。  
   **解决什么**：把「筛选」和「面试评价」串成闭环，理解为什么匹配分不能替代结构化面试。

4. **[美团技术团队 — 智能招聘相关技术分享（搜索「美团 简历 筛选」）](https://tech.meituan.com/)**  
   **适合**：想看国内大厂工程化落地的 PM。  
   **解决什么**：简历解析、多路召回、排序特征在真实高并发场景里的折中。

### 适合 PM 的科普

5. **[HBR — The Problem with Using AI to Hire（哈佛商业评论，英）](https://hbr.org/)**  
   **适合**：要向管理层解释「为什么不能全自动」的 PM。  
   **解决什么**：用商业案例说明算法招聘的偏见、误判与组织信任成本。

6. **播客：《组织人事合辑》或《HR 科技圈》中关于 ATS / 智能筛选的访谈（中文）**  
   **适合**：想听一线 HR 真实吐槽的产品经理。  
   **解决什么**：理解 HR 工作流里，系统卡在哪个环节最招人恨。

### 动手小练习（30 分钟）

7. **练习：手工当一次「匹配引擎」**  
   找一份真实 JD（可脱敏），再准备 5 份简历（3 份真实风格 + 2 份故意堆砌关键词的「水分简历」）。  
   - 用 10 分钟分别打「规则分」「语义相似分」「项目可验证分」  
   - 写下你会自动淘汰谁、谁进灰区、谁必须人工看  
   - 对比：如果只允许看 30 秒/份，你的决策和「全读 5 分钟」差在哪  
   **适合**：所有转行 PM。  
   **解决什么**：亲手体验「目标函数不一致」和「简历对抗」是什么感觉，比看架构图直观十倍。
