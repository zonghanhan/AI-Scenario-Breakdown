# 2. 业务场景故事

## 《那场两小时的评审，五分钟出来的纪要改了一下午》

### 第一章：散会五分钟后，纪要已经躺在群里了

周二下午 3 点，SaaS 公司「云栈」的产品评审会结束。议题只有一个：新版「客户健康度」仪表盘能不能在 8 月 15 日上线。

参会 9 人：产品负责人林薇、刚转岗的 AI 产品经理程诺、后端老周、前端小唐、数据分析师阿杰、客户成功主管魏琳，还有两位销售代表和一位财务旁听。会议开了 127 分钟，中间穿插了三次屏幕共享、两轮「你刚才说的那个接口」的追问，以及最后 15 分钟老板远程接入说了几句方向性意见。

散会后 3 点 05 分，程诺在飞书群里收到一条系统通知：

> **AI 会议纪要已生成**  
> 核心结论 5 条 · 待办 8 条 · 风险 3 条 · 点击确认后同步至项目看板

林薇扫了一眼，脸色还行：「比人工整理快多了。程诺，你负责核对，下午五点前定稿。」

程诺点开纪要，第一眼很惊艳——章节标题清楚，「背景」「争议点」「决议」「待办」都齐了。第二眼开始不对劲：

- 待办第三条写着：**老周负责在下周一把缓存方案改成 Redis Cluster**；
- 待办第五条写着：**魏琳确认客户侧数据口径，本周内完成**；
- 争议记录里有一句：**「财务不同意这个预算」**——但财务同事全程只说了「我这边没有异议，听你们」。

老周在群里回了一句：「我会上说的是**先评估**，没答应下周一改。Redis Cluster 是阿杰提的备选，我没接话。」

魏琳私信程诺：「数据口径我早就发过文档了，会上说的是**销售要不要新增字段**，别给我凭空加活。」

**悬念**：五分钟生成的纪要，看起来比人写的还工整——为什么参会者第一反应是「这不是我说的」？

---

### 第二章：机器听见的，和「会议里发生的事」不是同一件事

程诺去查后台流水线。原来云栈三个月前采购了企业版「智能会议助手」，流程是：

1. **会议录音接入**：飞书视频会议结束，自动拉取音频（可选开摄像头录像，但纪要链路主要吃音频）；
2. **语音转写（ASR，Automatic Speech Recognition）**：把声音变成带时间戳的文字；
3. **说话人分离（Speaker Diarization）**：区分「谁在说」，默认用入会姓名，但多人同会议室、有人没开麦、有人手机接入时，标签会漂；
4. **摘要与结构化抽取**：大模型读全文，生成纪要、待办、风险项。

问题出在链条的每一环都有「静默丢信息」：

**ASR 层**：老周口音重，「评估」被听成「改成」；财务同事声音小，模型把阿杰的「预算够」和后面销售的叹气拼成了一句「财务不同意」。

**说话人层**：会议室只有两个麦克风，销售代表 A 和 B 经常被标成同一个人；老板远程接入的最后一段，被标成「林薇」——因为林薇在复述老板的话。

**抽取层**：模型有强烈的「行动导向」偏好——听到「Redis Cluster」和「下周一」出现在相邻句子里，就合成了一条待办，**不管中间有没有「可能」「再看看」**。

程诺在复盘里写了一句：**语音转写不是「录音变文字」，是「有损压缩」；纪要生成不是「文字变摘要」，是「二次推断」。** 两步推断叠在一起，工整的输出反而更危险——人看到排版好的 bullet，会默认它比原始录音更可信。

林薇问：「那还用它干嘛？」

程诺：「用它做**初稿和索引**，别用它做**事实公证**。」

**悬念**：如果纪要不能当事实，待办还能自动进看板吗？

---

### 第三章：八条待办进看板，三条没人认领

下午 4 点，程诺按流程把 AI 纪要送进「确认台」——这是采购时林薇坚持要的功能，不是直接同步 Jira。

确认台左边是 **录音时间轴**：点击任意一句转写，跳到对应音频；右边是 **结构化字段**：结论、待办（负责人 / 截止时间 / 优先级 / 原文依据句）、风险。

程诺逐条处理 8 条待办：

| AI 待办 | 处理结果 |
|---|---|
| 老周下周一改 Redis Cluster | **驳回**——依据句是阿杰提议，老周未承诺 |
| 魏琳本周确认数据口径 | **驳回**——议题已关闭，文档 7 月已发 |
| 小唐 8 月 10 日前完成前端联调 | **修改**——正确截止日是 8 月 12 日，会上老板口头改过 |
| 程诺输出 PRD 修订版 | **确认**——但负责人应是林薇指派程诺，不是模型猜的 |
| 销售补充 3 个客户案例 | **拆分**——实际两人各 1 个案例，模型合并了 |
| … | … |

最终 **8 条里确认 4 条、修改 2 条、驳回 2 条**。从散会到定稿，程诺花了 78 分钟——比「五分钟出纪要」长，但比纯人工听录音写纪要（魏琳说通常 2–3 小时）还是省了一半。

更重要的是：**被驳回的待办不会进看板**。若下午直接一键发布，老周和魏琳今晚就会收到错误工单。

阿杰补充了一个技术细节：系统在抽取待办时，会输出 **置信度** 和 **原文时间戳**。但采购版本的默认 UI 把置信度藏在「高级设置」里，程诺之前根本不知道有这列数据。

林薇当场拍板：「以后待办默认展示依据句和置信度；低于 0.75 的条目必须人工点确认，不许批量通过。」

**悬念**：纪要定稿了，下周复盘时怎么证明「会上真的这么定的」？

---

### 第四章：老板问「会上谁反对的」，系统差点背锅

周三上午，项目延期风险升高。老板问林薇：「周一会上财务是不是反对预算？我看纪要里写过。」

林薇后背一凉——她昨天定稿版已经删了那句，但 **AI 初稿被自动存进了会议知识库**，销售副总昨晚检索「客户健康度 预算」，第一条结果就是未修订版纪要片段。

这就是程诺在需求文档里漏写的一块：**纪要版本管理 + 权限**。会议助手默认行为是：

- 初稿、修订稿、定稿 **共用同一个会议 ID**；
- 知识库检索 **不区分版本状态**；
- 旁听人员（财务）的发言 **与内部分享权限相同**。

下午紧急补丁：

1. 只有标记为 **「已定稿」** 的纪要进入可检索知识库；
2. 初稿仅参会人可见，且带水印「待确认，非最终决议」；
3. 财务旁听类会议，默认 **不** 把纪要同步到全公司搜索索引。

魏琳借此提了另一个需求：客户成功周会常讨论具体客户名，**ASR 转写里客户名错误率极高**（「恒生科技」→「恒生科机」），纪要若直接入库，等于把脏数据写进 CRM 的上游。

程诺在方案里加了 **实体校验层**：客户名、金额、日期抽出来后，跟主数据做模糊匹配；匹配失败则标黄，不进入自动同步。

老板风波平息了。程诺意识到：**会议纪要系统的用户不只是参会者，还有一周后、一个月后「拿纪要当证据」的人。** 产品设计要按「审计视角」做，不能只按「省秘书时间」做。

---

### 第五章：成本账——省下的秘书时间，和花掉的核对时间

月底，林薇让程诺汇报 AI 会议助手的 ROI。云栈上月开了 186 场会，其中 62 场勾选了「自动生成纪要」。

| 成本项 | 金额 / 工时 |
|---|---|
| 企业版会议助手 License | ¥ 28,000 / 月 |
| 语音转写 + 大模型摘要 API 超量 | ¥ 6,400 |
| 程诺等 3 人核对纪要（估） | 约 45 人时 |
| 因错误待办产生的扯皮会议（估） | 2 场 × 1 小时 |

节省侧：

- 以前每场评审会人工纪要约 1.5–2 人时，62 场若全人工约 **93–124 人时**；
- 核对后净节省约 **48–79 人时**，折合内部成本 ¥ 15,000–25,000（按混合时薪粗算）。

林薇结论：「ROI 是正的吗？算是。但 **不是买了就省**，是 **买了以后多了一道核对工序**。」

程诺补充三条产品判断：

1. **自动化率别按「生成纪要场次」算**，要按「零修改定稿场次」算——上月只有 11 场；
2. **最大价值不是省秘书**，是 **待办进看板 + 时间轴索引**——新人复盘、争议举证时，跳录音比翻聊天记录快；
3. **最长会议不一定最划算**——127 分钟那场转写 + 摘要 API 费用是 30 分钟站会的 4 倍，但信息密度未必 4 倍。

苏棠式收尾（林薇原话）：「下次买工具，别演示『五分钟出纪要』，演示『错误待办被拦下』的那一刻——那才是值回票价。」

# 3. 系统正解

会议纪要自动生成与待办提取系统的核心数据流是：**会议音频/视频接入 → 语音转写（ASR）→ 说话人分离与标注 → 文本清洗（去口语、分段、议题切分）→ 摘要生成 + 结构化抽取（结论 / 待办 / 风险 / 决策）→ 实体校验与主数据对齐 → 人工确认台 → 定稿版本入库 → 待办同步至项目系统（Jira / 飞书任务等）**。

- **第一章**对应摘要与待办抽取模块的「成品展示」——输出快，但不等于事实正确。
- **第二章**对应 ASR + 说话人分离 + 抽取三层——每一层都可能引入推断，工整排版会放大信任感。
- **第三章**对应人工确认台与待办状态机——驳回 / 修改 / 确认分流，防止错误待办污染看板。
- **第四章**对应版本管理、权限与知识库检索策略——纪要是为「未来举证」服务的，不是即时聊天替代品。
- **第五章**对应成本模型——按会议时长计费 + 人工核对工时，决定真实 ROI。

**AI 产品岗典型应用：**

- **需求文档**：写明「待办字段」必须含负责人、截止时间、优先级、**原文依据句 + 时间戳 + 置信度**；定稿前禁止写入可检索知识库。
- **方案评审**：争论「要不要一键同步看板」时，用状态机图说明「初稿 → 核对中 → 已定稿 → 已同步」四段，避免销售副总搜到未修订片段。
- **指标设计**：核心指标用「待办准确率」「零修改定稿率」「核对耗时/场」；别只报「纪要生成覆盖率」。
- **跨团队沟通**：跟算法说「说话人分离在混合会议室误标率」；跟工程说「幂等同步 Jira、版本水印」；跟法务说「录音留存期限与旁听人员权限」。

# 4. 类比锚定

**类比：电视台新闻编辑室——记者外采录音 → 速记员听打 → 编辑编稿 → 制片人审片 → 播出稿归档。**

观众看到的是 30 秒新闻，背后是「原始素材 ≠ 播出稿」；AI 会议纪要就是跳过了专职速记员，但 **制片人核对** 和 **归档版本** 不能省。

| 新闻编辑室（旧经验） | 会议纪要系统（新系统） | 映射关系 |
|---|---|---|
| 外采原始录音 / 同期声 | 会议音视频录制 | 唯一可追溯的「事实源」 |
| 速记员听打稿 | ASR 语音转写 | 声音→文字，有错字、有漏句 |
| 记者姓名与出镜语音 | 说话人分离与身份标注 | 多人场景下标签会漂 |
| 编辑提炼导语与正文 | 大模型摘要生成 | 压缩信息，可能合并、误读 |
| 编审单上的「待核实」标记 | 低置信度待办 + 依据句高亮 | 不确定的不能当定论播出 |
| 制片人签字定稿 | 人工确认台「定稿」状态 | 只有定稿进档案库 |
| 播出稿 vs 粗剪版 | 定稿纪要 vs AI 初稿 | 检索系统只能索引定稿 |
| 同期声字幕上屏 | 时间轴跳转播放 | 争议时回听 10 秒比看文字快 |

# 5. 类比边界与系统要点

## A. 系统核心要点

- **数据输入要求**：音频采样率、降噪、是否多人同麦；视频会议需约定「重要决议口头复读一遍」；客户名、金额等建议屏幕共享或会前议程结构化输入。
- **AI 能力边界**：ASR 对口音、专业术语、中英夹杂敏感；摘要模型会「补全逻辑」制造从未达成的待办；说话人在远程 + 线下混合场景误标率高。
- **人工介入触发**：待办置信度低于阈值、负责人无法匹配组织架构、截止时间为相对表述（「下周」「这周内」）、涉及预算/合规/客户名的条目——默认进核对队列。
- **容错与降级**：ASR 失败时保留录音 + 议程模板手动纪要；摘要超时则只出转写全文；看板同步失败时不得标记为已定稿。
- **成本结构**：License + 按音频时长计费；长会、多场次叠加；**核对人力**常被忽略；错误待办引发的返工会议是隐性成本。

## B. 类比失效点

1. **新闻稿有「播出即定论」的时点，会议决议常是渐进形成的**——会上口头说的和最后邮件确认的可能不一致，系统只能锚定「某一刻录音」，不能替代正式决议邮件。
2. **电视台粗剪版不会进搜索引擎，但 AI 工具常默认「生成即可搜」**——权限与版本策略是产品必选项，类比里制片人环节被低估了。
3. **新闻编辑对「捏造事实」有职业红线，大模型摘要没有**——它会用流畅的 bullet 填补断句，制造「从未被承诺的待办」；这是概率性输出，需置信度与依据句对冲。
4. **类比掩盖实时场景**：销售客服质检（系列 1/4）可做实时提示，会议纪要多数是 **会后批处理**——产品节奏、超时策略、用户预期完全不同。
5. **电视新闻不自动给记者派 Jira 工单**——待办同步涉及组织树、项目空间、任务类型映射；一键同步是工程深坑，不是「多接一个 API」。

# 6. 深度业务洞察

### 洞察 1：用户要的是「会后省事」，真正痛点是「会前没对齐、会后扯皮没证据」

采购演示永远展示「五分钟出纪要」；上线后投诉最多的是「待办不是我说的」和「会上没定的事怎么进看板」。**表面需求**是自动写纪要；**真实需求**是争议时可回听、待办可追责、定稿可检索。PM 应优先做时间轴 + 版本 + 权限，再优化摘要文采。

### 洞察 2：「待办抽取」比「摘要」难一个数量级，别用一个模型打天下

摘要允许概括；待办是 **结构化承诺检测**——谁、做什么、何时、什么条件。工程上常见拆分：转写全文 → 议题分段 → 每段抽候选行动项 → 规则过滤（「可以考虑」不算承诺）→ 组织树匹配负责人。一个端到端 Prompt 在 demo 里够用，在生产里待办误报率会逼你拆 pipeline。

### 洞察 3：说话人分离是隐形天花板，混合会议室场景要单独验收

采购 POC 常在耳机清晰的远程会里做；真实企业大量「3 人在会议室 + 5 人远程」。误标会导致「张总说的变成李总待办」。产品要在验收清单里写：**混合会议误标率**，不是实验室字准率。

### 洞察 4：冷启动没有「会议域术语库」，专业团队第一周都会骂 ASR

「客户健康度」「NDR」「回款周期」在通用 ASR 里全是鬼画符。需要 **热词表 / 自定义语言模型**——会从议程、项目 Wiki 自动拉术语。跟客服质检一样，**会前 24 小时导入议程**应成为标准流程，不是可选项。

### 洞察 5：合规与留存——录音比纪要更敏感

纪要定稿可以脱敏；原始录音含客户名、薪酬、未公开战略。法务关心：存多久、谁可下载、离职人员权限、跨境会议数据驻留。PM 若只谈「AI 多聪明」，法务会一票否决；**留存策略和旁听权限**应和 MVP 同期设计。

# 7. 学习资料参考

### 官方文档 / API 参考

1. **[微软 Azure：Conversation Transcription 与说话人分离](https://learn.microsoft.com/zh-cn/azure/ai-services/speech-service/conversation-transcription)**  
   **适合**：要跟算法/工程评技术方案的 PM。  
   **解决什么**：理解 ASR 在多人会议里的能力边界，以及「转写」和「分离」是不同模块。

2. **[飞书开放平台：视频会议录制与纪要相关能力（国内团队常用）](https://open.feish.com/document/server-docs/vc-v1/meeting/meeting-list)**  
   **适合**：负责国内协作套件集成的 PM。  
   **解决什么**：会议结束后的数据拉取时机、权限范围、回调事件——集成 PRD 的直接参考。

3. **[OpenAI API：Audio 转写与长文本处理指南](https://platform.openai.com/docs/guides/speech-to-text)**  
   **适合**：评估云端 vs 私有化部署的 PM。  
   **解决什么**：按音频时长计费、文件大小限制、长会议分段策略。

### 行业最佳实践

4. **[Google Cloud Blog：Best practices for speech-to-text in meetings（中英检索可找到镜像）](https://cloud.google.com/blog/products/ai-machine-learning/bringing-speech-to-text-to-meetings)**  
   **适合**：写验收标准的产品 PM。  
   **解决什么**：麦克风布置、降噪、热词配置对转写质量的影响——可写进实施手册而非甩锅「模型不行」。

5. **[Atlassian 工程博客：Jira 与自动化集成中的「人类确认」模式](https://www.atlassian.com/blog/announcements)**（检索 "human in the loop" 相关实践）  
   **适合**：设计「待办同步看板」流程的 PM。  
   **解决什么**：自动创建工单 vs 建议工单——后者才是会议纪要场景的常态。

### 适合 PM 的科普

6. **[少数派 / 各协作平台测评：「AI 会议纪要」横评文章（持续关注更新）](https://sspai.com/)**  
   **适合**：刚接手选型任务的 PM。  
   **解决什么**：建立「演示效果 ≠ 日常效果」的预期，重点看核对台、版本、权限而非摘要文采。

### 动手小练习（约 30 分钟）

7. **练习：用任意免费转写工具处理一段 10 分钟会议录音（可自录两人对话），手工列出「真实待办」与「工具摘要里的待办」，对比差异并标注三类错误：ASR 错字、说话人误标、模型臆造。**  
   **适合**：没做过会议纪要产品的 PM。  
   **解决什么**：亲手获得「待办误报」体感，写 PRD 时知道为什么要「依据句 + 时间戳 + 驳回按钮」。
