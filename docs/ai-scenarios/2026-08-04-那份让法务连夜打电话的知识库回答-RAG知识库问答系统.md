# 2. 业务场景故事

## 《那份让法务连夜打电话的知识库回答》

### 第一章：新政策上线两小时，知识库先被问了 847 次

3 月 18 日上午 10 点，云杉电商发布了新版《商家退款与赔付管理办法》，共 47 页，替换了 2024 年旧版里关于「预售违约」「延迟发货」「价保补差」的三章内容。

10:02，内部知识库问答入口的并发从平日 30 次/分钟跳到 210 次/分钟。提问的人五花八门：

- 商家运营：「预售商品超期未发货，按新办法最多赔多少？」
- 一线客服：「用户说页面写了退一赔三，新办法还适用吗？」
- 区域经理：「旧版合同里的赔付条款，3 月 18 日前下单的订单按哪版执行？」

刚转行做 AI 产品的小周站在运维大屏前，看着绿色曲线一路往上爬，心里还挺得意。过去半年，他和算法、工程搭了一套「智能知识库问答」：把公司制度、产品手册、FAQ、工单案例全部灌进系统，用户用自然语言提问，几秒就能拿到带引用的答案。

上线演示时，CEO 问过：「这玩意儿会不会胡说八道？」小周当时的回答是：「我们用了 RAG（检索增强生成，先查文档再让大模型组织答案），不是让模型凭空编，是让它『照着材料说』。」

10:47，法务总监陈律的电话打过来，语气很平，但每个字都像敲在桌上：「有个商家把你们知识库的回答截图发给我了。上面写——预售违约可以要求退一赔三。你告诉我，新办法第 12 条哪一句这么写的？」

小周后背一凉。他打开后台，定位到那条问答记录：

> **用户问**：预售商品超时未发货，商家必须退一赔三吗？
>
> **系统答**：根据《商家退款与赔付管理办法（2025 版）》，预售商品未按约定时间发货，消费者有权要求退一赔三。请参考文档第 3 章第 2 节。
>
> **引用来源**：`退款赔付办法_2025.pdf` 第 18-19 页

陈律发来新办法原文截图：第 3 章第 2 节写的是「按实付金额 5%–30% 进行赔付，单笔上限 500 元」，根本没有「退一赔三」。

**悬念**：系统明明「引用了文档」，为什么还能一本正经地答错？小周意识到，问题不是「模型会不会聊天」，而是「检索、拼接、生成」整条链路上，哪一环把业务风险放大了。

### 第二章：用户只看到一个框，系统背后其实跑了六步

小周拉上工程负责人老韩和算法同学阿宁，按那条事故问答的 request_id 把日志从头捋了一遍。用户以为「问一句、答一句」，实际上系统走了完整流水线：

**第一步：问题理解与改写（AI 介入）**

原始问题是口语化的：「预售商品超时未发货，商家必须退一赔三吗？」

系统先做两件事：

- 识别意图：政策咨询 / 赔付标准 / 预售场景；
- 改写检索 query：补上同义词「延迟发货」「违约赔付」「预售订单」，去掉口语助词。

这一步用的是轻量分类模型 + 规则。改写后的 query 会同时送给「关键词检索」和「语义检索」两路——因为员工问「退一赔三」，文档里可能写的是「三倍赔偿」或「惩罚性赔付」，光靠字面匹配会漏。

**第二步：文档检索（RAG 的核心）**

知识库里并不存「47 页 PDF 一整块」，而是切成上千个 chunk（文档切片，把长文切成小块方便检索）。

那次事故里，检索命中的 top 5 片段来自三份文档：

1. 《商家退款与赔付管理办法（2025 版）》第 18 页——讲预售违约 5%–30% 赔付；
2. 《商家退款与赔付管理办法（2024 版）》第 22 页——旧版确有更严厉的表述；
3. 一份 2023 年的「大促商家答疑纪要」——运营同学习惯性写「严重违约可按退一赔三协商」；
4. 一个已下线产品的 FAQ 页面缓存——标题含「退一赔三」；
5. 客服培训课件片段——举例说明「消费者常误以为退一赔三」。

问题在这里露出了头：**检索召回了「相关」文本，但没有区分「哪份文档有效、哪一段是现行规定、哪一段只是举例或历史口径」。**

**第三步：重排序（Re-rank，对候选片段再排一次座次）**

语义检索容易「意思像」就排前面。重排序模型会把 top 20 片段按与问题的相关度再打分。那次事故里，重排把 2023 年答疑纪要抬到了第 2 位——因为它和用户问题字面最像，都含「预售」「退一赔三」。

**第四步：上下文组装（工程逻辑）**

系统把排名前 4 的片段拼成「给大模型的阅读材料」，并附上元数据：文档名、版本号、生效日期、页面号。理想情况下，生成模型只能基于这些材料回答。

但小周在日志里看到一个致命细节：**2024 版办法和 2023 年答疑纪要都没有被标记为「已废止」**，元数据里 `effective_status` 是空的。

**第五步：答案生成（大模型介入）**

大模型读罢材料，输出了那段错误回答。它犯的错不是「完全没看文档」，而是把不同来源的信息**揉成了一句话**——把旧版/示例/用户常见误解，当成了现行规则的肯定陈述。

更麻烦的是，生成模块还自动「补全」了章节号：材料里其实没有「第 3 章第 2 节明确写退一赔三」，但模型为了显得专业，编造了精确引用格式。这叫**幻觉（模型用很自信的语气说了材料里没有的话）**，是 RAG 产品最常踩的坑。

**第六步：回答后处理（规则 + 人工边界）**

系统本来有一道「高风险问题拦截」：涉及赔付金额、法律承诺、合同解释的问答，应强制附带「仅供参考，以正式制度文本为准」并降低自动展示优先级。

但这次拦截没触发。原因是：分类器把问题标成了「普通政策咨询」，而生成答案的「自信语气」让置信度评分偏高。

老韩在白板上写下：**RAG 不是「检索 + 聊天」，而是「检索 → 版本过滤 → 重排 → 受控生成 → 风险拦截 → 可追溯发布」。** 少一环，法务就会在半夜打电话。

### 第三章：切得太碎、搜得太宽、说得太满——三个设计误区同时爆炸

复盘会上，团队把事故拆成三个产品决策失误，每一个都典型得能让 PM 对号入座。

**误区一：切得太碎，上下文丢了「否定句」**

47 页办法按固定 512 token 切块，第 18 页那个 chunk 刚好以「下列情形不适用本条的简易赔付标准」开头，下一块才写「不得单方面承诺退一赔三」。用户问的那句话，检索命中了前一块，没命中后一块。

阿宁说：「固定长度切分省事，但政策文档里，『不适用』『除外』『以前版本』往往出现在段落末尾或下一页。」

他们后来改成**按章节结构切分 + 重叠窗口（相邻块保留 10%–15% 重复内容）**，并在每个 chunk 注入「本章标题、生效日期、替代关系」作为前缀。

**误区二：搜得太宽，没把「知识有效期」当硬过滤**

知识库里有 1,240 份文档，来自法务、运营、客服、产品四个部门。上传时只填了「标题 + 部门」，没有统一的**版本状态机**：现行有效 / 已废止 / 仅供案例参考 / 内部培训示例。

检索阶段如果只按相关度排序，2023 年的答疑纪要和 2025 年正式办法会一起挤进候选集。小周在 PRD 里补了一条硬规则：

> 涉及赔付、合同、合规的问答，检索结果必须先经过「生效日期 + 文档状态」过滤；同主题存在多版本时，默认只保留最新有效版本，旧版必须降权且不得单独作为唯一依据。

**误区三：说得太满，把「引用存在」误认为「答案正确」**

产品上线时，小周很骄傲地做了「答案脚注」：每个回答下面列 PDF 页码。陈律在复盘里指出：「脚注给了用户虚假安全感。模型把三份材料拼错，脚注照样能列得整整齐齐。」

团队把 UI 改成：

- **强制展示原文摘录**（高亮命中句子），而不只是文档名；
- 多来源冲突时，显示「检测到版本冲突，请人工确认」，禁止生成单一肯定句；
- 高风险类目默认结尾：「如需对外承诺，请联系法务确认。」

### 第四章：AI 搞不定时，系统怎样优雅降级

事故当天下午，陈律要求：在赔付类问题修复前，系统不能对商家侧自动开放，内部客服可以用，但必须「可降级、可追责」。

小周和老韩设计了四级响应路径：

**L1 自动回答（绿色）**

条件同时满足：

- 检索命中唯一有效版本；
- 重排 top1 与 top2 分差超过阈值（说明答案集中）；
- 问题不属于高风险类目；
- 生成答案中的每个关键事实都能在引用片段中找到**逐句对应**。

例如：「价保补差申请入口在哪里」——FAQ 有唯一条目，可自动答。

**L2 带警告的自动回答（黄色）**

命中多个相关片段，但结论一致；或问题略敏感但文档表述清晰。回答顶部加黄条：「以下依据 2025 版办法，2024 年 3 月 18 日前订单除外。」

**L3 人工审核后发布（橙色）**

触发条件任一即可：

- 检测到版本冲突；
- 赔付金额、法律术语、对外承诺表述；
- 检索 top3 相关度接近，模型置信度却很高（典型幻觉前兆）；
- 用户连续两次点击「答案没用」。

工单进入「知识运营队列」，由法务或政策owner 30 分钟内确认或改写。确认后的答案会写回「黄金问答对」，下次同类问题优先命中——这是**人工沉淀为可检索资产**，不是每次重新赌模型。

**L4 拒答与转人工（红色）**

知识库无命中，或命中内容均来自「已废止」「培训示例」；或用户追问「那你能不能替我承诺赔多少」。

系统明确说：「当前知识库没有足够依据回答该问题，已为你转接值班法务/客服专家。」同时记录问题文本，进入**知识缺口看板**——这是 PM 最该盯的 backlog：不是模型笨，是组织压根没把答案写进知识库。

降级不是失败，而是产品对业务风险的态度：**宁可少答，不可错答。**

### 第五章：成本、效率与那条被忽视的「知识飞轮」

一周后，小周向管理层汇报「修复后」的数据。结论不浪漫，但足够真实。

| 指标 | 事故前一周 | 修复后两周 |
|------|-----------|-----------|
| 内部知识库日问答量 | 4,200 | 4,800 |
| 自动回答率（L1+L2） | 78% | 61% |
| 人工审核队列（L3） | 几乎为 0 | 日均 186 条 |
| 用户「答案有用」率 | 71% | 84% |
| 对外错误承诺类投诉 | 3 起 | 0 起 |
| 平均响应时长 | 4.2 秒 | 9.8 秒（含人工） |

陈律只评价了一句：「9.8 秒换来零投诉，划算。」

成本账同样清楚：

- **计算成本**：每次问答要做「双路检索 + 重排 + 生成」，比单纯关键词 FAQ 贵 8–15 倍；加入重排后单次成本再涨 20%，但错误率下降更明显。
- **人工成本**：新设 2 名「知识运营」负责 L3 审核、文档版本标记、黄金问答维护；法务每周 2 小时抽检高风险问答。
- **纠错成本**：那次错误回答若对外扩散，潜在商家索赔谈判和品牌损失远超半年知识库预算。

小周在汇报最后写了一句给 PM 同行的话：

> **RAG 的 ROI 不在「替代多少客服」，而在「把组织里沉默的文档变成可复用、可审计、可迭代的答案资产」。** 自动回答率是果，知识治理（版本、权限、缺口）才是因。

系统最终保留的人工介入点：

- **入库时**：新文档必须标生效日期、废止关系、适用范围，否则不进赔付类检索池；
- **问答时**：高风险类目默认 L3 起；
- **问答后**：「没用」「举报错误」触发重审，同题错误两次则冻结自动回答；
- **周期运营**：每周从 L4 转人工和 L3 审核中提炼 Top 20 未覆盖问题，推动业务部门补文档。

# 3. 系统正解

这个系统的核心组件和数据流可以概括如下：

**用户提问 → 意图识别与 query 改写 → 混合检索（关键词 + 向量语义）→ 版本/权限过滤 → 重排序 → 片段组装 → 受控生成（仅基于检索上下文）→ 事实校验与风险拦截 → 分级发布（自动/警告/人工/拒答）→ 反馈回写知识库。**

回扣故事：商家问「预售能否退一赔三」，对应「query 改写 + 混合检索」；引用了 2023 年纪要，对应「缺版本过滤」；模型拼出错误肯定句，对应「生成幻觉 + 高风险拦截未触发」；陈律连夜电话，对应「无 L3 人工审核」；最后的黄金问答对，对应「人工确认后沉淀为可检索资产」。

在 AI 产品岗的典型应用场景：

- **需求文档**：不只写「接入大模型知识库」，要写清文档切分策略、元数据字段（版本、状态、部门、权限）、检索过滤规则、高风险类目清单、拒答话术、人工审核 SLA。
- **方案评审**：当业务方说「文档都上传了，为什么还不全自动」时，用事故案例反问——「赔付类问题答错一次，和少答 10% 哪个成本高？」
- **指标设计**：同时看自动回答率、答案有用率、幻觉举报率、人工审核通过率、知识缺口关闭时长；单独追求自动率会逼系统「说得太满」。
- **跨团队沟通**：跟算法说「重排阈值和高风险分类召回率」；跟工程说「废止文档不得进入检索池」；跟法务说「L3 审核是产品流程不是甩锅」；跟运营说「黄金问答对需要 owner 和过期机制」。

# 4. 类比锚定

## 旧知 → 新知：律师事务所的「研究员 + 主办律师」

传统 PM 都见过这种协作：客户问一个复杂问题，研究员先从案例库、法规库、内部备忘录里找出相关段落，整理成一份带出处的摘要；主办律师过目后，才决定能不能对客户说、怎么说、哪些话不能说死。

RAG 知识库问答，就是把这套分工做成系统：**研究员 = 检索与重排，主办律师 = 受控生成 + 人工审核，档案室规则 = 版本与权限管理。**

| 你熟悉的旧经验 | RAG 知识库问答系统 |
|---------------|-------------------|
| 客户原始问题 | 用户自然语言提问（口语、缩写、多意图） |
| 研究员检索案例库 | 混合检索 + 向量语义搜索 |
| 法规/案例的版本效力 | 文档生效日期、废止状态、适用范围元数据 |
| 研究备忘录（只列依据） | 检索片段组装成的上下文，不直接给用户 |
| 主办律师把关后对外口径 | 大模型生成 + 事实校验 + L3 人工审核 |
| 「这个问题我们要研究一下」 | L4 拒答 / 转人工 / 知识缺口工单 |
| 办案笔记沉淀为所内知识 | 审核通过的「黄金问答对」写回知识库 |
| 引注页码 | 答案脚注 + 原文高亮摘录 |

# 5. 类比边界与系统要点

## 类比在哪里会失效

律所研究员默认知道「新法优于旧法」、知道培训材料不能当法规引用；RAG 系统不会「懂」，除非你把规则写进元数据、过滤器和流程。**版本与权限不是档案室的常识，是产品要显式建模的配置。**

## A. 系统核心要点总结

- **数据输入要求与格式规范**：文档入库不是上传 PDF 就完事；需要结构化元数据（标题、版本、生效/废止日期、部门、权限、文档类型）、可检索的正文清洗（去页眉页脚、表格还原、图片 OCR），以及切分策略与原文锚点（能定位到页码/段落）。
- **AI 模型的能力边界与置信度**：检索模型解决「找得像不像」，生成模型解决「读起来顺不顺」； neither 能单独保证「对不对」。生成置信度高 ≠ 事实正确，必须有「答案-引用逐句对齐」校验。
- **人工介入的触发条件与流程**：版本冲突、高风险类目、低检索区分度、用户负反馈、连续同类失败——都应有明确触发 L3/L4 的规则，不能依赖用户「自己分辨」。
- **系统的容错与降级机制**：自动答 → 带警告答 → 人工审核 → 拒答转人工，应形成可配置降级链；关键业务场景宁可降低自动率，也要阻断错误肯定句对外流出。
- **成本结构**：计算成本（embedding、检索、重排、生成调用次数）、人工成本（知识运营、法务审核、文档治理）、纠错成本（错误承诺、合规事故、客户信任损失）要合并算账；重排和人工审核是「保险费」，不是纯开销。

## B. 类比失效点

1. **律师会追问澄清，默认系统不会**：用户问「能赔吗」可能缺订单日期、渠道、商品类目；RAG 若不做多轮澄清，容易在信息不全时给出过度肯定的答案。律所类比不会提醒你设计「槽位追问」或「条件分支回答」。
2. **研究员数量固定，检索池随上传指数膨胀**：文档从 500 份涨到 5 万份，「相关片段」的噪声会淹没信号；需要分库分域、权限隔离、定期退役低质量文档，不是档案柜越大越好。
3. **AI 输出是概率性的，同一问题两次答案可能措辞不同**：即使事实正确，表述波动也会让客服困惑「到底以哪次为准」；产品要提供「标准答案版本」和变更记录，不能像律所口头沟通那样容忍随意发挥。
4. **幻觉不会出现在研究员备忘录里，却会出现在生成环节**：材料明明写 5%–30%，模型可能说成「可以要求退一赔三」；必须有生成后事实校验，不能只看有没有脚注。
5. **知识需要持续迭代，不是一次入库永久有效**：政策、产品、活动规则按月变；废止关系、黄金问答过期、embedding 重建都是运营日常工作，律所类比容易让人误以为「建好库就结束」。

# 6. 深度业务洞察

1. **业务侧：用户要的是「敢对客户说的话」，不是「看起来专业的段落」**  
   业务方验收时爱测「刁钻问题能不能答上来」，但真正有价值的是：客服敢不敢把答案复制给客户、法务敢不敢在审计时签字。PM 要把验收标准从「有回答」改成「可对外、可追溯、可担责」。

2. **技术侧：RAG 难往往难在检索以外的「知识治理」**  
   向量检索、重排、大模型生成都有成熟组件；项目翻车的常见原因是：文档没版本、PDF 是扫描件、表格丢了、废止文件没下架、同题多口径没人 owner。工程化难点常常是做「文档生命周期管理」，不是调模型参数。

3. **运营侧：冷启动期要靠「黄金问答对」和人工审核养库**  
   新系统上线前 4–8 周，应用「窄域启动」：只开放 1–2 个高频低风险主题，人工审核通过的问答写回库；别一上来全库开放全自动。审核记录是最贵的训练数据——比盲目扩文档数量更有用。

4. **合规侧：答案必须可审计，引用必须可点击到原文**  
   ToB 客户和内部合规会问：「这个回答依据哪条制度、谁审核、何时生效？」需要保存检索候选、最终选用片段、生成结果、审核人、发布时间。黑盒聊天在合规场景走不通。

5. **商业侧：别用「省了多少客服人力」单维度卖 RAG**  
   对内可算「新人上手时间缩短、政策变更触达延迟下降」；对外 ToB 要算「错误回答导致的索赔风险」和「知识库维护服务」的持续费用。客户常低估文档治理成本，PM 要在售前把「谁负责更新文档、多久同步一次」写进合同，否则交付后一定扯皮。

### 动手小练习（30 分钟内可完成）

**练习：为你熟悉的一个政策主题设计「最小可行 RAG 验收表」**

1. 选一份你司（或虚构）的真实制度 PDF，不超过 10 页；  
2. 手写 8 个员工会问的口语问题，其中故意包含 2 个「旧版口径」和 2 个「文档没写」的问题；  
3. 列出 5 条元数据字段（如生效日期、废止状态），说明每条如何影响检索过滤；  
4. 为每个问题标注期望路径：L1 自动 / L3 人工 / L4 拒答。

完成后自问：如果只能测 3 个指标上线，你选哪 3 个？为什么不是「自动回答率越高越好」？写下你的理由——这就是你下一场方案评审的开场白。
