# 2. 业务场景故事

## 《周五四点五十分的那句「帮我把办公椅定下来」》

### 第一章：一句口语，背后藏着七个系统

4 月 11 日周五 16:50，云杉电商行政部的小林在飞书群里 @ 了刚上线的「行政小助手」：

> 「新搬来的设计组 12 个人，每人一把人体工学椅，预算 1500 以内，最好下周一到货，走公司采购流程。」

这条消息 47 个字，行政同学听了觉得「需求很清楚」。但刚转行做 AI 产品的小周盯着后台监控面板，知道这句话会触发一整套他花了三个月搭的 **采购 Agent**——不是聊天机器人回几句建议，而是真的去查供应商、比价格、填申请、推审批。

16:50:03，Agent 收到任务，状态从 `idle` 切到 `planning`。

16:50:08，规划模块输出了一份执行计划，共 9 步：

1. 解析需求字段（人数、品类、单价上限、到货时间、采购类型）
2. 查询「已签约供应商库」里符合品类 + 预算的候选
3. 对 top 3 供应商发起询价（调用采购系统 API）
4. 等待报价回传（或超时）
5. 按价格、交期、历史履约评分做对比
6. 生成《采购申请单》草稿
7. 校验预算科目与部门权限
8. 提交 OA 审批流
9. 回写结果并通知发起人

小周在演示时跟 VP 说过：「用户只说一句话，Agent 自己拆任务、调工具、跑完全流程。」

16:51:20，第一条告警跳出来：`tool_call_failed: vendor_inquiry_api timeout`。

小林还在等回复。她不知道的是，她的「一句话」，已经在背后烧了 6 次工具调用、2 次重试、1 次计划改写——而真正的翻车，还没开始。

**悬念**：Agent 不是「更聪明的 ChatGPT」，而是一套带状态机的业务流程执行器。小周要搞清楚的，不是模型会不会说话，而是「多步任务怎么不半路摔死」。

---

### 第二章：Agent 不是一次回答，而是「计划—执行—观测—修正」的循环

小周拉上工程负责人老韩和 Agent 框架同学阿宁，用 trace_id 把刚才那次任务从头回放。用户界面只有一段对话，系统内部其实跑的是 **ReAct 式循环**（Reason 推理下一步 + Act 调用工具 + Observe 看结果，反复直到完成或放弃）：

**第一轮：需求结构化（AI + 规则校验）**

Agent 先把口语需求抽成结构化字段：

| 字段 | 解析结果 | 置信度 |
|------|---------|--------|
| 品类 | 人体工学办公椅 | 0.94 |
| 数量 | 12 | 0.99 |
| 单价上限 | 1,500 元 | 0.91 |
| 到货时间 | 下周一（4/14） | 0.72 |
| 采购类型 | 行政物资集中采购 | 0.88 |
| 发起部门 | 设计组（需映射成本中心） | 0.65 |

注意最后一行：用户没说「设计组」，是从飞书组织架构推断的，置信度只有 0.65。这类字段如果直接往下传，后面预算校验可能报错。

系统规则：**置信度 < 0.8 的必填字段，必须先向用户确认，不得自动提交。**

但小周复盘时发现，这条规则写在 PRD 里，上线时被工程漏配了——Agent 直接用了推断值。这是第一个隐患，后面会爆。

**第二轮：工具调用链启动（工程 + 权限）**

Agent 按计划调用工具，每一步都是「带副作用」的真实操作，不是生成一段文字：

```
Step 1: search_approved_vendors(category="office_chair", max_price=1500)
  → 返回 5 家已签约供应商

Step 2: batch_inquiry(vendor_ids=[A,B,C], qty=12, delivery_date="2025-04-14")
  → A、B 成功发出询价单；C 的 API 超时

Step 3: retry(C, backoff=2s) → 仍超时
  → 触发「供应商不可用」分支
```

这里涉及 **工具调用链（Tool Chain）**：前一步的输出是后一步的输入。供应商 C 超时，不等于任务失败——Agent 应该走「降级到 A、B 两家比价」分支，而不是卡死。

阿宁在日志里指出：早期版本里，Agent 遇到超时后会「自己编一个报价」填进对比表——因为大模型的训练目标是「把话圆上」。这在聊天场景只是不好看，在采购场景是**事故**。

他们后来加了硬约束：**涉及金额、合同、审批的字段，只能来自工具返回值，模型不得生成。**

**第三轮：状态管理——系统要记住「办到哪了」**

16:52–16:58，Agent 进入 `waiting_quotes` 状态。这不是「模型在思考」，而是**异步等待外部系统回传**。

状态机大致如下：

```
planning → executing → waiting_external → comparing → drafting → approving → done
                ↓              ↓              ↓
            tool_error    quote_timeout    budget_reject
                ↓              ↓              ↓
            retry/fallback  replan         human_review
```

每个状态要持久化：

- 已调用了哪些工具、参数是什么、返回了什么（审计链）
- 当前计划走到第几步、哪些步骤可跳过、哪些不可逆
- 用户确认过的字段快照（防止中途改口）
- 超时计时器（询价 10 分钟不回 → 用已有报价继续，或问用户是否等）

老韩说：「Chat 无状态，Agent 必须有状态。服务一重启，不能让用户从头再说一遍。」

**第四轮：观测与修正——计划不是铁板一块**

16:58:40，供应商 A 报价 1,380 元/把，4/14 可到货；供应商 B 报价 1,290 元/把，但最早 4/18。

Agent 的对比模块算出综合分，B 更便宜但交期不满足。按采购制度，交期不满足应直接淘汰，不应为了低价牺牲硬约束。

于是 Agent **改写计划**：放弃 B，以 A 为主选，同时触发 `check_nearby_vendors` 看是否有 4/14 前能交货的备选。这是 **replan（重新规划）**——不是从头再来，而是在当前状态上局部调整。

小周在白板上画了个公式：**Agent 智能 ≠ 一次规划完美，而是「观测到偏差后能改计划」。**

### 第三章：真正翻车的地方——不是模型笨，是「不可逆步骤」没护栏

17:03，Agent 生成采购申请单，调用 `submit_purchase_request`——这一步不可逆，提交后就会占用预算、进入审批流。

提交前，系统跑了三道校验：

1. **预算科目校验**：设计组 Q2 行政采购预算剩余 8,400 元；12 × 1,380 = 16,560 元 → **超额**。
2. **权限校验**：小林是行政专员，可为设计组代提，但单笔超过 15,000 元需部门负责人联署。
3. **交期校验**：A 承诺 4/14，满足。

第 1 条直接红灯。根因是第二章埋的雷：成本中心被推断为「设计组」，而实际椅子应走「行政部统一采购科目」，预算池不同。

如果是传统表单，小林填到预算栏就会看到红色提示。Agent 路径里，这个错误被包在自动流程中，差点直接提交——幸好他们在 `submit` 前加了 **硬规则拦截**，预算不足时禁止调用提交工具。

Agent 进入 `human_review` 状态，给用户发消息：

> 「当前按设计组成本中心测算，预算不足（缺口 8,160 元）。请确认：是否改走行政部统一采购科目？确认后我将继续提交。」

小林回了一句「走行政采购」。Agent 更新状态快照，从 `drafting` 回到 `executing`，只重跑预算校验和提交两步——**不是从第一步重新询价**。

小周把这次有惊无险的拦截写进复盘：**不可逆工具调用前，必须有「规则闸门 + 人工确认」双保险。**

### 第四章：异常回退——工具挂了、人改口了、审批驳回了怎么办

同一晚，另一个用户任务就没这么幸运。有人让 Agent「帮我把上周出差的机票和酒店发票一起报了」，触发费用报销 Agent。这条链路更脆，因为涉及 OCR、发票验真、差旅标准、财务系统——任一环节失败都要会回退。

团队从周五晚上的两次任务里，总结出四类异常和对应策略：

**类型一：工具临时失败（可重试）**

- 现象：API 超时、503、限流
- 策略：指数退避重试（2s → 4s → 8s），最多 3 次；仍失败则标记该工具 `degraded`，走备用工具或跳过非关键步骤
- 例：供应商 C 询价超时 → 只用 A、B 比价，并在结果里注明「未纳入 C 的报价」

**类型二：业务规则拒绝（不可硬闯）**

- 现象：预算不足、权限不够、发票重复、超标
- 策略：停止不可逆操作，进入 `human_review`，向用户说明**具体哪条规则**拦住了，给出可选动作（改科目 / 拆单 / 找审批人）
- 禁止：让模型「想办法绕过去」

**类型三：用户中途改需求（状态冲突）**

- 现象：「还是改成 10 把吧」「预算提到 2000」
- 策略：比较新需求与已确认快照；若影响已执行步骤（如已询价 12 把），则提示「将作废当前询价，是否继续」；确认后部分回滚状态，保留仍可用的中间结果
- 关键：**回滚不是清内存，是状态机合法迁移**

**类型四：长流程外部驳回（跨天异步）**

- 现象：OA 审批驳回、财务打回、供应商突然缺货
- 策略：Agent 任务不能假设一次会话内结束；需要 `task_id` 持久化，支持次日从 `approving_rejected` 恢复，通知用户并给出「修改后重提 / 换供应商 / 终止」分支

老韩补充了工程底线：**每个工具调用都要幂等（同一操作执行两次结果一样）**。Agent 重试时如果 `submit_purchase_request` 不幂等，就会出现「一张申请单提交两次」的经典惨案。

### 第五章：人机边界——哪些步骤自动，哪些必须等人拍板

采购 Agent 上线一个月后，小周整理出「自动化权限矩阵」，这是 PM 最该盯的产品文档：

| 步骤 | 默认模式 | 必须人工确认的条件 |
|------|---------|-------------------|
| 需求解析 | 自动 | 关键字段置信度 < 0.8；金额 > 5 万 |
| 供应商检索 | 自动 | 无签约供应商命中 |
| 发起询价 | 自动 | 首次合作供应商；单笔 > 10 万 |
| 比价选型 | 自动推荐 | 交期与价格冲突；评分最高者非最低价 |
| 生成申请单 | 自动草稿 | 永远可编辑，不自动发送外部 |
| 提交审批 | **禁止自动** | 用户显式点击「确认提交」或授权一次性令牌 |
| 外部发邮件/签合同 | **禁止自动** | 必须人工 |

赵敏（行政负责人）说：「我可以接受你帮我跑 80% 的跑腿，但不能接受你替我向供应商承诺交期。」

最终产品形态是 **「Agent 跑流程，人在关键闸门签字」**：

- 低风险、可逆步骤：全自动，后台跑完给用户摘要
- 中风险：自动执行但推送「请确认」卡片，15 分钟无操作则暂停
- 高风险/不可逆：只准备材料，不代提交

小周在月报里写：**Agent 的自动化率不是越高越好，而是「把人的注意力留在真正需要判断的 5% 上」。**

### 第六章：成本、效率与那条看不见的调用账单

月底，财务问：「这个 Agent 一个月到底花了多少钱？」

小周拉了一张账，比「大模型 API 费用」复杂得多：

| 成本项 | 4 月数据 | 说明 |
|--------|---------|------|
| 大模型推理（规划 + 解析） | ¥3,200 | 单次任务平均 4.2 次模型调用 |
| 工具 API 调用 | ¥1,800 | 询价、预算、组织架构等 |
| 异步任务存储与状态机 | ¥600 | Redis + DB 持久化 |
| 人工审核工时 | ¥12,000（等效） | 约 18% 任务进 human_review |
| 纠错成本 | ¥2,400（等效） | 2 起错误科目，人工追回 |

**单次采购任务平均耗时 6.8 分钟**（含等待报价），比纯人工填表（平均 35 分钟）快很多。但 18% 进人工审核，意味着团队必须配「Agent 运营」角色——看 trace、补工具、改规则，不是上线即躺赢。

更隐蔽的成本是 **失败任务的沉没成本**：一条任务跑到第 7 步才因预算失败，前 6 步的工具调用和模型费用已经花了。产品上要算「**有效完成率**」，不能只看「启动了多少任务」。

小周给管理层的结论是：**Agent 的第一年 ROI，往往不在「省多少人」，而在「把跨系统流程的标准耗时从小时级压到分钟级」——前提是异常回退和人工闸门设计到位，否则省下的时间会变成返工。**

# 3. 系统正解

这个系统的核心组件和数据流可以概括如下：

**用户目标输入 → 规划器拆分子任务 → 状态机调度 → 工具调用链（带权限与幂等）→ 观测结果并局部重规划 → 不可逆节点规则闸门 + 人工确认 → 异步等待外部回传 → 结案通知与 trace 归档。**

回扣故事：小林一句「帮我把办公椅定下来」，对应「需求结构化 + 计划生成」；三家供应商询价，对应「工具调用链与超时降级」；预算超额拦截，对应「不可逆操作前的规则闸门」；「走行政采购」改科目，对应「状态快照更新与局部重跑」；周五晚上的报销任务，对应「跨系统长流程的异常回退与幂等设计」。

在 AI 产品岗的典型应用场景：

- **需求文档**：不只写「Agent 能自动采购」，要写清工具清单、每步输入输出、状态枚举、超时时间、不可逆操作列表、人工确认触发条件。
- **方案评审**：当业务方说「全程自动、用户别操心」时，反问「提交审批、对外发邮件、占用预算这三步，谁签字？出错了谁负责？」
- **指标设计**：同时看任务完成率、有效完成率（扣除末端失败）、平均步数、人工介入率、单任务成本、不可逆步骤前的拦截率；不要只报「自动化率 82%」。
- **跨团队沟通**：跟工程说「每个 tool 要幂等、要 audit log」；跟算法说「规划可以错，但不能编造工具返回值」；跟业务说「置信度低的字段必须确认，不是体验差，是风控」。

# 4. 类比锚定

## 旧知 → 新知：项目经理协调外包交付

传统 PM 都干过这种事：业务方提一个目标 → 你拆 WBS（工作分解结构）→ 分别找设计、开发、测试、法务对接 → 中间有人掉链子你改计划 → 上线前必须业务方签字 → 全程在项目管理工具里更新状态。

Agent 多步骤任务执行，本质上是**「一个永不下班的项目经理 + 一群 API 外包」**——只不过项目经理的大脑是大模型，外包是各个业务系统接口。

| 你熟悉的旧经验 | Agent 多步骤任务系统 |
|---------------|---------------------|
| 业务方一句「这周上线」 | 用户自然语言目标 |
| 拆 WBS、排依赖 | 规划器生成步骤与执行顺序 |
| 找 UI / 后端 / QA 对接 | 调用搜索、询价、预算、审批等工具 |
| 飞书群里「谁阻塞了」 | 状态机 + trace 观测当前卡在哪一步 |
| 外包延期，改排期 | 工具失败 / 交期不满足 → replan |
| 上线前业务签字 | 不可逆操作前的人工确认闸门 |
| 项目复盘留档 | 全链路 audit log，支持事后追责 |
| 范围变更要评估影响 | 用户改需求 → 对比状态快照，局部回滚 |

# 5. 类比边界与系统要点

## 类比在哪里会失效

项目经理靠经验和沟通兜底；Agent 靠代码和规则。人可以读懂「这话有歧义」，模型可能自信地把歧义执行到底。**自然语言目标的不确定性**，是「协调外包」类比覆盖不了的——你必须用置信度、确认卡片和规则闸门补位。

## A. 系统核心要点总结

- **数据输入要求与格式规范**：Agent 输入是口语化目标，系统必须尽快结构化为带置信度的字段；未确认的低置信度字段不得流入不可逆步骤。工具接口要有明确 schema（字段类型、必填、枚举），不能让模型「猜参数格式」。
- **AI 模型的能力边界与置信度**：规划、解析、总结适合模型做；金额、审批结果、供应商报价、预算余额只能来自工具返回。模型可以建议「选 A 供应商」，不能虚构 A 的报价。
- **人工介入的触发条件与流程**：不可逆操作前、规则冲突时、置信度不足时、用户改需求时——必须有 `human_review` 状态和明确 UI（确认卡片 / 驳回 / 修改后重试），不能只在后台默默失败。
- **系统的容错与降级机制**：工具超时 → 重试 → 备用工具 → 跳过非关键步骤 → 暂停并通知；计划偏差 → 局部 replan，而非从头重跑或硬闯。所有写操作幂等。
- **成本结构**：模型调用次数 × 工具 API 费用 + 异步状态存储 + 人工审核工时 + 失败任务沉没成本。Agent 比单次问答贵一个数量级，要用「有效完成率」和「单任务耗时」算账。

## B. 类比失效点

1. **人类项目经理会「先问清楚再做」**：Agent 默认倾向「先动手」以显得高效；产品必须主动加「确认闸门」，否则误解析会直接变成错误操作。
2. **外包是人，会拒绝非法需求**：工具 API 通常「给什么参数就执行什么」，不会道德判断；预算超额、越权访问要靠规则引擎拦，不能指望模型自律。
3. **项目延期可以商量，Agent 超时是硬中断**：异步等待要有明确超时策略和恢复路径；不能像人一样「再等两天问问供应商」——除非产品设计了这个分支。
4. **AI 系统的计划是概率生成的**：同样输入可能拆出不同步骤顺序；要用回归测试和 trace 对比，确保关键路径（如「先校验预算再提交」）由规则保证，而非赌模型每次都想对。
5. **审计与合规要求更高**：采购、报销、合同类 Agent 必须逐步留痕：谁授权、调了什么工具、依据什么数据做了决策。项目经理的口头对齐，在 Agent 场景里不够用。

# 6. 深度业务洞察

1. **业务侧：用户要的是「帮我把事办了」，不是「陪聊」**  
   演示时「自动提交采购单」很震撼，上线后用户最怕「你背着我提交了什么」。真实需求是：少填表、少跳转、关键步骤可预览可撤回。PM 要把「自动」拆成「自动准备」和「自动执行」，后者必须显式授权。

2. **技术侧：难的不是让模型会调工具，而是状态一致性**  
   很多 POC（概念验证）在单会话、单用户、无并发的实验室里跑得很顺，一上生产就遇到：服务重启丢状态、用户开两个窗口同时改需求、审批异步驳回。Agent 的工程化难度 70% 在状态机和幂等，30% 在模型。

3. **运营侧：工具覆盖率决定 Agent 上限**  
   模型再强，没有「查预算」「发询价」的 API，Agent 只能生成一段「建议你去找行政」的废话。冷启动要先盘点：目标流程里哪些步骤有接口、哪些只能人工、哪些根本没有数字化。**先补工具，再谈智能。**

4. **合规侧：每一步都要能回答「谁授权的」**  
   采购 Agent 若自动发邮件给外部供应商，邮件主体是公司还是个人账号？报销 Agent 读取发票信息是否经过用户授权？金融、医疗、政务场景要求 trace 保留 3–7 年。PM 要在 PRD 里写清数据流和授权边界，不是事后补审计。

5. **商业侧：按「任务完成」定价，不按「对话轮次」**  
   一次 Agent 任务可能触发 15 次模型调用和 8 次工具 API，按 Chat 套餐卖会亏穿。ToB 定价常见模式：按成功完成的任务数、按接入系统数、或按人工审核节省的工时。对客户要教育：**Agent 的价值是流程自动化，不是更便宜的聊天。**

### 动手小练习（30 分钟）

**练习：为一个「出差报销 Agent」画状态机**

1. 选你熟悉的公司报销流程，列出 6–8 个步骤（订机票、开发票、OCR、验真、填单、审批、打款）；  
2. 标出哪些是**可逆**、哪些是**不可逆**；  
3. 为每种异常（发票重复、超标、审批驳回）写一条回退路径；  
4. 标出 2 个必须人工确认的闸门。

完成后自问：如果用户在第 5 步说「机票不是这张，换一张」，你的状态机是需要从第几步重跑？那就是你下一份 Agent PRD 的核心页。
