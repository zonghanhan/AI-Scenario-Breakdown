# 2. 业务场景故事

## 《周一晨会前八分钟，CEO 问了句「华东毛利为什么掉了」》

### 第一章：电梯里的问题，会议室里没人接得住

周一 8:52，星澜 SaaS 公司 9 楼电梯里，CEO 李总随口问销售 VP 张薇：「上季度华东区毛利为什么掉了 3 个点？是价格战还是交付成本上去了？」

张薇愣了半秒：「我让数据同学拉一下，会后给您。」

9:00 晨会准时开始。李总的第一页 PPT 就是「Q2 经营复盘」，第三行写着：**华东毛利 41.2%，环比 -3.1pp**。他抬头：「张薇，原因找到了吗？」

会议室安静了三秒。数据分析师小周在后排疯狂切 Tab——他刚打开 BI 看板，发现「毛利」在财务口径和销售口径里是两个数；「华东」在 CRM 里按签约地算，在 ERP 里按发货地算；「上季度」有人从 4 月 1 日算，有人从财季 4 月算。

坐在张薇旁边的周航，是刚接手「智能数据助手」的 AI 产品经理。过去两周，他推动上线了一个 Demo：老板在企微里 @ 数据助手，用中文提问，系统自动出图出数。

李总看向周航：「你的智能助手，能在晨会现场答吗？」

周航心里一紧。他知道，这个问题表面是「查个数」，实际是**指标定义 × 组织权限 × 时间窗口 × 归因逻辑**四重叠加。答错一个数字，比答不上来更危险。

**悬念**：周航要在 8 分钟内，让系统给出一个「敢在 CEO 面前念出来」的答案——同时不能牺牲数据治理的底线。

### 第二章：一句话背后，系统其实走了六步

周航让小周把李总的原话输入助手：「上季度华东区毛利为什么掉了 3 个点？」

屏幕上出现「正在理解问题…」，后台日志显示，系统并不是直接让大模型「编一个 SQL」，而是走了一条产品化的链路：

**第一步：意图识别与指标消歧（AI + 规则）**

系统先从企业「指标词典」里匹配关键词：

| 用户表述 | 系统匹配 | 置信度 | 处理 |
|---------|---------|--------|------|
| 毛利 | `gross_margin_rate`（财务口径：收入-销货成本）/ `gross_margin_rate_sales`（销售口径：合同额-标准成本） | 0.71 / 0.68 | **触发消歧**：弹窗「您要财务毛利还是销售毛利？」 |
| 华东 | `region_east_china`（组织架构华东大区） | 0.89 | 自动选中 |
| 上季度 | `calendar_q2_2026`（自然季）/ `fiscal_q2_2026`（财季） | 0.82 / 0.79 | 默认自然季，标注「按自然季 Q2」 |
| 为什么掉了 | 归因分析意图 | 0.91 | 路由到「维度下钻 + 贡献度分解」 |

周航在 PRD 里写过一条铁律：**数字类问题，指标歧义必须显性确认，不允许静默猜测。**

小周在手机上点了「财务毛利 + 自然季 Q2」。系统继续。

**第二步：语义层映射（工程 + 元数据）**

企业数仓有 400+ 张表，大模型不可能每次从零猜表名。中间有一层 **语义层（Semantic Layer，把业务指标翻译成可查询的数据模型）**：

- `gross_margin_rate` → 绑定数据集 `dm_finance_region_monthly`
- 维度：大区、产品线、客户行业、渠道
- 默认过滤：已结账数据、`is_valid_order = 1`
- 禁止字段：成本明细中的供应商合同单价（采购敏感）

这一步基本是查配置，不靠模型「蒙」。

**第三步：Text-to-SQL 生成（AI 介入，带约束）**

大模型收到的是结构化 Prompt，而不是裸问题：

```
指标：gross_margin_rate
维度：region_east_china
时间：2026-Q2 vs 2026-Q1
任务：计算环比变化，并按产品线、渠道做贡献度分解
可用表：dm_finance_region_monthly, dim_product, dim_channel
禁止：不得 JOIN 未授权表；不得使用 SELECT *
```

模型输出 SQL 后，**SQL 校验器**（不是人）先做四件事：语法检查、只允许访问白名单表、自动注入行级权限（Row-Level Security，按登录人只能看自己权限范围内的行）、估算扫描行数——超过 5000 万行则拒绝执行，提示「请缩小时间范围」。

**第四步：执行与缓存（工程）**

查询命中「热路径缓存」——同样的问题 24 小时内问过 3 次，直接返回缓存结果，并在角标标注「数据截至 2026-07-31 02:00」。

本次是首次问法，走 Presto 执行，耗时 11 秒。周航松了口气：晨会还能撑住。

**第五步：结果解读与可视化（AI 辅助，非自动结论）**

系统返回：

1. **主指标卡**：华东 Q2 财务毛利率 41.2%，Q1 44.3%，环比 -3.1pp ✓（与李总 PPT 一致，说明口径对齐）
2. **贡献度瀑布图**：产品线「星链标准版」-1.8pp；渠道「集成商转售」-1.1pp；交付成本上升 -0.4pp；其他 +0.2pp
3. **文字摘要（AI 生成）**：「华东毛利下降主要来自星链标准版在集成商渠道的折扣加深，叠加 3 个大单交付工时超预算。」

注意：摘要最后一层是「解释」，系统用**高亮标签**区分——蓝色是 SQL 算出的数，灰色是模型基于维度名称做的「可能原因」表述，并附「需业务确认」。

**第六步：人工确认闸门（人机协作边界）**

按周航设计的流程，**首次向 C-level 推送的归因结论，必须经过数据分析师确认**。小周在手机上点「确认可展示」，结论才投屏到会议室大屏。

8:58，李总看到瀑布图，点点头：「集成商那三个大单，是哪三个？」

系统无法自动回答——这涉及客户名称，权限不足。小周补了一句：「会后我拉明细给您。」

周航记下：**AI 答宏观，人答敏感明细——边界清晰，晨会没翻车。**

### 第三章：第一次翻车，藏在两个「活跃用户」的定义里

智能助手上线第三周，市场部负责人王琳在群里问：「我们上月活跃用户是多少？比竞品 A 高还是低？」

系统秒回：「上月活跃用户 128,400，环比 +6.2%。」

王琳很高兴，把截图发进了部门群。第二天，增长团队负责人私下找周航：「你们这个数不对，我们 DAU 口径上月是 89,300。」

复盘发现，不是 SQL 写错了，是**同一个中文词，映射了不同指标**：

| 指标 ID | 业务定义 | 上月结果 |
|--------|---------|---------|
| `mau_login` | 至少登录 1 次 | 128,400 |
| `mau_core` | 完成核心功能（创建项目）≥1 次 | 89,300 |
| `mau_paid_active` | 付费且活跃 | 41,200 |

王琳问的是「活跃用户」，系统默认匹配了 `mau_login`——因为在指标词典里它的「默认展示」权重最高，但增长团队对外汇报一直用 `mau_core`。

更糟的是后半句：「比竞品 A 高还是低？」系统从公开行业报告库里检索到一句「竞品 A 月活约 15 万」，直接生成对比句。竞品数据是第三方估算，**不是公司数仓里的数**，却被和内部指标放在同一张图里。

周航紧急上了三条补丁：

1. **指标选择强制显性化**：凡涉及「活跃、留存、转化」等歧义词，UI 必须展示「当前口径：XXX」，并提供一键切换；
2. **内外部数据分栏**：内部数仓数据与外部情报不得在同一张图默认合并；
3. **「对比类问题」降级**：没有授权的外部数据源时，系统只回答内部部分，并提示「竞品对比需引用来源，是否查看市场部的竞品周报？」

王琳后来跟周航说：「我不是要一个更快的数，我要一个**不会在群里让我社死的数**。」

### 第四章：权限、审计与「能查到」不等于「能说出来」

第四周，财务部发现一条告警：实习生账号通过智能助手查询了「销售提成明细」，共 47 行。

周航调日志，链路很清楚：

- 实习生问：「华东 Q2 谁贡献的毛利最高？」——合理问题；
- 系统按权限应只返回汇总，但 SQL 生成时多 JOIN 了 `sales_commission_detail`；
- 校验器白名单配置疏漏，新表上线 3 天未同步进语义层；
- 行级权限在明细表上生效，但列级敏感字段（提成金额）未被屏蔽。

这次没传到外部，财务总监仍要求停服 48 小时整改。周航拉着数据工程开了整晚会，定下 **「查询四层锁」**：

1. **语义层授权**：每个指标标注「最低可访问角色」；
2. **SQL 白名单**：生成 SQL 只能引用已注册数据集；
3. **行级权限**：按组织架构自动注入 `WHERE dept_id IN (...)`；
4. **列级脱敏**：薪资、提成、成本单价等字段默认聚合展示，明细需二次审批。

同时补了 **审计日志**：谁、何时、问了什么、用了哪条 SQL、返回多少行、是否经人工确认——法务说，这比传统 BI「人工导 Excel 发邮件」更可追溯。

李总听说后只问了一句：「以后 CEO 问的问题，也会留痕吗？」

周航答：「会。但 C-level 的查询默认不经过实习生复核，走更严格的口径锁定，而不是更宽松的权限。」

### 第五章：人机分工重新定义——分析师没被替代，而是从「取数工」变成「口径法官」

上线两个月后，星澜做了一次效果复盘：

| 指标 | 上线前（人工取数） | 智能助手上线后 |
|------|-------------------|---------------|
| 常规经营问数平均响应 | 4.6 小时 | 38 秒（80% 问题） |
| 数据分析师每周取数工单 | 126 单 | 41 单 |
| 口径争议类工单 | 9 单/周 | 3 单/周（消歧前置） |
| CEO 晨会「现场答不上来」次数 | 月均 4 次 | 月均 1 次 |
| 错误数字外泄事件 | 1 起/季（人工 Excel 传错） | 2 起（均为口径误解，未超权限） |

成本账同样现实：

- **计算成本**：大模型 Text-to-SQL + 结果解读，月均约 ¥18,000；数仓 Ad-hoc 查询资源上涨 22%；
- **人工成本**：数据团队投入 2.5 人月建设语义层和指标词典，运营 0.5 人月/月维护；
- **纠错成本**：一次口径错误的公关/决策风险，远超全年系统费用——周航用「王琳事件」做过内部算账。

小周的工作变了：他不再花 60% 时间写重复 SQL，而是：

- 维护指标词典和「歧义词映射」；
- 审核新型问题的 SQL 模板；
- 处理系统标记的「低置信度查询」队列；
- 每周从「被用户点踩的回答」里回收口径漏洞。

李总总结：「我要的不是消灭数据部，而是让**会的的人去定义什么叫对，而不是天天给别人跑数**。」

周航在版本 roadmap 上写下下一阶段的边界：

- **AI 自动答**：单指标查询、标准环比同比、已注册维度的下钻；
- **AI 辅助 + 人确认**：归因类、跨部门指标、首次出现的问法；
- **必须人工**：薪酬明细、未注册指标、涉及对外披露的合并数据、监管报送口径。

# 3. 系统正解

这个系统的核心组件和数据流可以概括如下：

**自然语言提问 → 意图识别与指标消歧 → 语义层映射（指标/维度/权限） → 受约束的 Text-to-SQL → SQL 校验与权限注入 → 数仓执行 → 结果可视化 + AI 解读（区分「硬数字」与「软解释」） → 人工确认闸门（高风险场景） → 审计日志与反馈回写指标词典。**

回扣故事：李总电梯里的「华东毛利」，对应「指标消歧 + 语义层绑定财务毛利」；11 秒出瀑布图，对应「受约束 Text-to-SQL + 预聚合缓存」；王琳的活跃用户风波，对应「歧义词默认映射与内外部数据隔离」；实习生提成明细泄露，对应「SQL 白名单与列级脱敏漏洞」；小周点「确认可展示」，对应「C-level 归因结论的人工闸门」。

在 AI 产品岗的典型应用场景：

- **需求文档**：不只写「支持自然语言查数」，要写清指标词典结构、歧义处理 UI、SQL 白名单规则、权限注入点、低置信度降级策略、审计字段。
- **方案评审**：当业务方说「接个大模型就能查数」时，反问——「『活跃』有几个定义？谁有权看提成明细？错了谁负责？」
- **指标设计**：同时看「查询成功率」「口径争议率」「人工确认率」「平均响应时长」「数仓查询成本」；单一追求「自动回答率」会推高错误数字风险。
- **跨团队沟通**：跟数据工程说「新表上线 48 小时内必须进语义层」；跟算法说「Text-to-SQL 必须走受约束生成，不要裸 Prompt」；跟财务法务说「审计日志保留多久、谁可查看 CEO 查询记录」。

# 4. 类比锚定

## 旧知 → 新知：公司里的资深商务助理

传统 PM 都经历过：老板问一句「上次跟某某客户的合同谈得怎样了」，好的商务助理不会乱答——他会先确认你问的是签约金额还是合作意向，去档案柜找对了文件夹，只拿你权限能看的页，念关键数字，不确定的会说「这部分我建议会后请法务补充」。

智能 BI 问答，就是给全公司配了一个「24 小时在线、但必须遵守档案管理制度」的数据助理。

| 你熟悉的旧经验 | AI 辅助数据分析系统 |
|---------------|-------------------|
| 老板一句模糊提问 | 自然语言查询（NL Query） |
| 助理追问「您指签约额还是回款？」 | 指标消歧与口径确认 |
| 档案柜分区（合同/财务/人事） | 数仓数据集 + 语义层 |
| 助理知道去哪格抽屉找 | Text-to-SQL / 指标到表的映射 |
| 涉密文件不能给实习生看 | 行级/列级权限与脱敏 |
| 助理念数字，但解读说「这块建议您问销售总监」 | 结果区分「硬数字」与「AI 软解释」+ 人工确认 |
| 事后能查谁借了哪份档案 | 查询审计日志 |

# 5. 类比边界与系统要点

## 类比在哪里会失效

商务助理靠社会常识知道「这话不能乱说」；AI 没有常识，只有概率。**它可能用非常自信的语气，把两个不同口径的数字放在一句话里**——这是助理类比覆盖不了的风险。

## A. 系统核心要点总结

- **数据输入要求与格式规范**：依赖指标词典、表血缘、维度枚举值、时间口径（自然日/财季/滚动 30 天）；元数据腐烂比模型不聪明更致命，新表不上语义层等于「助理不知道有新档案」。
- **AI 模型的能力边界与置信度**：大模型擅长理解意图、生成 SQL 草稿、写自然语言摘要；不擅长保证 JOIN 正确、不擅长记住企业独有口径、**绝不应该在无校验时直接输出数字**。
- **人工介入的触发条件与流程**：指标歧义、低置信度 SQL、首次出现的跨表关联、归因/预测类结论、对外披露场景——必须有人工闸门，且流程要比「找分析师跑数」更快而不是更慢。
- **系统的容错与降级机制**：SQL 执行失败 → 缩小范围重试 → 推荐相近已注册指标 → 转人工工单；权限不足 → 返回聚合数据 + 说明原因，不能静默截断部分字段造成误解。
- **成本结构**：数仓扫描成本（大宽表 Ad-hoc 查询很贵）、模型推理成本、数据治理人力（语义层维护）、**错误数字造成的决策损失**——四类成本必须一起评估 ROI。

## B. 类比失效点

1. **助理会「不敢答」，模型会「硬答」**：商务助理不知道会说不知道；大模型在训练数据里见过类似问题，容易编造看似合理的 SQL 或数字。产品必须把「不知道/需确认」设计成一等公民状态，而不是异常。
2. **助理一次只服务一个人，查询系统要服务千人千权**：同一句话，销售 VP 和区域经理应看到不同粒度、不同行范围。权限不是外挂，是查询链路的必经环节。
3. **档案是静态的，指标是活的**：合同签完很少变；但「活跃用户」「有效线索」的定义可能每月被运营改掉。语义层需要版本管理和变更通知，不能像助理记一次就永久有效。
4. **AI 解读不是事实陈述**：瀑布图上的贡献度是算出来的，但「因为价格战」可能是模型生成的解释性语言——必须在 UI 上区分，否则决策者会把猜测当定论。
5. **合规要求远超「借档案登记」**：金融监管、个人信息保护、上市公司信息披露——查询日志、口径版本、谁向谁展示了什么数字，都可能成为审计证据。助理类比不会提醒你保留「当时用的是哪个指标版本」。

# 6. 深度业务洞察

1. **业务侧：表面要「秒级查数」，真实要「敢用这个数字做决策」**  
   业务方常把 Demo 里「问一句出一张图」当成终点。真实痛点是口径对齐和问责链——王琳要的不是 128,400 还是 89,300 本身，而是「哪个数能拿去跟老板汇报」。PM 要把「指标主权」写进产品：谁定义、谁发布、谁对对外数字负责。

2. **技术侧：难的不是 Text-to-SQL，是「企业级正确」**  
   公开榜单上 Text-to-SQL 准确率 80%+ 是在干净学术数据集上；企业里表名晦涩、JOIN 路径绕、历史脏数据多，**首次查询正确率**能到 60% 就不错。工程化重点应是语义层、SQL 校验器、权限注入——而不是更大的模型。很多项目翻车，是 governance 为零，却指望模型「足够聪明」。

3. **运营侧：指标词典是产品，不是数据团队的内部文档**  
   冷启动需要把 Top 50 高频指标手工治理清楚，比覆盖 500 个烂指标更有用。每次口径争议、每次用户点踩，都应回流成词典条目或 SQL 模板——这是数据飞轮，不是一次性项目。

4. **合规侧：「能查」和「能展示」是两条线**  
   行级权限阻止了越权，但聚合结果仍可能推断出敏感信息（如「某唯一大客户的毛利」）。高阶产品要考虑差分隐私、最小粒度限制、对外分享水印——尤其金融、医疗、人力场景。

5. **商业侧：ROI 别只算「省了几个分析师」**  
   真实收益是决策节奏加快、口径争议减少、重复取数工单下降；真实成本包括数仓算力上涨、语义层专人维护、一次口径错误的声誉损失。ToB 售卖时，客户买的是「治理 + 助手」，不是「聊天框」——定价应绑定指标数量、查询量、权限模块，而不是按 Seat 卖。

### 动手小练习（30 分钟）

**练习：为你熟悉的产品列一张「指标歧义词表」**

1. 写出 5 个业务方常说的模糊词（如：活跃、留存、转化、成本、收入）；  
2. 每个词列出至少 2 种可能口径，标注「对外汇报用哪个」「系统默认用哪个」；  
3. 设计一个消歧 UI 草图：用户不问清楚时，系统不能出数；  
4. 指定 1 个敏感指标，写清「谁能看汇总、谁能看明细、日志留多久」。

完成后自问：如果 CEO 在晨会现场问其中一个词，你敢让 AI 不经过确认就投屏吗？不敢的那几项，就是你的 MVP 必须先做的治理清单。
