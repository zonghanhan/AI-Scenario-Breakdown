# 2. 业务场景故事

## 《寒潮前夜，暖气公司的 2,156 张待派工单》

### 第一章：气象台发布蓝色预警，调度室大屏开始变红

12 月 14 日 17:30，北方城市「凛冬」气象台发布寒潮蓝色预警：48 小时内最低气温将降至 -18℃。暖通服务公司「恒温热力」的客服进线量在两小时内涨了 3.8 倍——暖气不热、漏水、异响、阀门失灵，电话和 App 报修同时涌进来。

调度主管老周盯着大屏：待派工单 2,156 张，已派未上门 487 张，师傅当日满载率 94%，平均客户等待时长从平时的 6 小时涨到 19 小时。他给刚接手 AI 派单产品的林薇发了一条消息：「去年寒潮我们是人工画地图、班长打电话喊人。今年你上了智能派单，别让我在大屏上看见同一个小区派了三个师傅、隔壁街道却没人去。」

林薇信心满满。过去两个月，她和算法、GIS（地理信息系统，就是在地图上算位置和路线）同学搭了一套「工程类 AI 派单系统」：用户报修后，系统自动识别故障类型、匹配师傅技能、规划路线，并给出预计上门时间（ETA，Estimated Time of Arrival，预计到达时间）。

寒潮前夜，系统日志却开始刷黄：一批「壁挂炉漏水」工单被派给了只会修集中供暖的师傅；两个标注「老人独居、暖气已停 24 小时」的紧急单，ETA 显示「次日 14:00」；Meanwhile，资深师傅老马的车定位在城南转了三圈——系统连续给他塞了 5 个单子，导航路线像麻花一样缠在一起。

老周在电话里只问了一句：「你的智能，是在帮师傅少跑路，还是在帮客户多等一天？」

**悬念**：林薇意识到，问题不是「有没有自动派单」，而是「派单到底在优化谁的体验、牺牲了什么」。

---

### 第二章：一张报修单进来，系统其实要做六道判断

林薇拉着 GIS 工程师和算法同学复盘第一条「派错人」的工单。这条工单来自城南某小区 8 楼，用户描述：「壁挂炉压力表红灯闪，底部有渗水，家里老人，暖气已经凉了。」

系统实际走的流程，比「找个最近的师傅」复杂得多：

**第一步：报修理解与分类（AI 介入）**

用户通过 App 提交：三张现场照片 + 一段 40 秒语音。系统先做：

- 语音转文字（ASR，自动语音识别）；
- 图像识别：判断设备类型（壁挂炉 vs 暖气片 vs 管道）；
- 文本分类：故障类型（漏水 / 不热 / 异响 / 无法点火）；
- 紧急度抽取：「老人」「暖气已停 24 小时」「渗水」→ 标为 **紧急**。

这一层用的是多模态模型 + 规则引擎的组合。AI 不直接决定派给谁，只负责「把现场情况说清楚」，并输出置信度——比如「壁挂炉」置信度 0.91，「漏水」置信度 0.87。

**第二步：技能与资质匹配（规则 + 模型）**

恒温热力给每个师傅维护了一张「技能矩阵」：

| 技能标签 | 含义 |
|---------|------|
| A-集中供暖 | 小区锅炉、公共管道、暖气片 |
| B-壁挂炉 | 各品牌燃气壁挂炉维修 |
| C-水电改造 | 管道更换、大面积漏水 |
| D-品牌认证 | 特定品牌（如博世、威能）官方授权 |

这条工单需要 B + C，且用户壁挂炉照片识别为「威能」品牌，优先匹配带 D（威能认证）的师傅。系统先筛出「具备 B+C 且当前在岗」的师傅，共 23 人。

**第三步：地理位置与可达性（GIS 为主）**

23 人分散在全城。系统不是简单选「直线距离最近的人」，而是算**路网可达时间**：

- 实时路况（晚高峰城南拥堵系数 1.6）；
- 师傅当前位置（GPS 定位，每 30 秒更新）；
- 若师傅正在其他工单现场，加上「收尾时间」预估（上一单平均 45 分钟）；
- 小区门禁/停车限制（部分老旧小区标注「车辆无法进入，需步行 200 米」）。

算法同学解释：「直线距离 2 公里的师傅，可能比 5 公里但在高速入口的师傅晚到 40 分钟。工程派单里，**路网时间比欧氏距离诚实得多**。」

**第四步：时间窗口约束（业务规则 + 用户偏好）**

用户选了「今日 18:00–21:00 可上门」。师傅老马当前工单预计 19:30 结束，到城南小区路网时间 35 分钟——**赶不上窗口**。系统不能把单硬塞给他。

时间窗口是硬约束，不是软偏好。违反窗口的派单，客户不在家或师傅白跑，二次上门成本极高。

**第五步：零件与库存（ERP 联动）**

工单分类为「壁挂炉漏水」，系统查配件库：

- 常见密封圈：城南仓有货；
- 若识别为「压力传感器故障」，需特定型号，只有城北总仓有——要算「师傅先去城北取件 + 再上门」的总时长。

有些工单因此从「今日可修」变成「明日待件」——这不是派单算法偷懒，而是**物理世界约束**。PM 常犯的错误是：只优化「谁去」，忘了「去了能不能修」。

**第六步：综合排程与派单（优化引擎 + 人机边界）**

系统在 23 个候选师傅里，用多目标优化算出一组方案：

- 目标 1：紧急工单 SLA 达标（紧急单 4 小时内上门）；
- 目标 2：师傅总行驶里程最小化（降低油耗和疲劳）；
- 目标 3：各师傅当日负载均衡（避免老马一天 8 单、新人 2 单）；
- 目标 4：时间窗口命中率最大化。

最终，工单派给了师傅「孙强」——B+C+D 全匹配、当前在城南、上一单 18:00 结束、路网 25 分钟可到、且今日负载 4 单（团队平均 5.5 单）。

派单后不是结束。系统同时做了三件事：

1. 给孙强推送工单详情 + 导航路线 + 备件清单（AI 辅助生成，师傅可修改）；
2. 给用户发短信：「孙师傅预计 18:40 到达，请保持电话畅通」；
3. 启动 SLA 倒计时——若 18:40 前孙强未点击「出发」，或 20:00 前未「到达」，自动升级到调度台红灯池。

林薇在复盘白板写下：**AI 负责看懂报修和排序，GIS 负责算路，规则负责边界，人负责接单、改约和最终判断。**

### 第三章：寒潮峰值来了，「最优路线」成了「最差体验」

寒潮前夜 20:00，问题从「派错人」变成了「派不出去」和「派了也去不了」。

全城 312 名师傅在岗，但 B 类（壁挂炉）只有 48 人，且 60% 集中在城北工业区——城南住宅密集区「师傅荒漠」。紧急工单 SLA 要求 4 小时内上门，系统按优化目标拼命派单，结果：

- **路线缠绕**：老马被连续派了 5 个城南单子，导航来回穿越拥堵路段，实际完成率只有 60%；
- **虚假可达**：系统按「上一单 45 分钟结束」估算，但老马遇到的是「老旧小区管道老化需大面积更换」——一单干了 2.5 小时，后面 4 单全部超时；
- **窗口雪崩**：大量用户选了「今晚」，但可上门师傅只有 80 人，时间窗口冲突率 67%——系统只能把单子排到次日，用户 App 上却先显示「已派单」，期望被拉高，失望更大。

更麻烦的是「幽灵空闲」：有些师傅状态显示「空闲」，实际在等配件、在内部培训、或手机 GPS 漂移到了河里。系统按「空闲 + 最近」派单，工单过去后无人响应，紧急单在队列里继续涨。

老周当场拍板了三条临时策略——这些后来都成了产品里的正式功能：

1. **区域熔断**：某片区紧急单堆积超过阈值（如 50 单 / 2 小时无人接单），自动触发「跨区调度补贴」，吸引城北师傅南下，并在 App 对用户诚实展示「该区域运力紧张，预计等待 X 小时」；
2. **动态改派**：师傅上一单超时超过 30 分钟，系统自动释放其后续工单回池，并优先改派给同片区其他师傅，同时给用户推送「师傅延误，已为您重新安排」；
3. **紧急池人工接管**：超过 SLA 50% 时间的紧急单（如老人独居、暖气停 24h+），强制进入红色池，调度员可一键「指定派单」或「协调配件直送」。

林薇这时才明白：工程派单不是一次算准的最优路径，而是**在物理约束和峰值需求下持续做可解释的权衡**。

### 第四章：那条等了 26 小时的「老人独居」工单，错在一个隐藏字段

复盘最严重的一起投诉时，团队发现一条标注「老人独居」的紧急工单，从报修到师傅上门等了 26 小时。表面看是「系统没派」，实际根因很土：

用户报修时勾选了「家中只有老人」，但 CRM 里的「高龄独居」标签依赖民政数据对接，接口当晚维护超时。系统用了默认值「普通住户」，紧急度从 P0 降到 P1，在优化队列里被不断往后挤——前面压着 200 多张「普通不热」工单，算法认为那些更容易「顺路批量解决」。

这类问题 AI 模型完全无能为力。GIS 工程师补充了「画像兜底链」：

1. 主接口 500 毫秒内返回 → 用实时特殊人群标签；
2. 超时 → 读 72 小时内缓存；
3. 缓存也没有 → 用保守策略：用户自述含「老人」「婴儿」「病人」关键词时，**强制 P0，宁可高估不可低估**；
4. 仍不确定 → 标为「待核实紧急度」，调度台 30 分钟内人工确认，期间禁止降到 P2 以下。

林薇把这条写进 PRD 的「非功能需求」：**派单系统的输入不只来自图像和语音，还来自上游画像、配件库存、路况和师傅真实状态——任一字段错误，都会让「正确算法」产出「错误派单」。**

### 第五章：师傅不是网约车，客户等的不是一分钟

寒潮结束后第三天，老周要林薇汇报「智能派单到底省了什么」。

数据并不浪漫，但很真实：

| 指标 | 人工派单（去年寒潮） | 智能派单（今年） |
|------|---------------------|-----------------|
| 紧急单 4h 上门率 | 62% | 81% |
| 师傅日均行驶里程 | 186 km | 142 km |
| 单次上门平均等待（客户侧） | 22 小时 | 14 小时 |
| 改派率（师傅去不了/去错了） | 24% | 13% |
| 调度员人工干预次数 | 890 次/周 | 145 次/周 |
| 配件白跑率（人到件没到） | 18% | 9% |

但成本账同样清楚：

- 算法侧：寒潮周多模态识别 + 路径优化计算量涨 5.3 倍，云 GPU 和 GIS 路网调用费用是平时的 4 倍；
- 运营侧：跨区调度补贴、临时外协师傅招募，当周额外支出 32 万元；
- 师傅侧：部分老师傅抵触「被系统指挥」，私下改单、跳过导航，导致数据回流失真，改派逻辑被误导；
- 客服侧：「已派单但迟迟不到」的投诉咨询涨了一倍——因为系统自动派单后先给用户发了「已安排师傅」，但 ETA 算错时，体验比「明确告知要等明天」更差。

老周说：「我要的不是零调度员，而是让调度员从『打电话喊人』变成『处理红色池、配件协调和规则例外』。」

系统最终保留的人工介入点：

- **派单前**：新小区首次报修、高风险设备（商用锅炉）、AI 置信度低于 0.7 的故障分类，强制过调度台确认；
- **派单后**：用户改约、师傅拒单、配件缺货、路况封路，触发自动改派或人工协调；
- **派单异常**：紧急单 SLA 过半、连续 2 次改派仍无人接单、特殊人群标签冲突时，红色池亮灯；
- **事后优化**：每周从「改派率高的工单类型 × 片区 × 师傅技能」反推标签缺口和运力盲区，更新派单策略。

林薇在汇报最后一页写：**工程类 AI 派单的目标，不是算出一条数学上的最短路径，而是把「谁去、何时去、带什么去、去了能不能一次修好」变成可配置、可监控、可降级的系统能力。**

# 3. 系统正解

这个系统的核心组件和数据流可以概括如下：

**报修接入 → 多模态理解（语音/图/文）→ 故障分类与紧急度 → 技能/资质匹配 → GIS 路网排程 → 配件库存校验 → 派单执行与 ETA 推送 → 超时改派与人工兜底 → 结案数据回写优化模型。**

回扣故事：用户三张照片 + 语音描述，对应「多模态报修理解」；孙强被选中，对应「技能矩阵 + 路网时间 + 时间窗口 + 负载均衡」；老人独居等了 26 小时，对应「上游特殊人群接口超时导致紧急度算错」；老周的红色池和跨区补贴，对应「SLA 熔断与人工接管」；配件白跑，对应「派单与库存 ERP 未联动」。

在 AI 产品岗的典型应用场景：

- **需求文档**：不只写「自动派单」，要写清输入字段（位置、故障类型、紧急度、时间窗口、特殊人群、设备品牌）、匹配规则优先级、改派触发条件、配件缺货时的降级策略。
- **方案评审**：当业务方要求「全部自动派、零人工」时，用寒潮峰值数据和改派成本反问——「紧急单无人接单时，系统允许等多久？是否对用户展示真实 ETA？」
- **指标设计**：同时看 SLA 达标率、师傅行驶里程、一次修复率、改派率、配件白跑率；单一追求「派单速度」会掩盖「派错人、白跑路」的隐性成本。
- **跨团队沟通**：跟算法说「分类置信度低于多少必须人工确认」；跟 GIS 说「路况数据更新频率和封路事件来源」；跟供应链说「派单前必须校验配件库存」；跟运营说「运力盲区要有诚实的用户预期管理」。

# 4. 类比锚定

## 旧知 → 新知：外卖骑手派单

做过本地生活或用过外卖的 PM 都理解：订单进来 → 找骑手 → 算距离和时间 → 骑手取餐 → 送达。工程类派单，本质是「上门服务版的骑手调度」，但约束更多、容错更窄。

| 你熟悉的旧经验（外卖派单） | 工程类 AI 派单系统 |
|---------------------------|-------------------|
| 商家地址 + 用户地址 | 师傅当前位置 + 客户小区地址 + 路网可达时间 |
| 骑手电动车 / 汽车 | 师傅技能资质 + 工具车类型 + 品牌认证 |
| 预计送达时间 ETA | 预计上门时间 ETA + 用户时间窗口 |
| 骑手手头订单数 | 师傅当日已派单数 + 当前工单预估工时 |
| 餐品已备好 vs 商家现做 | 配件库存有货 vs 需调拨取件 |
| 骑手拒单 / 联系不上 | 师傅拒单 / GPS 异常 / 改约 |
| 超时赔付 | SLA 违约（紧急单 4h 未上门） |
| 爆单时加价调度 | 跨区补贴 / 外协师傅 / 人工红色池 |

# 5. 类比边界与系统要点

## 类比在哪里会失效

外卖订单「餐品是什么」在下单时就确定了；工程报修「现场到底是什么问题、要不要换大件」要到师傅上门才真相大白。**现场不确定性**和**一次修复率**，是外卖类比覆盖不了的。

## A. 系统核心要点总结

- **数据输入要求与格式规范**：派单依赖的不只是报修文字，还有 GPS 实时位置、路网路况、配件库存、用户时间窗口、特殊人群标签；任一上游字段延迟、缺失或漂移，都会让「正确算法」产出「错误派单」或「虚假 ETA」。
- **AI 模型的能力边界与置信度**：多模态模型适合识别设备类型、故障大类、紧急关键词，不适合在低置信度时直接决定「派谁」；图像模糊、方言严重、新型设备时，必须人工确认或调度台预审。
- **人工介入的触发条件与流程**：特殊人群、高风险设备、配件缺货、连续改派、SLA 过半——这些必须有明确红灯规则，不能靠调度员「自己发现」。
- **系统的容错与降级机制**：自动派单 → 改派 → 跨区补贴 → 红色池人工指定 → 外协兜底，应是一条写进配置的降级链，而不是寒潮时临时拍脑袋。
- **成本结构**：计算成本（多模态推理 + GIS 路网）、人工成本（调度干预、跨区补贴、外协）、纠错成本（白跑、二次上门、SLA 赔付、客户流失）三者要一起算账，不能只报「节省了多少调度人力」。

## B. 类比失效点

1. **外卖可以「先派后取」，工程常常「先确认再去」**：很多维修单需要先电话沟通确认故障和配件，师傅拒单率高；不能像外卖一样「派了就必须去」。
2. **外卖时效是分钟级，工程是小时到天级**：用户等 2 小时和等 20 小时的感知完全不同；ETA 算错对信任的伤害，远大于外卖晚 10 分钟。
3. **工程有「一次修复率」硬指标**：把单派给「最近的人」可能提高上门速度，却提高二次上门率；优化目标必须纳入技能匹配深度，不能只追距离。
4. **AI 系统需要持续迭代**：新设备型号、新小区门禁规则、季节性故障模式每年变；技能矩阵、路网标注、分类模型是「运营资产」，不是上线一次就完的配置。
5. **概率性输出无法当硬开关**：「壁挂炉置信度 0.82」不代表一定是壁挂炉，不能把模型分数直接写成不可逆的派单条件，要和规则引擎、人工确认分层。
6. **合规与安全要求**：燃气、电力维修涉及特种作业资质；派单日志（为何派此人、依据哪些字段）必须可追溯，外卖派单类比不会提醒你过「资质审计」。

# 6. 深度业务洞察

1. **业务侧：表面要「更快派单」，真实要「更少二次上门」**  
   业务方常把 KPI 写成「派单响应 < 5 分钟」，但客户感知的是「来一次能不能修好」。二次上门一次，比多等 4 小时伤害更大。PM 要推动同时考核 SLA 达标率和一次修复率，并在方案里给「就近派单 vs 技能优先派单」划清场景边界。

2. **技术侧：路径优化往往不难，难的是「工时预估」和「状态同步」**  
   师傅 GPS 漂移、上一单实际工时远超预估、手机关机、配件临时缺货——任一不同步都会造成「幽灵空闲」和「连环超时」。很多项目图像识别做得很漂亮，却在派单上翻车——因为工程没把「师傅真实可用性和工单真实工时」当成和模型同等重要的输入。

3. **运营侧：技能标签和片区运力是活的，不是入职时填一次表**  
   新小区交付、寒潮、厂家召回，都会瞬间改变「哪个片区缺哪种师傅」。冷启动期宁可提高人工确认比例，也不要用不完整标签跑全自动。运力紧张时，**对用户诚实展示等待时间**，比「先派单再改派」更能保住信任。

4. **合规侧：派单逻辑要能解释，资质要能审计**  
   用户投诉「为什么紧急单等了 20 小时」，客服和监管需要看到：当时紧急度算出来是多少、为什么、是否触发过改派。燃气维修派给无资质师傅，法律责任远大于一次外卖超时。

5. **商业侧：ROI 别只算省了几个调度员**  
   工程派单的真实收益是 SLA 达标率提升、行驶成本下降、一次修复率提高、客户续约率上升。成本要算上多模态推理、GIS 调用、跨区补贴、外协、SLA 赔付。对季节性峰值，要做「寒潮周」和「平日」两套账，否则容易被一次峰值的人力节省误导。

### 官方文档 / API 参考

1. **高德 / 百度地图「路径规划」「货车路径」「实时路况」API 文档（中文）**  
   - 适合：需要写清「路网时间 vs 直线距离」、限行规则的 PM  
   - 解决什么：把「就近派单」翻译成工程可落地的「可达时间」字段，避免 PRD 里只有「按距离排序」

   - 适合：设计多模态报修入口的 PM  
   - 解决什么：理解语音转写、图像分类的置信度输出格式，便于定义「低于多少转人工」

### 行业最佳实践

3. **滴滴 / 美团「智能调度」「运力预测」技术分享（可搜「外卖派单」「网约车调度」）**  
   - 适合：想了解峰值下调度和 ETA 管理的 PM  
   - 解决什么：真实峰值场景里「改派、补贴、预期管理」怎么设计，而不是实验室里的理想路径

4. **Salesforce Field Service Lightning 产品文档（Scheduling & Optimization 章节）**

### 动手小练习（30 分钟）

**练习：画一张你自己的「工程派单决策表」**

1. 选你熟悉的一个上门场景（家电维修、物业报修、IT 上门、安装服务均可）；  
2. 列出 5 种故障类型、4 个技能标签、3 档紧急度、2 种时间窗口策略；  
3. 写清「自动派单 → 改派 → 人工红色池」各在什么条件下触发；  
4. 故意设计一个「配件缺货」和「GPS 漂移」场景，写下系统应如何降级。

完成后自问：如果寒潮/大促流量 ×5，你这张表最先崩的是哪一格？那就是你下一份 PRD 该优先补的非功能需求。
