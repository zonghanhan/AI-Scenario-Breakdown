# 2. 业务场景故事

## 《竞对高薪挖走的候选人，在我们系统里只排第 187 名》

### 第一章：周一晨会，业务总监问了一个尴尬的问题

周一早上 9:15，星云科技的产品周会上，商业化总监老周把一份 LinkedIn 截图投到大屏上：「这个人，陈默，前字节商业化产品负责人，带过年营收 8 亿的广告产品线。你们 HR 说『简历池里没有合适的人』，人家周五就被竞对用 120 万年包挖走了。」

负责招聘 AI 产品方向的 PM 林薇愣了一下。她记得上周五确实上线了一版「智能简历筛选系统」——JD 一发布，系统自动解析岗位要求，把 1,247 份简历打分排序，Top 50 推给 HR 初筛，理论上不该漏掉这种级别的人。

会后她拉数据：陈默的简历确实在系统里，综合匹配分 **62 分**，在「高级产品经理（商业化）」岗位下排 **第 187 名**，没有进入 HR 的待办列表。

HR 负责人苦笑：「我们一天收两百多份简历，只看系统推的前 50。第 187 名？没人会翻到那里。」

**悬念**：林薇意识到，问题不是「有没有 AI 筛简历」，而是「AI 用什么标准理解一份简历、又用什么标准理解一个岗位」。

---

### 第二章：一份简历进来，系统其实在干三件不同的事

林薇把陈默的简历和当时那份 JD 拉进复盘后台。团队发现，智能筛选并不是「搜关键词」这么简单，而是三条链路并行：

**第一件：JD 解析（把岗位说清楚）**

业务方在招聘系统里填的 JD 原文有 1,800 字，夹杂大量「加分项」「团队氛围」「我们希望你」之类的软描述。系统要先做结构化抽取：

| 字段 | 从 JD 里抽什么 | 陈默这个岗位的抽取结果 |
|------|---------------|----------------------|
| 硬性条件 | 年限、学历、行业、职级 | 5 年+ 产品经验；本科及以上；ToB/广告商业化背景 |
| 核心技能 | 可验证的能力项 | 广告策略、客户成功、定价模型、跨部门推动 |
| 场景经验 | 具体业务域 | 信息流/搜索广告、大客户售卖、ROI 优化 |
| 软素质 | 协作、抗压、沟通 | 能扛业绩、能下客户现场 |
| 一票否决 | 明确排除项 | 纯 C 端工具产品、无商业化经验 |

这一层通常用「规则模板 + 大模型信息抽取」组合。模型负责从冗长 JD 里捞出硬条件，规则负责防止把「熟悉 SQL 是加分项」误写成「必须会 SQL」。

**第二件：简历理解（把候选人说清楚）**

陈默的简历是 PDF，两页，排版干净，但信息分布很「老练」：

- 工作经历按项目写，职级写「产品负责人」而非「P7/P8」；
- 商业化成果用「带动 XX 赛道收入增长 40%」表述，没有出现 JD 里的关键词「广告策略」；
- 最近一段经历只有 14 个月，系统里的「稳定性规则」默认扣了 15 分；
- 教育背景是 211 本科，没有硕士，在「学历加权」里又扣 8 分。

简历理解链路要做：版面解析（PDF/Word/图片）→ 实体抽取（公司、职级、时间、项目）→ 经历归一化（「产品负责人」映射到「高级/资深产品」）→ 技能与成果推断（从项目描述里反推能力，而不是等候选人自己写「我会广告策略」）。

**第三件：匹配与排序（把人和岗位放一起比）**

匹配不是简单算「JD 关键词命中几个」，而是多层打分：

1. **硬门槛过滤**：学历、年限、行业是否一票否决；
2. **语义匹配**：简历项目与 JD 职责的向量相似度（把「收入增长」和「商业化变现」对齐）；
3. **经历可信度**：公司背书、职级连贯性、项目粒度是否可验证；
4. **风险信号**：频繁跳槽、空窗期、职级倒挂、简历注水嫌疑；
5. **业务偏好**：HR 或用人经理设的「优先看过」条件，如「有大厂商业化背景 +2 档」。

陈默的简历死在多处：关键词没命中、稳定性扣分、学历扣分、最近一段经历短。算法同学坦诚：「模型没觉得他不行，是规则引擎和加权策略把他埋了。」

---

### 第三章：HR 不是不想看，是「只看 Top 50」被逼出来的

林薇去招聘组坐了一下午。她发现真实工作流和 PRD 里画的并不一样：

**表面流程**：JD 发布 → AI 筛简历 → HR 初筛 → 业务面试 → 录用。

**实际流程**：

1. 同一个 JD，内推、猎头、校招渠道同时涌进来，简历格式千奇百怪；
2. HR 每天要处理 6 个岗位，每个岗位系统推 50 份，实际能仔细看的不超过 15 份；
3. 用人经理口头说「我要商业化背景」，JD 里却抄了去年模板，写了 23 条「熟悉/了解/有经验更佳」；
4. 猎头简历往往包装过度，关键词堆满，AI 打分反而更高；
5. 真正优质的「老法师」简历写得克制，不靠堆关键词。

负责初筛的 HR 小雨说：「我不是迷信 AI，是实在看不完。系统说 85 分以上的我基本不过脑子就约面，60 分以下的我默认不看。187 名？那是另一个世界。」

林薇画出了**人机协作的真实边界**：

| 环节 | AI 做什么 | 人做什么 |
|------|----------|----------|
| 简历入库 | 解析、去重、渠道打标 | 处理重复投递、异常格式 |
| 初筛排序 | 匹配打分、风险标注 | 只看 Top N，快速扫标题 |
| 灰色地带 | 标「建议人工复核」 | 判断「分数低但看起来怪」的简历 |
| 约面决策 | 不推荐、不否决 | HR 和业务经理拍板 |
| 面试反馈 | 记录拒因、回流训练 | 告诉系统「这类人要提高权重」 |

问题的关键浮出水面：**AI 的决策权限是「排序建议」，不是「录用否决」**；但当 HR 只能看 Top 50 时，排序就变成了事实上的录用门槛。

---

### 第四章：那条被标成「跳槽频繁」的 14 个月，其实是业务调整

复盘陈默个案时，团队发现最冤枉的一票来自「稳定性规则」：最近一段工作 14 个月，低于系统默认的 18 个月阈值。

实际上，那 14 个月里他完成了整条商业化产品线的 0-1，离职原因是业务线被战略砍掉，不是绩效问题。简历里写了一句「因业务调整离开」，但规则引擎没读懂这句软信息，直接扣 15 分。

类似的问题还有：

- **职级映射失败**：「产品负责人」在不同公司对应 P7 还是 P6，系统用了保守映射；
- **成果表述偏业务**：「带动赛道收入增长 40%」没有命中「广告」「定价」等词，语义分偏低；
- **内推标识没加权**：陈默是 CTO 朋友推荐的，但内推加分规则只对「分数 70 分以上」生效，他根本没触发；
- **一票否决误伤**：JD 里「有 ToB SaaS 经验优先」，陈默做的是 ToB 广告平台，被错误归到「偏 C 端流量产品」。

算法负责人提出修复方向，林薇却问：「我们是在修一个 bug，还是在承认——简历筛选本质上不可能靠一次打分定终身？」

团队当晚加了四条产品策略，后来写进正式版本：

1. **内推 / 猎头绿色通道**：不论 AI 分数，先进「人工必看池」，24 小时内 HR 必须处理；
2. **低分高潜复核**：满足「大厂背书 + 职级达标 + 内推」任一组合，分数低于 70 也强制进复核队列；
3. **可解释拒因**：每份未进 Top 50 的简历，HR 可一键查看「扣分项」，而不是只看一个数字；
4. **业务经理纠偏**：面试后无论录用与否，用人经理可标注「系统高估/低估」，回流到下一批排序。

---

### 第五章：上线 30 天后，他们不再问「AI 准不准」，而是问「省下了什么」

一个月后，林薇向管理层汇报。数据不性感，但足够诚实：

| 指标 | 纯人工初筛（上月） | AI 辅助筛选（本月） |
|------|-------------------|-------------------|
| 单岗位 HR 初筛耗时 | 6.2 小时 | 2.1 小时 |
| 进入面试的候选人里「业务认可匹配度」 | 41% | 58% |
| 猎头包装简历通过初筛率 | 34% | 19% |
| 「低分复核池」捞回并录用 | — | 3 人（含 1 名 P7） |
| 漏看优质简历投诉 | 2 起/月 | 0 起 |

成本账同样清楚：

- **计算成本**：简历解析 + 语义匹配，单月 1,247 份简历，推理费用约 380 元；看似便宜，但若是集团全年 50 万份简历，就要单独做预算；
- **人工成本**：HR 从「全量翻简历」变成「看 Top 50 + 复核池 20 份」，但新增了「解释扣分项」「标注系统纠偏」的操作；
- **标注成本**：前 200 份「HR 最终约面 vs AI 分数」的对齐数据，用来校准权重，消耗 3 个 HR 人日；
- **纠错成本**：漏掉陈默这种个案，表面是 0 元，实际是一单招聘失败的机会成本——高级岗位空窗 2 个月，业务侧折算损失远超系统建设费。

老周看完只说：「我可以接受 AI 偶尔推错一个，不能接受把对的人排在 187 名还告诉我『系统运行正常』。」

林薇在汇报结尾写：**简历智能筛选的目标，不是替代 HR 的判断，而是在看不完的简历海里，把「该花 3 分钟仔细看的人」推到前面，同时给「被误伤的少数人」留一条人工兜底的路。**

# 3. 系统正解

这个系统的核心组件和数据流可以概括如下：

**JD 发布 → JD 结构化解析 → 简历入库与版面解析 → 简历实体抽取与归一化 → 多层匹配打分 → 风险标注 → Top N 推送 + 灰色复核池 → HR/业务面试 → 反馈回流优化权重。**

回扣故事：JD 里 23 条「熟悉/了解」对应「JD 解析需区分硬门槛与加分项」；陈默简历排第 187 名对应「规则扣分 + 语义未对齐 + Top 50 截断」；14 个月被扣稳定性分对应「风险规则需支持可解释与人工覆盖」；内推没进复核池对应「渠道策略应优先于纯分数」；小雨只看 Top 50 对应「产品必须按真实人力设计推送量与兜底池」。

在 AI 产品岗的典型应用场景：

- **需求文档**：不只写「AI 自动筛简历」，要写清 JD 字段分层（必须/优先/加分）、简历解析支持的格式、打分维度权重、Top N 推送规则、低分复核触发条件、面试反馈回流机制。
- **方案评审**：当业务方要求「全自动筛掉 80% 简历」时，追问——「被筛掉的人里，内推和猎头占多少？误杀一个高级岗的代价谁承担？」
- **指标设计**：同时看「HR 单位时间处理量」「进入面试的业务匹配率」「低分复核池捞回率」「优质简历漏看率」；单一追求「筛选自动化率」会把排序变成黑盒否决。
- **跨团队沟通**：跟算法说「语义匹配和规则扣分冲突时以哪个为准」；跟工程说「PDF 解析失败时是否阻断流程」；跟 HR 说「Top 50 是产品约束还是业务承诺」；跟法务说「简历数据存多久、模型训练能否用候选人信息」。

# 4. 类比锚定

## 旧知 → 新知：房产中介帮客户配盘

做过 C 端或平台产品的 PM，多少都见过「中介根据你的预算、地段、户型需求推房源」——客户说一堆模糊需求，中介手里有一堆房源卡片，最后给你一份「最值得先看的 10 套」。

简历智能筛选，就是招聘场景的「配盘系统」：JD 是客户需求，简历是房源，AI 是中介的初步筛选，HR 是带你看房的人，业务经理是最终拍板是否出价的人。

| 你熟悉的旧经验 | 简历智能筛选系统 |
|---------------|-----------------|
| 客户口头需求（「近地铁、三房、预算 500 万」） | 业务方口头要求 + JD 正文里的硬条件与软偏好 |
| 需求表单结构化（面积、学区、楼层） | JD 解析后的年限、技能、行业、职级字段 |
| 房源卡片（面积、朝向、装修、挂牌价） | 结构化简历（公司、职级、项目、成果、教育） |
| 虚假房源 / 图片美化 | 简历包装、关键词堆砌、猎头过度美化 |
| 中介先筛 10 套「最值得看」 | AI 输出 Top N 排序 + 风险标签 |
| 「这套不在预算里但值得一看」 | 低分高潜复核池、内推绿色通道 |
| 看完房后的「这套不行，下次别推类似的」 | 面试反馈回流，调整匹配权重 |

# 5. 类比边界与系统要点

## 类比在哪里会失效

房产配盘里，房源参数相对标准化（面积、价格、户型），且「挂牌价」是显性字段；简历里的大量价值藏在项目表述方式、公司背书、职级语境里，**同一经历在不同公司叙事下会呈现完全不同的可匹配性**。中介配盘是「信息撮合」，简历筛选还叠加了**公平性、合规性和不可量化的潜力判断**——这是房产类比天然覆盖不了的。

## A. 系统核心要点总结

- **数据输入要求与格式规范**：JD 需区分「必须/优先/加分/否决」；简历需支持 PDF/Word/图片及多渠道格式；职级、公司、时间线要做归一化，否则匹配分不可比。
- **AI 模型的能力边界与置信度**：语义匹配擅长「换一种说法识别同一能力」，不擅长「判断简历是否造假」或「预测文化契合」；低置信度解析结果（如模糊职级、空窗期原因）应触发人工复核，而非直接扣分。
- **人工介入的触发条件与流程**：内推/猎头必看、低分高潜复核、解析失败、一票否决边缘、业务经理点名——这些必须有独立队列，不能淹没在 Top N 之外。
- **系统的容错与降级机制**：解析失败 → 原文进人工池；语义分与规则分冲突 → 可配置优先级；模型服务不可用 → 回退关键词 + 规则粗筛，并标明「降级模式」。
- **成本结构**：计算成本（解析+匹配调用量）、人工成本（HR 初筛、复核池、纠偏标注）、纠错成本（漏招/误招的机会成本与品牌伤害）要一起核算；高级岗和低级岗应用不同策略，不能一套权重打天下。

## B. 类比失效点

1. **房源不会「因为表述方式不同而贬值」，简历会**：同样的大厂背景，写「负责增长」和写「带动收入增长 40%」在关键词系统里差很多；PM 必须推动「成果推断」而不只是「关键词命中」。
2. **房产中介可以推荐超预算房源，招聘 AI 常被要求「严格卡门槛」**：业务方希望「一个都不能漏」又希望「一个都不能错」，这在概率系统里互相矛盾；产品要想清楚「漏招」和「误杀」哪边更不能接受。
3. **AI 系统需要持续迭代**：同一岗位 JD 每招一次都可能变；公司职级体系、行业热门技能每年都在变；权重和规则不是上线一次就完，要靠面试反馈和 HR 纠偏持续回流。
4. **概率性输出不能当录用法律依据**：「匹配分 62」不是「不符合录用条件」的证据；在劳动合规和公平招聘语境下，系统输出是「排序建议」，拒因必须可追溯、可申诉。
5. **招聘涉及歧视红线**：年龄、性别、籍贯、婚育等敏感信息不应进入匹配特征；房产配盘不会提醒你做法务合规，简历 AI 必须做字段脱敏和审计。

# 6. 深度业务洞察

1. **业务侧：表面要「少看简历」，真实要「少漏人、少惹事」**  
   用人经理常说「帮我从一千份里筛出十个能聊的」，但真漏掉一个高级候选人时，抱怨的是「你们 AI 不行」。PM 要在需求阶段把「推送量」和「兜底池」设计进去，而不是只交付一个分数。

2. **技术侧：最难的不是匹配模型，是「简历解析」和「职级归一化」**  
   很多项目语义模型不错，却倒在 PDF 表格错位、时间线断裂、职级乱写上。解析置信度低于阈值时，宁可进人工池，也不要基于错误结构化结果打分——否则后面模型越准，错得越自信。

3. **运营侧：冷启动没有「天然标注数据」**  
   不像客服质检有历史工单，新岗位上线时常没有「什么样算合适」的样本。前 50～100 份「HR 最终约面」的对齐数据极其珍贵，应产品设计成「上线首月强制反馈模式」，而不是急着吹自动化率。

4. **合规侧：自动化筛选正在各国被严格审视**  
   欧盟 AI Act、美国部分州的招聘算法披露要求，都在推动「候选人有权知悉自动化决策」「企业需做偏见审计」。PM 要提前问法务：分数是否向候选人披露？训练数据是否含历史歧视性招聘结果？

5. **商业侧：ROI 别只算 HR 节省的小时数**  
   高级岗位空窗一周的业务损失，往往远大于 HR 少翻 200 份简历省下的时间。卖给企业客户时，应用「高级岗漏招成本 vs 系统费用」算账；对内产品，要给高级岗和低级岗配置不同策略，而不是一套模型省到底。

# 7. 学习资料参考

### 官方文档 / API 参考

1. **Moka / 北森 / 飞书招聘「智能简历解析」产品说明（中文帮助中心）**  
   - 适合：需要写清「简历字段、解析失败处理、渠道来源」的 PM  
   - 解决什么：看成熟 ATS（招聘管理系统）如何把非结构化简历落成可匹配字段，避免 PRD 里只有「上传简历」四个字

2. **OpenAI / 阿里云百炼「结构化信息抽取」API 文档（Resume / JD parsing 示例）**  
   - 适合：需要和工程评估「解析链路可否用大模型」的 PM  
   - 解决什么：理解从长文本抽实体、做 JSON 输出的能力边界与调用成本

### 行业最佳实践

3. **LinkedIn「AI-assisted hiring」与「Skills Graph」公开材料（中英均可搜到）**  
   - 适合：做中高端招聘、关注「技能图谱」而非关键词的 PM  
   - 解决什么：看工业级如何把「职位-技能-经历」建成可计算关系，而不是单次 JD 匹配

4. **美团 / 字节跳动技术博客中「简历推荐」「人岗匹配」相关分享**  
   - 适合：想了解大厂如何做排序、去偏、冷启动的 PM  
   - 解决什么：真实业务里「规则 + 模型 + 反馈」如何分层，而不是实验室里的 NDCG 指标

### 适合 PM 的科普与课程

5. **吴恩达 DeepLearning.AI《AI For Everyone》中关于 HR / 招聘用例的短章节（有中文字幕）**  
   - 适合：刚转行、需要建立「哪些环节适合 AI」直觉的 PM  
   - 解决什么：区分「筛简历」「写 JD」「面试辅助」的不同产品边界

6. **播客《组织人事杂谈》或 HR Tech 类中文播客中关于「AI 招聘合规」的单集**  
   - 适合：需要跟法务、HR 开会的 PM  
   - 解决什么：建立公平招聘、算法偏见的业务语感，不必读论文

### 动手小练习（30 分钟）

**练习：做一张「JD-简历匹配决策表」**

1. 选你熟悉的一个岗位（或虚构「高级产品经理-商业化」）；  
2. 写 5 条「必须」、5 条「加分」、3 条「一票否决」；  
3. 找一份真实或虚构的简历，手工打「硬门槛 / 语义匹配 / 风险扣分」三列；  
4. 设计：什么条件下进 Top 50？什么条件下进「低分复核池」？内推是否绕过分数？

完成后自问：若候选人职级写得很模糊、但项目经历很强，你的表会把他排第几？那就是你方案里「解析置信度 + 人工兜底」该出现的位置。
