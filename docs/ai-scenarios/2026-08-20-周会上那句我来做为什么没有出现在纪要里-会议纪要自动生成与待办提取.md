# 2. 业务场景故事

## 《周会上那句「我来做」，为什么没有出现在纪要里》

### 第一章：会开完了，纪要还没人动笔

周四下午 3 点，云杉科技「Q4 会员体系改版」跨部门评审会准时开始。参会 11 人：产品、前端、后端、数据、法务、运营，线上 4 人、线下 7 人。会议预定 60 分钟，实际开了 94 分钟。

散会时，产品负责人林姐在群里发了一句：「辛苦，纪要今天下班前发，待办同步 Jira。」

过去，这类会由产品经理小周手写纪要：回放录音、暂停、打字、再核对「谁说了要做什么」。平均一场 90 分钟的跨部门会，纪要要花 2.5 小时，待办漏跟率约 18%——不是不想跟，是「会上口头答应、会后没人记得写进系统」。

这次，小周刚推动上线「智能会议纪要系统」。林姐的 KPI 里写得很清楚：**纪要产出时间从 T+1 天缩短到 T+30 分钟，待办自动入库率 ≥ 85%。**

小周很有信心。系统流程他画过三遍：会议结束 → 自动拉取腾讯会议的云端录音 → ASR（自动语音识别，把语音转成文字）→ 大模型生成结构化纪要 → 抽取 Action Item（待办事项）→ 推送到飞书文档和 Jira。

4:34，会议结束。4:41，系统提示「纪要已生成，待办 7 条，请确认后发布」。小周打开预览，第一眼就觉得不对：摘要里写着「会员等级规则下周对齐」，但没有负责人；待办列表里有一条「浩哥负责 API 字段冻结」——浩哥根本没参会，是主持人口误把「豪哥」听成了「浩哥」。

林姐在 5:15 私信小周：「最重要的那句谁看到了？法务说『积分兑换涉及抽奖合规，必须我先出意见才能开发』——这条怎么不在纪要里？」

**悬念**：小周意识到，问题不是「有没有自动生成」，而是「一场会里，哪些话算数、哪些话要变成可执行的待办」。

---

### 第二章：一条待办被创建之前，系统其实走了六道工序

小周拉着语音算法和工程同学，把林姐追问的那句话在系统里逐帧回放。法务老陈在 14:23 说：「积分兑换如果涉及抽奖，我得先看方案，你们别急着开发。」

系统实际走的链路，比「语音转文字再摘要」复杂得多：

**第一道：音频采集与预处理（工程为主）**

会议录音来自腾讯会议云端，双声道，采样率 16kHz。系统先做：

- 去除静音段、背景键盘声（降噪）；
- 按说话人分离（Diarization，区分「谁在说话」）——线上 4 人里，有 2 人用了同款 USB 麦克风，声纹（每个人声音的特征）相似，系统把其中 3 段话标成了「Speaker_3」；
- 生成带时间戳的逐字稿（Transcript，带「几分几秒说了什么」的全文记录）。

**第二道：ASR 转写（AI 介入，误差从这里开始）**

老陈带口音，加上「抽奖合规」被识别成「抽奖合股」。更致命的是中间插了一句同事咳嗽，ASR 把半句「我得先看方案」和后半句「你们别急着开发」拆到了两个说话人名下。

算法同学调出置信度（模型对识别结果有多把握）：「我得先看方案」整句 ASR 置信度 0.71，低于系统默认的 0.80 自动入库线。

**第三道：会议结构理解（AI + 规则）**

大模型读取逐字稿后，按预设模板切分章节：

| 章节 | 内容来源 |
|------|---------|
| 背景与目标 | 开场 5 分钟 + 主持人复述 |
| 方案讨论 | 产品演示段落 |
| 风险与依赖 | 法务、数据发言 |
| 结论与待办 | 最后 15 分钟 |

问题出在「风险与依赖」：老陈的发言被 ASR 标为低置信度，又被错误归到「Speaker_3」——模型在生成摘要时，把这段话降权成「有人提到合规需注意」，没有升格为**阻塞性待办**。

**第四道：待办抽取（AI 介入，产品规则决定形态）**

待办不是「摘要里提到的事」，而是结构化字段：

- **动作**（做什么）：如「输出积分兑换合规意见」
- **负责人**（谁来做）：必须映射到企业通讯录里的真实 userId
- **截止时间**（何时完成）：显式日期，或「会后 3 个工作日」这类可计算表达
- **优先级 / 是否阻塞**（不做会怎样）：是否卡住开发
- **来源锚点**（哪句话）：原话时间戳 + 逐字稿片段，方便复核

系统从老陈的话里其实抽到了动作「出合规意见」，但负责人匹配失败——「Speaker_3」无法映射到人，规则引擎把这条待办打上了「待确认」标签，却没有进入小周的强制确认队列，因为默认策略是「待确认待办 ≤ 2 条时静默挂起」。

**第五道：人机确认（本应是产品定义的闸门）**

小周设计的发布流程是：生成 → 会议发起人 10 分钟内确认 → 一键同步 Jira/飞书。

但小周当时正在开下一场会，手机静音。系统 30 分钟后自动执行了「超时自动发布（草稿模式）」——这是工程为了「提高自动化率」加的默认值，PRD 里其实写的是「超时提醒，不自动发布」。配置被运维改过一次，没人通知产品。

**第六道：任务分发与回写（工程 + 集成）**

已确认的 6 条待办里，4 条进了 Jira，2 条进了飞书任务——因为有些团队用 Jira，有些用飞书，映射表不完整。「浩哥负责 API 字段冻结」进了 Jira，@ 了错误的浩哥；真正负责的架构师豪哥没收到通知。

小周在白板上写下：**纪要系统的核心不是「写得像人」，而是「把会上承诺变成可追踪、可问责、可复核的任务」。**

### 第三章：一场会里，至少有五类「话」不能同等对待

复盘会上，林姐让小周先别讲技术，讲清楚「你们怎么定义一句话算不算待办」。

小周梳理了真实会议里的五类发言：

| 类型 | 例子 | 系统应如何处理 |
|------|------|----------------|
| **明确承诺** | 「这块我来做，周五前给你」 | 高优抽取 → 必须有人名+时间 → 人工确认 |
| **条件阻塞** | 「合规没意见前不能开发」 | 标为 Blocker（阻塞项）→ 即使没说是谁做，也要生成待办并 @ 法务接口人 |
| **讨论中的假设** | 「如果我们砍掉积分兑换呢？」 | 不进待办，进「未决问题」列表 |
| **背景陈述** | 「去年会员流失率是 12%」 | 进纪要正文，不生成任务 |
| **口头玩笑 / 插科打诨** | 「再改需求我就辞职」 | 过滤，不进任何输出 |

之前的系统几乎把所有「动词句」都当待办候选，导致待办 inflation（待办通胀）——一场会抽出 23 条，真正该跟的只有 7 条，大家很快对系统自动通知免疫。

算法同学提议用大模型做「意图分类」，小周坚持加一层**业务规则**：

1. 出现「我来做」「我来跟」「我负责」「截止」「之前必须」→ 强制进入高优待办池；
2. 出现「不能」「不行」「先别」「阻塞」「等……再」→ 标 Blocker，默认负责人走「职能接口人表」（如法务 → 老陈）；
3. 出现「如果」「 maybe 」「是不是可以」→ 降权到「讨论记录」，不自动生成 Jira；
4. ASR 置信度 < 0.75 且含 Blocker 关键词 → **必须人工复核**，不允许静默挂起。

林姐点头：「法务那句话，不是普通待办，是红灯。你们之前把它当黄灯了。」

---

### 第四章：线上混合开会，「听见」比「听懂」更难

团队接着排查第二个大坑：Speaker 分离在混合会议里几乎必错。

线下 7 人共用一个全向麦克风，线上 4 人各自接入。系统把 38% 的发言标成「Speaker_未知」。当豪哥在线下说「API 字段我来冻结，周三前」，ASR 转写正确，但说话人标成「Speaker_2」——通讯录里 Speaker_2 被历史数据错误关联到了测试账号「浩哥」。

工程负责人提出三条工程补丁，后来写进 PRD：

1. **会前绑定**：参会者入会时扫码确认身份，把「会议账号 ↔ 工号」写进 metadata；说话人分离结果优先用 metadata 校正，而不是纯声纹。
2. **关键节点人工锚点**：主持人点击「进入结论环节」或输入 `#待办` 时，系统提高后续 10 分钟内抽取的权重，并强制弹出确认框。
3. **负责人二次确认**：凡待办负责人不是「明确指名（老陈/豪哥）」而是 Speaker_ID 推断的，发布前必须人工点选——**不允许 Speaker_ID 直接创建 Jira assignee**。

小周还推动了一个「看起来不 AI」的功能：**会后 5 分钟「待办速确认」弹窗**——只展示 Blocker + 低置信度高优句，参会者手机点「是我说的 / 不是 / 记错了」三选一，30 秒完成。运营数据显示，这项功能把负责人错误率从 19% 降到 6%，比换更大的 ASR 模型还管用。

### 第五章：自动化的边界——哪些纪要可以 AI 写，哪些必须人过一眼

上线一个月后，数据并不浪漫，但很真实：

| 指标 | 人工纪要（上月均值） | 智能纪要（本月） |
|------|---------------------|-----------------|
| 纪要产出时长 | 2.5 小时/场 | 18 分钟/场（含确认） |
| 待办漏跟率（2 周回访） | 18% | 9% |
| 负责人错误率 | 5%（人工也会写错） | 6% → 优化后 4% |
| 参会者「愿意看纪要」比例 | 62% | 71% |
| 会后纠纷「我说没说过」次数 | 11 次/月 | 4 次/月 |

成本同样清楚：

- **ASR + 大模型推理**：90 分钟会议约 ¥8–15/场（含摘要、抽取、多轮校正），月度 200 场约 ¥2,000–3,000；
- **人工复核**：Blocker 待办强制确认，每场平均多 6 分钟人力，但比全手写节省 80%+；
- **集成维护**：Jira/飞书字段映射、人员离职账号同步，每月约 0.5 人日；
- **纠错成本**：一次「错误待办 @ 错人导致开发白干两天」的隐性成本，远高于一年 ASR 账单。

林姐最终拍板的**人机协作边界**：

- **AI 全自动**：背景摘要、讨论要点、未决问题列表、高置信度非 Blocker 待办（置信度 > 0.85 且指名明确）；
- **AI 生成 + 发起人必确认**：任何 Blocker、任何负责人推断、任何 ASR 置信度 < 0.75 的句子；
- **人工主笔**：对外客户会议、人事/绩效、涉密项目——仅提供逐字稿辅助，不自动发布纪要；
- **异常降级**：ASR 整体失败率 > 15% 或说话人分离 UNKNOWN > 50% → 退回「逐字稿 + 模板填空」，不硬发「智能纪要」。

小周在复盘最后一页写：**会议纪要系统的目标，不是替代记录员，而是把「会后记忆博弈」变成「带时间戳、可审计、可分发的工作流」。**

# 3. 系统正解

这个系统的核心组件和数据流可以概括如下：

**会议结束 → 音频采集/预处理 → ASR 逐字稿 + 说话人分离 → 章节结构切分 → 摘要生成 → 待办/Blocker 结构化抽取 → 人机确认闸门 → 同步协作工具（Jira/飞书/Notion）→ 跟进提醒与闭环回写。**

回扣故事：老陈的合规意见没进纪要，对应「ASR 低置信度 + 说话人未映射 + Blocker 规则未生效」三重失效；「浩哥背锅」对应「Speaker 分离错误 + 禁止 Speaker_ID 直派 Jira 规则缺失」；林姐追问的那句「我来做」，对应「明确承诺类发言必须高优抽取且不能静默挂起」的产品规则。

在 AI 产品岗的典型应用场景：

- **需求文档**：不只写「自动生成纪要」，要写清音频来源、说话人识别策略、待办字段 schema、Blocker 定义、确认超时策略、哪些会议类型禁用自动发布。
- **方案评审**：当业务方要求「零人工、开完即发」时，用「负责人错误一次的人力成本」和「法务阻塞项漏跟的合规风险」反问——「漏一条 Blocker，谁担责？」
- **指标设计**：同时看纪要产出时长、待办漏跟率、负责人准确率、参会者阅读率、纠纷「我没说过」次数；单一追求「自动化率 95%」会牺牲 Blocker 召回。
- **跨团队沟通**：跟算法说「ASR 置信度如何参与复核队列」；跟工程说「会前 identity 绑定和 Jira 映射表谁维护」；跟法务说「哪些词触发 Blocker 必须人工确认」。

# 4. 类比锚定

## 旧知 → 新知：新闻编辑部的「录音 → 听写 → 剪辑 → 发稿 → 分版」

传统 PM 都见过内容生产：记者采访录音 → 听写员出稿 → 编辑删冗余、留重点 → 责编标「待跟进」→ 校对 → 分到各版面。智能会议纪要，就是企业场景里的一场「内部发布会报道」，只不过读者不是公众，而是参会者和没参会但必须执行的人。

| 你熟悉的旧经验 | 会议纪要自动生成系统 |
|---------------|---------------------|
| 现场采访录音 | 会议云端录音 / 本地采集 |
| 听写员听打 | ASR 语音转文字 |
| 编辑删废话、留引语 | 摘要生成 + 章节结构切分 |
| 责编标注「待核实/待跟进」 | 待办/Blocker 结构化抽取 |
| 校对核对人名职务 | 说话人映射 + 负责人确认 |
| 社会版/财经版/评论版分稿 | 同步 Jira / 飞书 / 邮件 / Wiki |
| 读者来信纠错 | 会后「我说没说过」仲裁 + 时间戳锚点 |

# 5. 类比边界与系统要点

## 类比在哪里会失效

新闻稿可以「略去口语、重组语序」只要不改原意；会议待办如果「略去」或「改写」一句话，可能直接变成错误的工作指令。**待办抽取要求 fidelity（忠实），摘要要求 readability（可读）——同一系统里两种目标打架**，是编辑部类比覆盖不了的。

## A. 系统核心要点总结

- **数据输入要求与格式规范**：除音频外，还需参会名单、工号映射、会议类型、职能接口人表、协作工具字段映射；混合会议必须解决「谁在说」，否则会前 identity 绑定比换模型更优先。
- **AI 模型的能力边界与置信度**：ASR 在口音、专有名词、叠话场景必错；大模型擅长摘要但可能「脑补」结论；待办负责人不能由模型猜，低置信度句必须人工确认。
- **人工介入的触发条件与流程**：Blocker 关键词、Speaker 推断负责人、ASR 置信度低于阈值、涉密会议类型——需明确「强制确认队列」，禁止静默挂起或超时自动发布（除非 PRD 明确允许）。
- **系统的容错与降级机制**：ASR 失败 → 仅出逐字稿；说话人 UNKNOWN 过高 → 模板填空模式；待办无法映射负责人 → 退回发起人确认，不创建 orphan task（无主任务）。
- **成本结构**：计算成本（ASR 时长 × 模型单价）、人工成本（Blocker 确认、映射表维护）、纠错成本（错派待办、漏跟合规项、会后扯皮）需一起核算；更长会议非线性变贵（摘要上下文窗口、多轮校正）。

## B. 类比失效点

1. **新闻允许「后期剪辑」，待办不允许**：摘要可以合并三句话，待办必须锚定原话时间戳；把「剪辑思维」用在待办上，是产品事故高发区。
2. **报道面向读者，纪要面向执行者**：执行者要的是「谁、做什么、何时、阻塞谁」四要素，不是写得漂亮的 narrative（叙事）；编辑部类比容易让人过度 invest 在「文笔」而忽视结构化字段。
3. **AI 输出是概率性的，发布会截稿时间是硬性的**：同一录音跑两次，待办列表可能略有差异；产品必须设计「确认后再发布」而非「生成即真理」，并保留版本 diff。
4. **会议是多人博弈，不是单人叙述**：打断、抢话、阴阳怪气、「你刚才说啥」——说话人分离和意图分类在真实会议里比采访复杂一个数量级。
5. **合规与审计**：人事、法务、客户会议涉及隐私和承诺记录；逐字稿和纪要版本、确认人、发布时间需可追溯，新闻编辑部类比不会提醒你留「谁确认了这条待办」的审计链。

# 6. 深度业务洞察

1. **业务侧：表面要「省写纪要时间」，真实要「会后少扯皮、少漏跟」**  
   业务方 KPI 常写「纪要 30 分钟内产出」，但管理者真正怕的是「会上明明说好了，两周后互相甩锅」。PM 要把「待办漏跟率」「Blocker 召回率」「会后争议次数」写进成功标准，而不只是「自动化率」。

2. **技术侧：难的不是摘要，是 Speaker + 负责人 + 时间**  
   很多 POC（概念验证）演示只展示「摘要很漂亮」，一上生产就栽在「豪哥变浩哥」「周五变下周五」。工程上，会前 identity 绑定和职能接口人表，往往比再训一个 ASR 模型 ROI 更高。

3. **运营侧：待办通胀比待办遗漏更隐蔽**  
   抽取太多「讨论句」当待办，团队会对系统通知脱敏，真正重要的 Blocker 反而被淹没。冷启动期应保守：宁可多人工确认，也不要「场场 20 条待办」。

4. **合规侧：逐字稿是证据，摘要是观点**  
   劳动纠纷、客户合同变更、监管检查可能要求出示「当时怎么说的」。产品要区分存储策略：逐字稿长期留存、摘要标注「AI 生成需确认」、待办记录确认人和来源锚点。

5. **商业侧：别按「场」卖，要按「闭环」卖**  
   ToB 客户买的不是「转写准确率 95%」，而是「待办进他们的 Jira 且跟得动」。集成深度、确认工作流、提醒闭环决定续费；只卖 ASR 转写容易陷入价格战。

   - 适合：使用 Microsoft 365 的企业 PM

3. **飞书开放平台 — 会议纪要 / 妙记、Jira REST API 创建 Issue 文档**  
   - 适合：负责「纪要 → 待办入库」集成的 PM  
   - 解决什么：字段怎么映射、assignee 如何用 userId 而不是 displayName

### 行业最佳实践

### 动手小练习（30 分钟）

**练习：用一场真实或模拟会议，设计你的「待办抽取规则表」**

1. 找一段 15–20 分钟的公开会议录像（产品发布会 Q&A、开源项目 RFC 讨论均可）；  
2. 人工列出你认为的「明确承诺 / Blocker / 讨论句 / 背景句」各 3 条；  
3. 写 5 条「如果 ASR 置信度 < X 则……」规则 + 3 条「禁止自动创建 Jira」规则；  
4. 指定 1 个「Speaker 无法识别」时的兜底流程（谁确认、时限多久）。

完成后自问：如果你的规则全自动跑，哪一类话最可能被误伤？那就是你 PRD 里「强制人工确认队列」的第一批条目。
