# 2. 业务场景故事

## 《文档明明更新了，为什么助手还在说旧政策》

### 第一章：一条报销咨询，财务群里炸锅了

3 月 6 日 10:17，云杉科技销售部的林涛在飞书问内部 AI 助手「小杉」：「客户招待费，单次上限多少？需要提前审批吗？」

小杉 3 秒后回复：

> 根据《云杉科技费用报销管理制度（2023 版）》，业务招待费单次上限 800 元，超过 500 元需直属主管审批。

林涛照此填报，下午带着客户吃了 980 元的商务宴请，发票提交后被财务驳回：「2025 年 1 月起，销售线招待费单次上限已调整为 1,500 元，且 1,000 元以上才需 VP 审批。你这张票按新规可以报，但审批流走错了。」

林涛懵：「我问的是 AI 助手，它给的数比制度还严，我怎么知道要去看飞书文档第几版？」

财务总监老周把截图丢进「AI 落地群」，@ 刚转岗做 AI 产品的苏念：「知识库 2 月 28 日就更新了，为什么助手还在背 2023 年的旧规？」

苏念的第一反应是查模型——「是不是 GPT 瞎编？」工程同学五分钟定位：**模型没瞎编，它忠实引用了检索到的文档片段；问题是，检索到的就是旧版 PDF 的第 14 页。**

**悬念**：苏念意识到，这不是「模型不够聪明」，而是「知识库喂错了、找错了、或找对了但拼错了」。

---

### 第二章：用户只问一句话，系统背后要走七步

苏念拉着知识库工程负责人和算法同学，把林涛这次问答的全链路日志拉出来。表面是一次对话，背后是一条完整的 RAG（Retrieval-Augmented Generation，检索增强生成：先从文档库找相关内容，再让大模型组织成答案）流水线：

**第一步：问题理解与改写（AI 介入）**

用户原问：「客户招待费，单次上限多少？需要提前审批吗？」

系统先做 Query 改写（把口语问题改写成更适合搜索的形式）：

- 子问题 A：销售业务招待费单次上限
- 子问题 B：业务招待费审批阈值与流程

改写用的是轻量模型 + 规则：若问题含「报销」「招待费」，自动挂上标签 `finance/expense/entertainment`。

**第二步：权限过滤（工程 + 规则，常被 PM 忽略）**

云杉知识库按部门设权限：全员可见「通用制度」，销售专属条款在 `sales-policy` 集合。林涛是销售，两个集合都搜。

但如果检索时不做权限过滤，会出现「搜到了但用户不该看」的合规事故——这一步必须在向量检索（把文字变成数学向量来比相似度）**之前**完成，而不是生成答案后再遮。

**第三步：向量检索 + 关键词混合召回（AI + 工程）**

每个知识库文档在入库时被切成若干 Chunk（文档块，通常 300–800 字一段），转成向量存进数据库。

林涛的问题命中了 6 个 Chunk，按相似度排序：

| 排名 | 来源文档 | 相似度 | 版本日期 |
|------|---------|--------|---------|
| 1 | 《费用报销管理制度（2023 版）》§4.2 招待费 | 0.89 | 2023-06 |
| 2 | 《费用报销管理制度（2023 版）》§4.2 招待费（副本） | 0.88 | 2023-06 |
| 3 | 《2025 销售激励与费用补充说明》§2.1 | 0.84 | 2025-01 |
| 4 | 财务 FAQ：常见驳回原因 | 0.79 | 2024-11 |
| 5 | 《费用报销管理制度（2025 版）》§4.2 | 0.76 | 2025-01 |
| 6 |  onboarding 培训 slide 截图 OCR 文本 | 0.74 | 2022-09 |

问题在这里露头：**2023 版被切成 47 个 Chunk，向量覆盖极全；2025 版刚入库 6 天，只切了 12 个 Chunk，且「销售招待费 1,500 元」写在表格里，OCR 后表格结构被打散，相似度反而低于旧版正文。**

**第四步：重排序（Rerank，AI 介入）**

召回 6 条后，Rerank 模型（专门判断「这段文字和问题有多相关」的二道筛子）把 Rank 1、2 的 2023 版片段又往上推了一把——因为它们的表述和用户问题几乎字面对仗。

Rank 5 的 2025 版 §4.2 虽被召回，但排在 Context 窗口（模型一次能读入的参考资料长度上限）的末尾，且被截断，表格里的「1,500 元」那一行没进上下文。

**第五步：上下文组装与引用生成（工程）**

系统把 Top-3 Chunk 拼成 Prompt（给模型的指令），要求：「仅依据引用内容回答，并在末尾标注来源。」

模型读到的三段里，两段来自 2023 版，一段来自 2024 FAQ——**没有任何一段完整包含 2025 销售线的 1,500 元新规。**

**第六步：大模型生成答案（AI 介入）**

大模型严格按 Prompt 要求，引用了 2023 版 §4.2，生成林涛看到的那条回复。从「生成质量」看，模型表现完美；从「业务正确性」看，系统整体失败。

**第七步：置信度评估与人工兜底（人机协作边界）**

系统其实算了一个「检索置信度分」：Top1 与 Top5 相似度差距仅 0.13，属于「多版本冲突」灰区。按苏念之前写的 PRD，这种情况应触发：

- 回答末尾显示「检测到多版本制度，请以 2025-01 版为准」；
- 或直接降级：「我不确定，已为你打开最新制度链接 + 转人工」。

但这条规则在上线前被业务方砍了——「加警告显得 AI 不智能」。于是灰区默认走「自信回答」。

苏念在白板写下：**RAG 的质量上限 = 检索到的内容质量 × 组装策略 × 生成约束；模型只负责最后一环。**

### 第三章：文档入库那天，踩了三个「看不见的坑」

苏念把 2025 版制度更新流程复盘了一遍，发现事故在入库阶段就埋下了：

**坑 1：旧文档没有「下线」，只是「不再推荐」**

2 月 28 日，法务上传了 2025 版 PDF 到飞书知识库，但 2023 版文件仍留在同一目录，状态是「已归档」而非「已失效」。索引系统 nightly job（夜间批处理任务）把两个版本都 embed（向量化入库）了，检索时没有「版本优先」策略。

**坑 2：Chunk 切在表格中间**

2025 版 §4.2 是一张跨页表格：「岗位序列 | 单次上限 | 审批节点」。切块策略按固定 512 token 切，一刀下去，「销售序列 1,500 元」被拆成两个 Chunk，前半段只有「销售序列」，后半段只有「1,500 元需 VP 审批」——单独检索时语义不完整，相似度打分偏低。

**坑 3：增量更新延迟 72 小时**

知识库索引是 T+1 全量 + 增量队列。2 月 28 日上传的文档，3 月 1 日才完成 re-index（重新建索引）。林涛 3 月 6 日提问时 2025 版已在库，但 rank 仍被旧版压制——**不是没入库，是入库质量差 + 排序策略旧。**

工程负责人补充：他们还缺一个「文档生效日期」元数据字段。法务以为「上传 = 生效」，系统以为「入库 = 可引用」，中间没有 `effective_from`（生效起始日）过滤。

### 第四章：当检索不到时，系统更危险

修复版本策略的同时，苏念要求压测另一个场景：**用户问了一个知识库里根本没有的内容，系统会怎么说？**

测试问题：「云杉科技驻外补贴，每天多少？」——公司尚未发布驻外政策。

旧逻辑下，系统仍召回「差旅补贴」「异地办公申请流程」等弱相关 Chunk，相似度最高 0.62。大模型在「必须依据引用回答」和「用户等着要答案」的双重压力下，生成：

> 驻外补贴参考国内差旅标准，一般按 300 元/天执行，具体以 HR 确认为准。

这句话**半真半假**：300 元/天来自某份 2021 年「短期出差」FAQ，和「驻外补贴」不是一回事，但模型把它们缝合了——这就是 RAG 场景最典型的**幻觉（Hallucination，模型编造或混用不存在/不相关的内容）**。

苏念和算法同学定了一条硬规则，写进产品：

| 检索最高分 | 系统行为 |
|-----------|---------|
| ≥ 0.82 | 正常生成 + 引用来源 |
| 0.70 – 0.82 | 生成 + 显著低置信提示 + 推荐相关文档链接 |
| < 0.70 | **禁止生成具体数字/日期/审批结论**；只返回「未找到明确规定」+ 转 HR 工单 |

算法同学强调：「阈值不是 universal 的，要按业务域调——财务域宁可少答，不能错答。」

### 第五章：人机协作——从「问答机器人」到「可审计的知识服务」

老周给苏念下了一个很 PM 的 KPI：**财务域问答准确率 ≥ 95%，错答率 < 1%，且每错 1 次要能在 24 小时内追溯原因。**

苏念把系统从「聊天框」升级成「知识服务」，人工介入点明确写进配置：

**回答前：**

- 多版本冲突、低置信度、涉及金额/合规 → 不直接给结论，或强制展示最新版链接；
- 新规生效后 14 天内，旧版 Chunk 自动降权（不是删除，防审计需要）。

**回答后：**

- 每个答案带「引用片段 + 文档版本 + 生效日期」可展开；
- 「这个答案有帮助吗」点「否」→ 进入 Bad Case 队列，运营/法务 48 小时内标注：检索错 / 切块错 / 生成错 / 文档本身错。

**兜底：**

- 连续 2 次点踩，或用户输入「我要人工」→ 转 HR/财务在线客服，对话上下文一并带过去；
- 客服结案后，若发现文档问题，走「文档修正 → 优先 re-index」快速通道。

**成本与效率账：**

| 指标 | 纯人工 FAQ（旧） | RAG 上线 3 个月 |
|------|-----------------|----------------|
| HR/财务重复咨询量 | 约 420 次/月 | 约 180 次/月 |
| 单次问答成本（人工折算） | ≈ 8 分钟人力 | ≈ 0.03 元推理 + 0.3 元检索 |
| 错答导致的驳回/返工 | 基线 12 次/月 | 峰值曾到 9 次/月（版本事故月） |
| 文档维护人力 | 分散在各 BP | 集中 0.5 人日/周做 Bad Case + 切块抽检 |

老周看完说：「我要的不是 AI 替 HR 回答问题，而是**让员工先问 AI、问不对时能马上找到最新文档和真人**——省的是重复劳动，不是省掉责任。」

苏念在复盘最后一页写：**RAG 知识库问答的目标，不是做一个「什么都能答」的 Oracle，而是做一个「查得到、引得明、错得起、改得快」的企业知识接口。**

# 3. 系统正解

这个系统的核心组件和数据流可以概括如下：

**文档采集 → 清洗与切块 → 向量化入库 → 用户提问 → Query 改写 → 权限过滤 → 混合检索 → Rerank 重排 → 上下文组装 → 大模型生成（带引用）→ 置信度判断与人工兜底 → 反馈回写优化索引。**

回扣故事：林涛问招待费上限，对应「Query 改写 + 混合召回 + Rerank」；答成 2023 年的 800 元，对应「旧版 Chunk 未降权 + 表格切块失败 + 2025 版 rank 过低被截断」；财务驳回，对应「缺少版本优先与低置信兜底」；驻外补贴瞎答，对应「检索弱相关时生成层幻觉」；Bad Case 队列和 14 天新规降权，对应「反馈闭环 + 文档生命周期管理」。

在 AI 产品岗的典型应用场景：

- **需求文档**：不只写「对接企业知识库」，要写清文档格式、切块策略、元数据字段（版本号、生效日、部门权限）、检索阈值、无答案时的降级话术、引用展示规范。
- **方案评审**：当业务方说「把所有 PDF 扔进去就能用」时，追问——「旧版怎么办？表格怎么切？更新延迟能接受多久？错答谁负责？」
- **指标设计**：同时看回答满意度、引用点击率、Bad Case 率、转人工率、**错答造成的业务损失**；单一追求「自动回答率」会逼系统在灰区瞎答。
- **跨团队沟通**：跟法务说「文档要有生效日和失效策略」；跟工程说「权限过滤必须在检索前」；跟算法说「财务域阈值要比通用域更保守」；跟运营说「Bad Case 不是客服工单，是知识库迭代输入」。

# 4. 类比锚定

## 旧知 → 新知：公司图书馆的参考咨询台

传统 PM 都去过图书馆：读者带问题来 → 馆员查卡片目录/数据库 → 找到相关书架和页码 → 把书翻到章节指给读者 → 若资料过期或没有，馆员说「这个我们没收录，我帮你联系采购/其他分馆」。

RAG 知识库问答，就是把这个流程自动化，且 7×24 小时营业——但「馆员会不会指错书、会不会把两本书的内容拼错」，依然是核心风险。

| 你熟悉的旧经验 | RAG 知识库问答系统 |
|---------------|-------------------|
| 图书目录卡片（书名、作者、版本） | 文档元数据（标题、部门、版本号、生效日、权限） |
| 一本书拆成章节上架 | PDF/Word 切块（Chunk）后向量化入库 |
| 读者描述模糊需求 | 用户自然语言提问 + Query 改写 |
| 馆员查索引找书架 | 向量检索 + 关键词混合召回 |
| 馆员对比多本书选最相关的 | Rerank 重排序 |
| 翻到具体页码指给读者 | 上下文组装 + 带引用的生成答案 |
| 资料太旧或馆藏没有 | 低置信降级 / 转人工 / 推送最新文档链接 |
| 读者反馈「这本书不对」 | Bad Case 标注 → 文档修正 / 切块策略调整 |

# 5. 类比边界与系统要点

## 类比在哪里会失效

图书馆的书是静态、有 ISBN 的，一本就是一本；企业知识库里有「2023 版 + 2025 版 + FAQ 摘要 + 培训 PPT 截图」并存，**同一问题的答案会随版本和时间变**。馆员可以凭经验说「以最新版为准」，RAG 系统若没把「版本优先」写进检索逻辑，就会同时引用新旧两本书拼答案。

## A. 系统核心要点总结

- **数据输入要求与格式规范**：文档需结构化元数据（版本、生效日、权限域、文档类型）；扫描件/OCR/表格/幻灯片要单独定义切块与清洗规则，不能和纯文本同一套参数。
- **AI 模型的能力边界与置信度**：向量相似度 ≠ 业务正确性；Rerank 也可能把「表述像」的旧文档排到前面。生成层再守规矩，也救不了检索层的版本错误。
- **人工介入的触发条件与流程**：低置信度、多版本冲突、涉及金额/合规/人事结论、用户连续点踩——必须触发警告、转人工或只给链接不给结论。
- **系统的容错与降级机制**：检索失败 → 弱相关 → 多版本冲突 → 转人工，应是一条显式降级链；财务/法务域应比通用域更保守。
- **成本结构**：计算成本（Embedding、检索、Rerank、生成调用）、人工成本（文档维护、Bad Case 标注、法务审核）、纠错成本（错答导致的审批返工、合规风险）要一起算；re-index 频率和实时性也是成本项。

## B. 类比失效点

1. **图书馆书不会自己「改内容」**：企业文档每周都在变，索引延迟、旧版未下线、增量切块失败，都是图书馆类比覆盖不了的动态问题。
2. **馆员会说不确定，模型默认要「像答案」**：大模型有补全倾向，检索弱相关时更容易把半相关片段缝成像真的答案——这是概率性输出特有的风险。
3. **馆藏有物理边界，向量库会「相似即相关」**：语义相近但业务域不同的段落（「出差补贴」vs「驻外补贴」）可能被误召回，馆员靠专业判断，系统靠阈值和域标签——这些都要产品显式配置。
4. **借阅记录 ≠ 可审计的知识引用链**：合规场景需要「某次回答引用了哪版文档哪一段、谁审批生效」，比图书馆借书卡更严格；PM 要设计引用日志和版本快照。
5. **规模放大后，切块策略比模型选型更决定成败**：书少时馆员能手工找；文档上万份时，Chunk 切法、表格处理、版本策略才是准确率的主因，不是换一个更大的模型就能解决。

# 6. 深度业务洞察

1. **业务侧：表面要「员工自助问 AI」，真实要「减少错答带来的隐性成本」**  
   业务方常把 KPI 写成「问答覆盖率 90%」，但 HR/财务最怕的是「 confidently wrong（自信地说错）」。一个错答的审批返工，成本远高于十次「我不知道，请点这里看最新制度」。PM 要在方案里为「拒答」设计产品体验，而不是把它当失败。

2. **技术侧：RAG 难在「检索工程」，不在「聊天 UI」**  
   很多项目 80% 时间花在 Prompt 调优，但真正决定准确率的是：切块、元数据、版本策略、混合召回、Rerank、上下文截断。PM 若不懂这些环节，会把所有 Bad Case 都推给「换个模型」——往往换三次也没用。

3. **运营侧：知识库是「活的内容产品」，不是一次性导入**  
   冷启动期文档质量参差、旧版堆积、FAQ 和正文冲突——此时应提高转人工比例，用 Bad Case 驱动文档治理。数据飞轮是：错答 → 标注 → 修文档/调切块/调阈值 → 错答下降；没有闭环，RAG 会越用越让人不信。

4. **合规侧：引用可追溯是底线，不是加分项**  
   人事、财务、法务域的问答，审计时要能还原「当时系统引用了什么」。不能只存最终回复文本，要存检索结果快照、文档版本 hash、阈值与策略版本——否则一次错答可能变成合规事件。

5. **商业侧：ToB 卖 RAG 别只报「节省多少客服」**  
   客户教育成本很高：「扔 PDF 就能用」的期望必须在上售前 managed（管理预期）。定价应区分文档量、更新频率、域数量、是否要人工审核环、是否含 Bad Case 运营——否则交付会被文档质量拖垮，ROI 算不清。

### 动手小练习（30 分钟）

**练习：手工模拟一次「会答错的 RAG」**

1. 找一份你熟悉的公司制度（或任意公开 FAQ），复制全文到文档；  
2. 人工按 200 字一切块，编号 Chunk 1–N；  
3. 写 3 个用户问题，每个问题手动选出「你会喂给模型的 Top-3 Chunk」；  
4. 故意再写一份「旧版制度」仅改一个关键数字，重复步骤 2–3；  
5. 看旧版是否会在某个问题上「更像」用户提问——那就是你要在 PRD 里写的「版本降权 / 生效日过滤 / 低置信拒答」触发点。

完成后自问：如果业务方要求「不要拒答、都要给结论」，你愿意在哪个域（财务/法务/通用）签字负责？——答案会帮你定阈值策略。
