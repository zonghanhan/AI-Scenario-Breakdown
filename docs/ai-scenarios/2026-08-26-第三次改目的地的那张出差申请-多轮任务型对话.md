前三篇我们分别讲了：用户来问，机器人答（客服）；用户留了电话，机器人追（线索跟进）；员工问制度，机器人查（政策问答）。今天收束整个对话式 AI 系列：**当用户说的不是「告诉我」，而是「帮我办」——系统怎么在多轮来回里记住进度、补全信息、处理改口、跑题回来、最后真正提交一张单。** 如果你做过表单设计、审批流、或任何「填一半保存草稿」的产品，这篇会把「聊天」和「办事」之间的产品边界讲透。

# 2. 业务场景故事

## 《第三次改目的地的那张出差申请》

### 第一章：一句「帮我订下周出差」，系统其实收到了一张空表

9 月 2 日周二上午 10:17，云杉科技华东区售前经理陈磊在飞书 @ 了差旅助手：

> 「帮我订下周出差，去见个客户。」

要是按传统 OA 表单，陈磊得打开「差旅申请」→ 选出发城市 → 填目的地 → 选日期 → 写事由 → 选交通等级 → 估预算 → 选审批人 → 提交。平均耗时 8–12 分钟，销售同事最烦的是**客户临时改约，整张单推倒重来**。

Beta 版差旅助手 3 秒就回了：

> 好的，已为您创建出差申请草稿。请问目的地是哪里？

陈磊：「上海。」

> 出发和返回日期？

陈磊：「下周二去，周四回。」

到这里还算顺利。但陈磊下一句是：

> 「对了，公司高铁能坐几等座来着？」

Beta 版立刻把对话状态**清零**，重新检索知识库，回了一大段《差旅管理制度》第三章全文。陈磊等了 20 秒，发现**刚才填的上海、日期全没了**，得从头再说一遍。

产品新人周扬——刚从前一家 SaaS 公司的流程产品转做 AI 产品——被陈磊在群里 @ 了。周扬原本以为多轮任务对话就是「客服问答 + 最后调个 API」，陈磊只问了一句：

「**我跟它说了三遍上海，它怎么还能问我『目的地是哪里』？**」

**悬念**：周扬很快会发现，多轮任务型对话的难点从来不是「听懂第一句话」，而是**在七八轮来回里维持一张不断被修改的「隐式表单」**——用户会改口、会跑题、会隔天接着聊，而系统必须在某个时刻干脆利落地问一句：「确认提交吗？」

### 第二章：一张出差申请，背后藏着十二个槽位

周扬拉着差旅运营、OA 研发、对话工程把陈磊这次会话做了完整复盘。一次看似简单的「订出差」，系统在后台要维护一张**对话状态表**（Dialogue State，当前对话里已收集到的任务信息快照）：

| 槽位（Slot，待填字段） | 是否必填 | 陈磊第 1 轮值 | 来源 |
|----------------------|---------|-------------|------|
| 出发城市 | 必填 | 上海（默认工作地） | HRIS 注入 |
| 目的地 | 必填 | 上海 | 用户口述 |
| 出发日期 | 必填 | 2026-09-09（下周二） | 用户口述 |
| 返回日期 | 必填 | 2026-09-11（周四） | 用户口述 |
| 出差事由 | 必填 | **空** | 未收集 |
| 客户/项目名称 | 条件必填 | **空** | 销售岗必填 |
| 交通方式 | 必填 | **空** | 未收集 |
| 舱位/座席等级 | 条件必填 | **空** | 依赖交通方式 |
| 住宿需求 | 选填 | **空** | 未询问 |
| 预估费用 | 必填 | **空** | 可系统估算 |
| 审批链 | 必填 | **空** | 规则引擎生成 |
| 是否超标 | 系统计算 | **未知** | 依赖费用+制度 |

**「槽位填充」（Slot Filling）** 就是多轮任务对话的核心动作：每轮用户话里能提取的字段写进状态表，缺的字段由系统**主动追问**——但追问有顺序、有策略，不是把 12 个问题一次性甩给用户。

Beta 版的两个致命设计失误：

1. **跑题没隔离**：陈磊问「高铁几等座」是**政策咨询子意图**，应插入一个「问答支线」答完回到主任务，而不是重置主任务状态。
2. **追问顺序错乱**：在事由、客户名都没填的情况下就去估费用——后面全得重算。

正式版对话策略（周扬写在 PRD 里的「填槽优先级」）：

```
P0：目的地 + 日期（决定能不能往下走）
P1：事由 + 客户/项目（销售岗合规要求）
P2：交通 + 座席（依赖制度校验）
P3：住宿 + 费用估算
P4：审批人确认
→ 全部必填槽满 → 汇总确认卡片 → 用户点头 → 调 OA API 提交
```

**悬念**：槽位凑齐了就能提交吗？陈磊的会话还没完——客户临时改了约。

### 第三章：用户第三次改目的地，系统能不能不崩溃

9 月 3 日，陈磊接着昨天的草稿继续聊（飞书会话 ID 未变，但已隔 18 小时）：

> 「客户改约了，不去上海了，改杭州。出发还是下周二，但要住到周五。」

这里同时发生了四件事：

**事件 1：槽位覆写（Slot Update）**

| 槽位 | 旧值 | 新值 | 触发动作 |
|------|------|------|---------|
| 目的地 | 上海 | **杭州** | 费用重估、审批链可能变化 |
| 返回日期 | 9/11 | **9/12（周五）** | 住宿晚数 +1 |
| 出发日期 | 9/9 | 9/9（未变） | 无 |

系统不能简单覆盖——要触发**依赖槽位级联更新**：上海→杭州，高铁二等座预估从 ¥553 变 ¥73（杭州更近，陈磊 base 苏州）；住宿从 2 晚变 3 晚；预估总费用变化，**超标状态要从「未超标」重新计算**。

**事件 2：变更次数风控（防折腾）**

Beta 版没限制，陈磊测试时改过 5 次目的地，每次覆盖都不留痕。正式版规则：**同一草稿核心槽位（目的地/日期）修改 ≥3 次**，系统弹出：

> 「您已第三次调整行程。为避免审批反复，建议确认本次信息后再提交。需要我帮您 **转差旅专员人工协助** 吗？」

不是惩罚用户，是**保护审批人不被同一张单反复打扰**——产品要算的是组织成本，不只是对话轮次。

**事件 3：澄清歧义（「下周二」在不同日期说，值不同）**

陈磊 9 月 2 日说「下周二」= 9 月 9 日；若 9 月 8 日再说「下周二」= 9 月 16 日。对话状态里日期槽必须存**绝对日期**，不能只存「下周二」这个相对表达。周扬要求 NLU 输出层强制做**日期归一化**，并在确认卡片里用绝对日期展示：「2026-09-09（周二）」，不让审批人猜。

**事件 4：支线回归（政策问答嵌套在主任务里）**

陈磊又问：「杭州出差住宿标准多少？」

正式版处理：

```
[主任务状态：冻结，不丢失]
  → 进入子意图「政策咨询」
  → 调制度 RAG：P6 销售、二线城市、住宿上限 ¥450/晚
  → 回答完毕
  → 自动回到主任务：「好的。按标准您 3 晚住宿上限 ¥1,350。继续确认交通方式？」
```

**对话管理器（DM，Dialogue Manager）** 在这里维护两棵树：主任务树（填槽→确认→提交）和临时问答枝（答完即焚）。Beta 版把两棵树当成一棵树，一跑题就全砍。

### 第四章：确认闸门——差一个「对」字，就不能调 OA 写接口

槽位终于填满。正式版不直接提交，而是弹出**汇总确认卡片**（这是多轮任务对话里最关键的「硬闸门」）：

```
【出差申请草稿 · 请确认】
行程：苏州 → 杭州
时间：2026-09-09（周二）至 2026-09-12（周五），共 4 天 3 晚
事由：拜访杭州智云科技，推进 Q3 合作框架协议
交通：高铁 二等座（符合 P6 标准）
住宿：经济型酒店，预估 ¥1,200（3 晚 × ¥400，未超标）
费用合计：约 ¥1,580
审批链：直属上级 王莉 → 区域总监 赵峰
[确认提交]  [修改某项]  [保存草稿]  [取消]
```

陈磊点了「修改某项」→ 选「交通」→ 说「这次想坐飞机，省点时间」。

系统立刻：

1. 交通槽改为「飞机经济舱」
2. 重算费用：+ ¥680
3. 规则引擎命中：**苏州-杭州高铁 1.5 小时，飞机未体现「时间紧迫」事由，经济舱需直属上级 + 说明理由**
4. 插入追问：「高铁约 1.5 小时。若选飞机，需在事由中补充时间紧迫说明。是否添加？」

陈磊添加了「客户要求 9 日上午 10 点前到场签约」。系统更新事由槽，重新生成确认卡片。**直到陈磊点「确认提交」，才调用 `OA.create_travel_request` API**——中间无论多少轮，生产数据不动。

周扬跟研发强调：**这不是模型「谨慎」，是产品红线**。涉及创建/修改/提交审批单的操作，必须有人类明确确认动作（点击按钮或口令「确认提交」），不能靠模型判断「用户应该同意了」。

### 第五章：提交之后还有对话——状态不能丢在半路

陈磊确认提交。OA 返回申请单号 TR-2026-09182，状态「审批中」。助手：

> 已提交，单号 TR-2026-09182。王莉预计今日 18:00 前审批。需要我 **审批通过后自动预订高铁** 吗？

陈磊：「要，还是二等座。」

这是**任务完成后的延伸对话**——主任务状态从 `filling_slots` → `submitted` → `awaiting_approval` →（未来）`booking`。新槽位「是否代订」「座席偏好」挂载在**子任务「预订」**上，而不是新开一个无关会话。

9 月 4 日王莉驳回：「客户名称写错了，是『智云数据』不是『智云科技』。」

陈磊在**同一会话**里说：「把客户改成智云数据，重新提交。」

系统识别为**修订已驳回单**意图（不是新建），调用 `OA.update_travel_request(TR-2026-09182)`，只改客户槽，其余不变，再次走确认闸门。

上线两周数据：

| 指标 | 传统 OA 表单 | 多轮任务对话助手 |
|------|------------|----------------|
| 平均完成时长 | 11 分钟 | 4 分 20 秒 |
| 一次性提交成功率 | 62% | 78% |
| 填表中途放弃率 | 23% | 9% |
| 因信息错误被驳回率 | 18% | 7% |
| 平均对话轮次 | — | 6.8 轮 |
| 跑题后成功回归主任务率 | Beta 版 41% | 正式版 89% |
| 人工差旅专员介入率 | — | 6%（三次改目的地/超标/系统异常） |

周扬在复盘里写：**多轮任务对话的成功标准不是「聊得像人」，而是「事办成了、且办对、且可审计」**。陈磊省了 7 分钟，审批人少驳回一次——ROI 在这里，不在「对话多自然」。

# 3. 系统正解

多轮任务型对话系统 = **意图识别（区分「办事」vs「问答」）** → **对话状态管理器（维护槽位表 + 任务阶段）** → **槽位填充策略（优先级追问 + 依赖级联更新）** → **支线隔离与回归（政策问答不冲掉主任务）** → **业务规则引擎（超标/审批链/座席等级）** → **汇总确认闸门（人类显式授权）** → **业务系统 API 调用（OA/CRM/预订）** → **任务后状态延续（审批中/预订/修订）** → **会话持久化与审计日志**。

回扣故事：陈磊的「下周出差」触发**槽位表初始化**；问「高铁几等座」走**支线隔离**，正式版用冻结主状态 + 答完回归；三次改目的地触发**级联重算 + 变更风控**；飞机超标走**规则引擎追加说明槽**；「确认提交」是**写操作硬闸门**；驳回后「改客户名」是**同会话任务修订**而非新会话。

**AI 产品岗典型应用场景：**

- **需求文档**：不写「支持多轮对话」，要写槽位清单（必填/选填/条件必填）、填槽优先级、支线意图列表、确认卡片字段、写操作触发条件、会话超时与草稿恢复规则——研发能据此实现状态机，业务能验收「改三次会不会丢数据」。
- **方案评审**：问业务「哪些槽位允许用户跳过、哪些必须追问」；问研发「会话状态存 Redis 还是 DB、超时多久」；问合规「对话记录能否作为审批依据」；问运营「转人工后助手是否旁路只读展示已填槽位」。
- **指标设计**：任务完成率、一次性提交成功率、驳回率、平均填槽轮次、跑题回归成功率、确认前放弃率、级联重算次数、人工介入率——**不要只盯对话轮次越少越好**（轮次太少可能是漏问必填项）。
- **跨团队沟通**：跟 OA 团队对齐 API 幂等（重复提交怎么办）；跟 HR 制度团队对齐槽位校验规则；跟审批流团队对齐「修订驳回单」vs「新建单」的状态机；跟客服团队对齐「对话办不了」时的转人工话术和上下文交接。

# 4. 类比锚定

**核心类比：多轮任务型对话 ≈ 旅行社定制行程的资深顾问**

你没去过某家店，但多半经历过：告诉顾问「想下周出去玩」，对方一边记小本本一边问「几个人、几天、预算、喜不喜欢爬山」，你突然问「那边现在热吗」，顾问答完接着问「那酒店您偏景区还是市区」，最后念一遍完整行程等你点头才下单——**不是聊完才想起来订，而是一路记着、一路改、最后确认才出票**。

### 类比映射表

| 旅行社定制顾问（旧经验） | 多轮任务型对话系统（新系统） |
|------------------------|---------------------------|
| 顾问面前的小本本 | 对话状态表（槽位 + 当前阶段） |
| 「几位、几天、预算」标准追问 | 填槽策略与优先级（P0–P4） |
| 客户说「改成杭州」顾问划掉重写 | 槽位覆写 + 依赖级联重算 |
| 客户问「那边签证要多久」插一句 | 支线意图（政策问答）+ 主任务冻结 |
| 顾问念一遍行程「您确认吗」 | 汇总确认卡片 + 写操作硬闸门 |
| 「好的」之后才刷卡出票 | 用户确认 → 调用业务 API |
| 出票后改航班要查订单号 | 任务后状态延续 + 修订 vs 新建 |
| 顾问搞不定复杂签证转专员 | 变更超阈值 / 超标 → 转人工 |
| 小本本留档备查 | 会话审计日志（每轮槽位快照） |

# 5. 类比边界与系统要点

## A. 系统核心要点总结

- **数据输入要求与格式规范**：每个任务类型预定义槽位 schema（字段名、类型、必填规则、校验规则）；NLU 输出必须归一化（相对日期→绝对日期、城市名→标准编码）；HRIS/组织架构数据作为默认值注入，减少用户重复输入。
- **AI 模型的能力边界与置信度**：模型擅长从自然语言**抽取**槽位值，不擅长判断「审批该不该过」「费用是否合规」——这些交给规则引擎。槽位置信度 < 阈值时必须追问确认，不能静默写入状态表。
- **人工介入的触发条件与流程**：核心槽位反复修改超阈值、费用超标需特批、系统 API 失败、用户主动要求、涉及敏感变更（国际差旅/高管出行）。转人工时交接**完整槽位表 + 对话历史 + 当前阶段**，专员从断点继续，不让用户重讲。
- **系统的容错与降级机制**：OA API 超时 → 保存草稿 + 提示稍后重试，**不丢已填槽位**；NLU 抽取失败 → 降级为结构化选项（「请选择交通方式：[高铁][飞机][自驾]」）；会话超时（如 24 小时）→ 草稿恢复提示「您有未完成的出差申请，是否继续？」
- **成本结构**：LLM 每轮推理成本 × 平均轮次 + 会话状态存储 + 业务 API 调用 + 规则引擎维护 + 人工兜底。ROI 来自**表单完成率提升 + 审批驳回减少 + 销售/员工时间节省**，不是替代整个 OA 系统。
- **审计与合规**：每次槽位变更留快照（谁、何时、改了什么、改前改后）；写操作必须有确认动作记录；对话记录能否作为内部审计依据需法务确认。

## B. 类比失效点

1. **真人顾问一次服务一位客户，系统同时服务数千会话**：每个会话的状态必须严格隔离，**不能 A 用户的「上海」写进 B 用户的槽位表**——Session ID 绑定是工程底线，类比不会告诉你并发隔离成本。
2. **顾问能看客户表情判断「他其实还没想好」**：AI 不知道用户是「犹豫」还是「说错了」。产品不能靠猜，**关键槽位必须确认卡片显性展示**，不能模型觉得对就直接提交。
3. **旅行社顾问不会第 2 轮就忘了你说过要去上海**：Beta 版跑题重置就是「失忆」。AI 系统的状态管理是**显式工程**，不是模型天然记忆——长会话还要处理上下文窗口截断，必要时只把槽位表注入 Prompt，而不是塞满全部对话历史。
4. **顾问的「标准追问」靠经验，系统要靠可配置策略**：不同岗位（销售/研发/高管）槽位 schema 不同、填槽顺序不同、审批链不同——**一套对话流不能全公司通用**，需要任务类型 × 岗位 × 部门的配置矩阵，类比掩盖了配置爆炸的产品复杂度。
5. **顾问改行程会主动提醒「机票退票费谁承担」**：级联影响不只是重算数字，还涉及**业务副作用**（已审批单修改需重新走审批、已预订需取消）。对话系统必须和 OA 状态机深度耦合，不是聊天机器人外接一张表单。
6. **AI 抽取是概率性的，表单字段是确定性的**：同一句「下周二去」可能抽成错误日期；**关键字段要双重校验**（NLU 抽取 + 确认卡片展示 + 用户点击），不能把「聊得像理解了」等同于「数据对了」。

# 6. 深度业务洞察

1. **业务侧：用户要的是「少填表」，不是「陪聊天」**  
   销售同事要的是 4 分钟办完，不是觉得机器人风趣。每多一轮无效追问，放弃率就涨一截。产品要用**能注入的不问**（工作地、职级、默认审批人）、**能推断的先填后确认**（「下周二去周四回」直接展示日期让用户点头）、**真缺了再问**。陈磊烦的不是对话，是**问了又忘**。

2. **技术侧：对话状态管理器比 LLM 选型更重要**  
   很多项目 80% 精力调 Prompt 让回答更自然，翻车全是**跑题丢状态、改槽不级联、重复提交**。PM 的 P0 验收用例应是：「第 5 轮跑题问政策，第 6 轮说改目的地，系统是否保留事由且重算费用」——不是测模型文风。

3. **运营侧：槽位 schema 是「活文档」，随制度变**  
   差旅制度改了住宿标准，不只是 RAG 文档更新，**规则引擎和填槽追问逻辑也要改**。一次制度修订 = 对话策略表 + 规则表 + 确认卡片文案三处同步。没人维护的配置，三个月后就变成「问一堆过时问题」。

4. **合规侧：对话草稿算不算「正式申请」**  
   法务会问：用户聊到一半走了，槽位里写了「去客户处送礼」，日志算不算员工正式陈述？产品要明确：**草稿态不等于提交态**，审计日志分阶段；确认提交前的槽位变更标记为「未生效意向」，避免后续纠纷。

5. **商业侧：别和 OA 厂商抢「表单」，抢「表单前那段体验」**  
   大企业 OA 表单短期不会消失。多轮任务对话的定位是**表单前置收集器 + 智能校验层**，提交后仍进原有审批流。ROI 算法：（节省的填表时间 × 人数 × 时薪）+（减少驳回往返 × 审批人时薪）−（LLM + 研发维护成本）。卖给业务负责人时，**用驳回率和完成率说话**，不要用「我们也有 ChatGPT」说话。

### 动手小练习（30 分钟）

**练习：画一张「出差申请」对话状态机**

纸笔或 Excalidraw 即可。要求：

1. 画出至少 5 个状态：`空闲` → `填槽中` → `政策支线` → `待确认` → `已提交` → `修订中`  
2. 标注每个状态的**进入条件**和**退出条件**  
3. 设计 3 条测试路径：  
   - 路径 A：正常填完一次提交  
   - 路径 B：第 3 轮跑题问制度，第 4 轮回来改目的地  
   - 路径 C：提交被驳回，同会话改一个槽位重提  
4. 自问：哪条路径最容易丢状态？你的设计里用什么机制防止（冻结、快照、版本号）？

完成后对照本篇第二章槽位表，检查：**有没有哪个必填槽位在你的状态机里永远问不到？**
